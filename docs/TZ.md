## 1. Суть

Сервис автоматически сверяет три массива документации объекта капитального строительства:

- **ПД** — проектная документация (стадия P);
- **РД** — рабочая документация;
- **ИД** — исполнительная документация.

Проверка идёт по **Матрице контроля из 132 параметров** и заканчивается **протоколом несоответствий** с привязкой к документу, странице и области на листе (bbox). Инспектор подтверждает или отклоняет найденные расхождения в веб-интерфейсе. Результаты уходят во внешнюю ИС **ИАИС «РиН»**.

Главный принцип ТЗ: **система не выносит нарушений сама**. Модель находит `CANDIDATE`, а `CONFIRMED_VIOLATION` ставит только инспектор. Некачественные входные данные дают отдельные статусы (`MISSING_EVIDENCE`, `NOT_COMPARABLE`, `CLARIFICATION_REQUIRED`) и не считаются нарушениями.

| ID | Требование |
|---|---|
| REQ-UPL-01 | `POST /api/v1/documents/upload` → `process_id` |
| REQ-UPL-02 | Неподдерживаемый формат → отказ с перечнем форматов (PDF, DOCX, XML) |

| REQ-UPL-05 | Пакет > **200 МБ** → отказ всего пакета с указанием лимита |
| REQ-UPL-06 | Таймаут обработки → **до 2 повторов**, затем уведомление администратора |
| REQ-UPL-07 | Инкрементальная дозагрузка без перезагрузки имеющихся файлов, до финализации |
| REQ-UPL-08 | Антивирусная проверка каждого файла до сохранения |

| REQ-UPL-10 | *(Перечень ИД ред. 1.1)* Каждый комплект сопровождается **машиночитаемым реестром файлов** (CSV/XLSX/JSON): `object_id`, `file_id`/`file_name`/SHA-256, `doc_stage`, `discipline`, `document_code`, `revision`, `approval_status` (DRAFT/APPROVED/FOR_CONSTRUCTION/SUPERSEDED/CANCELLED), `approval_date`, `sheet_page_range`, `predecessor_id`/`successor_id`, `signature_status`. Без реестра пакет принимается со статусом `CLARIFICATION_REQUIRED` — [domain/registry.md](domain/registry.md) |
| REQ-UPL-11 | Система хранит исходный файл, его хеш и цепочку редакций. **Перезапись под тем же `file_id` запрещена**; повторная загрузка создаёт новую запись и новую версию протокола. Выбор источника: одна утверждённая редакция → эталон; заменённая → хранится, но исключается; неоднозначно → `CLARIFICATION_REQUIRED` (вывод о нарушении блокируется); нет документа → `MISSING_EVIDENCE`; неприменим → `NOT_APPLICABLE` с основанием; нечитаем → `NOT_COMPARABLE` |

| REQ-PRS-02 | **Exact Match ≥ 0.90** для ключевых полей: шифр, стадия, редакция, номер листа/страницы, номер помещения/элемента |
| REQ-PRS-03 | Рукописные и нечитаемые зоны → вернуть `LOW_QUALITY` или `ABSTAIN`; долю таких зон и покрытие фиксировать в отчёте |
| REQ-PRS-04 | NLP-извлечение по `regex_pattern` + семантическим якорям (Sentence-BERT) |
| REQ-PRS-05 | CV для чертежей: масштаб по размерной линейке, распознавание линий, измерение расстояний |
| REQ-PRS-06 | Для каждого значения сохраняются `file_id`, SHA-256, стадия, шифр, редакция, статус утверждения, лист/страница, **bbox/polygon в [0;1]** видимой области страницы с учётом CropBox, MediaBox и Rotate |
| REQ-PRS-07 | Кеш парсинга в Redis по хешу файла |
| REQ-PRS-08 | Метаданные каждого файла: `object_id, doc_stage, discipline, document_code, revision, approval_status, approval_date, sheet/page, file_hash`, связь predecessor/successor |

Устаревшая редакция эталоном быть не может. Конфликт редакций, отсутствие утверждения или неоднозначная связь → `CLARIFICATION_REQUIRED`, вывода о нарушении нет |

## 6. Сравнение и протокол (REQ-CMP)

| ID | Требование |
|---|---|
| REQ-CMP-01 | Единица результата — **evidence_group**: объект + параметр/правило + актуальные ПД/РД/ИД + фрагменты |
| REQ-CMP-02 | В каждом запуске и протоколе фиксируются `matrix_version, dataset_version, model_version, input_manifest_hash` |
| REQ-CMP-03 | Сценарий: `FULL` (ПД+РД+ИД), `PD_RD_ONLY`, `PD_ID_ONLY`, `RD_ID_ONLY`, `SINGLE_ONLY`, `PARTIALLY_LOADED` |
| REQ-CMP-04 | Порядок проверки параметра: применимость → комплектность доказательств → актуальность и сопоставимость редакций → **только потом** предметное сравнение |
| REQ-CMP-05 | Результат сравнения: `expected_value, actual_value, delta` и статус `CANDIDATE` или `NEGATIVE_VERIFIED`. Модель **никогда** не ставит `CONFIRMED_VIOLATION` |
| REQ-CMP-06 | Если правилу хватает двух стадий, сравнение парное, неприменимая стадия получает `NOT_APPLICABLE`. Нет обязательного источника → `MISSING_EVIDENCE` (не нарушение) |
| REQ-CMP-07 | Недостаточно доказательств или источники несопоставимы → `NOT_COMPARABLE`. Редакция не определена → `CLARIFICATION_REQUIRED` |
| REQ-CMP-08 | Протокол (JSON/PDF) содержит разделы: «Статус загрузки документов», «Тип проверки» и **5 отдельных таблиц**: (1) комплектность и сопоставимость; (2) кандидаты; (3) подтверждённые нарушения; (4) проверенные отрицательные; (5) гипотезы |
| REQ-CMP-09 | **Карточка доказательства** обязательна для каждого кандидата: `finding_id`, код параметра/правила, expected/actual, `file_id` и SHA-256 каждого источника, стадия, шифр, редакция, статус утверждения, лист/страница, bbox/polygon, обоснование, уровень риска, решение инспектора и его причина |
| REQ-CMP-10 | Протокол сохраняется в `Protocols` с версией, процесс переходит в `READY`, инспектор получает уведомление |
| REQ-CMP-11 | При дозагрузке **пересчитываются только затронутые параметры**. Прошлая версия протокола остаётся в истории |
| REQ-CMP-12 | Формат протокола задан **Приложением № 2** (обязателен, но **отсутствует у нас**) |

**Статусы findings (REQ-CMP-13):**

| Статус | Нарушение? | Кто ставит |
|---|---|---|
| `NEGATIVE_VERIFIED` | нет (отрицательный пример) | модель или инспектор |
| `CANDIDATE` | нет | модель |
| `CONFIRMED_VIOLATION` | **да** | только инспектор |
| `MISSING_EVIDENCE` | нет | модель |
| `NOT_APPLICABLE` | нет | модель или инспектор |
| `NOT_COMPARABLE` | нет | модель |
| `CLARIFICATION_REQUIRED` | нет | модель или инспектор |
| `SUSPICION` | нет | модуль гипотез |

Уровень риска (HIGH/MEDIUM/LOW) задаёт **только очерёдность** проверки и не является юридическим основанием.

## 7. Верификация (REQ-VER)

| ID | Требование |
|---|---|
| REQ-VER-01 | Для каждого кандидата на одном экране: expected и actual, страницы ПД/РД/ИД с подсвеченными областями, шифры, редакции, статус утверждения, ссылка на согласованное изменение. Комплектность показывается отдельно |
| REQ-VER-02 | «Подтвердить» → `CONFIRMED_VIOLATION`. Фиксируются `user_id`, timestamp, комментарий |
| REQ-VER-03 | «Отклонить» → `NEGATIVE_VERIFIED`. **Обязательны `reason_code` и комментарий** |
| REQ-VER-04 | «Требует уточнения» → `CLARIFICATION_REQUIRED` |
| REQ-VER-05 | Составной кандидат **делится на атомарные findings**, у каждого своё решение. Статуса `PARTIALLY_CONFIRMED` нет |
| REQ-VER-06 | Дозагрузка во время верификации не сбрасывает уже принятые решения, после неё идёт инкрементальный пересчёт |
| REQ-VER-07 | Финализация возможна, только когда каждый `CANDIDATE` обработан или переведён в `CLARIFICATION_REQUIRED`. `MISSING_EVIDENCE` выводится отдельным списком |
| REQ-VER-08 | После финализации дозагрузка и смена статусов запрещены |
| REQ-VER-09 | Отменить финализацию может только ADMIN или SUPERVISOR с указанием причины (пишется в аудит). После отмены статус `VERIFICATION_COMPLETED` |
| REQ-VER-10 | Юзабилити: весь цикл (132 параметра, 14 нарушений) ≤ 30 мин, **≤ 3 кликов на одно нарушение**. «3 клика» — не более трёх осознанных действий **от открытия карточки** до сохранённого решения |
| REQ-VER-11 | Инспектор может выбрать авторитетную редакцию (с основанием) и **править доказательные фрагменты** (добавить, исправить, удалить) — новой версией (кто, когда, причина, ссылка). **Метаданные не правит**, машинный результат не перезаписывается |
| REQ-VER-12 | Одно рабочее окно: карточка + **синхронные панели ПД / РД / ИД** (файл, шифр, редакция, статус, переход к доказательству). Массовое решение по одному параметру — допустимо, **массовое отклонение — нет** |

Статусы верификации: `PENDING, CONFIRMED_VIOLATION, NEGATIVE_VERIFIED, CLARIFICATION_REQUIRED, VERIFICATION_COMPLETED, PROTOCOL_FINALIZED`.

## 8. Дообучение и GOLD (REQ-ML)

| ID | Требование |
|---|---|
| REQ-ML-01 | GOLD включает только `CONFIRMED_VIOLATION` (позитив) и `NEGATIVE_VERIFIED` (негатив) с полными карточками. `CANDIDATE`, `SUSPICION`, `MISSING_EVIDENCE` и незавершённые решения в обучение не берутся |
| REQ-ML-02 | Отклонённые записи попадают в **черновик** набора. В `dataset_version` запись входит только после проверки куратором |
| REQ-ML-03 | Разбиение train/val/test **по object_id**. Hidden test и его SHA-256 фиксируются заранее |
| REQ-ML-04 | Модель публикуется только при выполнении порогов из §14, при падении Recall любой категории не более чем на 2 п.п. и росте FPR не более чем на 2 п.п. Решение подписывает ответственный, откат должен быть возможен |
| REQ-ML-05 | По каждой итерации хранятся `model_version, dataset_version, matrix_version`, хеши наборов, код и параметры обучения, метрики, решение, ответственный, предыдущая модель |
| REQ-ML-06 | Еженедельный отчёт для ML-инженеров: статистика отклонений и рекомендации |
| REQ-ML-07 | Воспроизводимый контур (сбор, проверка полноты доказательств, разбиение по object_id, хеши наборов) и **настоящее дообучение** |
| REQ-ML-08 | *(Приложение 1, лист СХЕМА GOLD)* Запись GOLD: `evidence_group_id`, `finding_id`, `object_id`, `matrix_code`/`rule_version`, `expected_value`, `actual_value`; для источников ожидаемого и фактического значения — `file_id`+sha256, стадия/шифр/редакция/статус утверждения, страница + `bbox_polygon` в [0;1]; `approved_change_ref` (или `NONE`); `completeness_status` (COMPLETE / MISSING_EVIDENCE / NOT_APPLICABLE / NOT_COMPARABLE / CLARIFICATION_REQUIRED); `finding_status` (NEGATIVE_VERIFIED / CANDIDATE / CONFIRMED_VIOLATION / SUSPICION); `review_priority`; `expert_id`+время, `expert_reason_code`+комментарий; версии датасета, матрицы, модели; `split` (TRAIN / VALIDATION / HIDDEN_TEST, по object_id). CANDIDATE и SUSPICION положительной меткой не являются. **Без полного доказательства finding не засчитывается** |

## 9. Гипотезы (REQ-SUS)

Четыре метода:

- `LOGICAL_ANALYSIS` — например, больше 10 этажей → нужен лифт;
- `SEMANTIC_DISSONANCE` — например, в ПД «Техническое», в РД «Склад ГСМ»;
- `NORMATIVE_ANALYSIS` — например, высота 2.4 при норме 2.5;
- `ML_PATTERN` — например, расход бетона на 20% ниже среднего.

Структура: `suspicion_id, discovery_method, confidence, description, pd_reference, rd_reference, review_priority, normative_base, finding_status=SUSPICION, inspector_status`.

Дедупликация идёт только внутри одного объекта и сопоставимых редакций. В `CANDIDATE` гипотеза переходит только с источниками и координатами. В число нарушений и в GOLD не попадает.

**Ищем только несоответствия между ПД, РД и ИД.** Проект на соответствие нормам (СП, СНиП) не проверяем: примеры «лифт при > 10 этажах» и «2,4 м против 2,5 м» в ТЗ приведены некорректно. `NORMATIVE_ANALYSIS` — вне объёма.

## 13. Приёмка качества (§14 ТЗ)

| Контур | Метрика | Порог |
|---|---|---|
| OCR | Character Accuracy = 1 − ΣLevenshtein/Σсимволов; отдельно CER, WER, coverage | ≥ 0.95 |
| Ключевые поля | Exact Match | ≥ 0.90 |
| Связка документов | Доля evidence_group с верными object_id, стадией, шифром и актуальной редакцией | ≥ 0.95 |
| Локализация | Совпадают file_id и страница, **IoU ≥ 0.5** | ≥ 0.95 групп |
| Нарушения | Precision / Recall / F1 по evidence_group (параметр и доказательство должны быть верными) | **P ≥ 0.90, R ≥ 0.80, F1 ≥ 0.85** |
| Ложные срабатывания | FPR на NEGATIVE_VERIFIED и на устаревших редакциях | ≤ 0.10 |

Метрики считаются по объектам, разделам и типам нарушений. Вместе с ними публикуются размер выборки, coverage/abstention и 95% доверительный интервал. **Провал любого порога = система не принята.**

Пилотная разметка: 9 объектов, в ней 1 подтверждённое нарушение, N кандидатов и 1 отрицательная группа. Этого хватает для формата, но не для количественной оценки.
