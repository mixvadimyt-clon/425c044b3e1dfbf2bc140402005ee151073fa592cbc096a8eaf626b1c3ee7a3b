# Развёртывание «Продукта» в Docker (сдача и стенд)

> Решения: [ADR-0005](../adr/0005-local-first.md) — разработка без Docker; [ADR-0007](../adr/0007-stand-cpu-precomputed-cache.md) — стенд без GPU, образ ML в вариантах CPU и GPU.

Разработка идёт локально без Docker (`./scripts/start-local.sh`). Docker нужен для сдачи и стенда. Образы собирает CI: `.github/workflows/images.yml` проверяет сборку и сквозной сценарий на каждом PR.

## Что внутри

`docker-compose.app.yml` — всё приложение, без обязательной инфраструктуры:

| Сервис | Образ | Что делает |
|---|---|---|
| `web` | `infra/docker/web.Dockerfile` | Веб-клиент и Caddy: статика, `/api/*` в api, HTTPS (Let's Encrypt). Единственный открытый наружу порт (80/443) |
| `api` | `services/api/Dockerfile` | REST API, SQLite и файлы в томе `data`, оркестрация ML, экспорт, обмен с внешней ИС |
| `ml` | `infra/docker/ml.Dockerfile` (CPU) или `ml-gpu.Dockerfile` (GPU) | Разбор PDF, OCR (веса PaddleOCR внутри образа), движок сравнения. Общий с api том `data`: файлы `raw/{sha256}` и кеш разбора `parsed/` |
| `rin-mock` | `services/rin-mock/Dockerfile` | Мок внешней ИС надзора (ИАИС «РиН»): пакеты документов и приём результатов |
| `prometheus`, `grafana` | профиль `monitoring` | Метрики api и ml (REQ-MON). Grafana — только на `127.0.0.1:3001` |

**Тома:**
- `data` — `inspector.sqlite`, `storage/` (файлы и разбор), `backup/`;
- `rin` — пакеты и принятые результаты мока;
- `caddy-data` — сертификаты.

> Обкатка на своей машине с настоящим комплектом ПД + РД + ИД — [local-demo-run.md](local-demo-run.md).

## Запуск одной командой

Требования: Docker 24+ с Compose v2. На процессоре: 2 vCPU, 8 ГБ RAM, от 20 ГБ диска. С видеокартой: плюс NVIDIA
Container Toolkit на хосте (драйвер в образ не кладём) и от 40 ГБ диска: GPU-образ ML весит около 22 ГБ
(сборка на RTX 3050 29.09, около 17 минут).

```bash
git clone https://github.com/mixvadimyt-clon/425c044b3e1dfbf2bc140402005ee151073fa592cbc096a8eaf626b1c3ee7a3b.git inspector
cd inspector
./start.sh
```

`start.sh` создаёт `.env.stand` со свежими секретами (`infra/stand/make-env.sh`), выбирает вариант
образа ML по наличию видеокарты, собирает образы, поднимает web, api, ml и мок «РиН», ждёт
готовности всех healthcheck и проверяет, что интерфейс отдаётся и вход работает. В конце печатает
адрес и пароль демо-пользователей. Первая сборка — 10–25 минут (в образ ML кладутся веса
распознавания, чтобы в работе не требовался интернет), дальше запуск за секунды.

| Команда | Что делает |
|---|---|
| `./start.sh` | поднять и проверить |
| `./start.sh --gpu` / `--cpu` | решить за скрипт, какой вариант образа ML брать |
| `./start.sh --port 8080` | если 80-й порт занят |
| `./start.sh --domain stand.example.ru` | HTTPS: Caddy сам получит сертификат Let's Encrypt (нужны порты 80 и 443) |
| `./start.sh --no-build` | не пересобирать образы |
| `./start.sh check` \| `logs` \| `stop` | проверка, логи api и ml, остановка с сохранением данных |

Логины: `inspector`, `supervisor`, `admin`, `ml`; пароль общий, печатается при первом запуске
и лежит в `.env.stand` (права 600, в git не попадает). Пароль фиксируется при **первом** запуске
на пустой базе: чтобы сменить его, нужен новый том данных.

**До 22.09 эту же команду выполнял CI** на каждый PR по сборке. Сейчас проверки Actions отключены
(минуты исчерпаны до конца месяца), поэтому сборку образов проверяем этой командой вручную —
на любой машине с Docker. Остальные проверки повторяет `./scripts/check-local.sh`.

**Без скрипта** — то же самое руками:

```bash
cp infra/stand/stand.env.example .env.stand   # задайте JWT_SECRET, INTERNAL_TOKEN, DEMO_PASSWORD (openssl rand -hex 32)
docker compose -f docker-compose.app.yml --env-file .env.stand up -d --build
docker compose -f docker-compose.app.yml -f docker-compose.gpu.yml --env-file .env.stand up -d --build   # на видеокарте
./scripts/stand-smoke.sh http://localhost inspector "<DEMO_PASSWORD>" пд.pdf рд.pdf   # сквозной сценарий целиком
```

`./start.sh` берёт GPU-вариант, только если карта **годится**: архитектура 6.1 и новее. В колесе
`paddlepaddle-gpu` собраны `[61, 70, 75, 80, 86, 89, 90]`, Maxwell (5.x) туда не входит — на такой
карте распознавание не пойдёт, и скрипт молча уходит на процессор, сказав почему.

На GPU устройство выбирается само (`OCR_DEVICE=auto`), бюджет страниц OCR снят, потребление
видеопамяти ограничено 20 ГБ (`GPU_MEMORY_LIMIT_MB`): организаторы допускают проверку нескольких
команд на одной карте. GPU-образ собирается в CI автоматически, когда меняются его файлы или
зависимости ML.

**Нормативы распознавания (REQ-PERF) выполняются только на видеокарте, и на слабой — на пределе.** Замеры
([upload-to-result.md](upload-to-result.md)): 500 страниц на RTX 3050 — 9 мин 19 с 24.09 и 595–617 с
(в среднем 604 с) в шести прогонах 26.09, то есть в 4 из 6 чуть больше цели 10 минут; в GPU-образе для сдачи 27.09: 513 с. Проверяющий стенд с
H100 этим не ограничен; на RTX 3050 запаса нет. На процессоре распознавание — около минуты на страницу, поэтому
в варианте `cpu` бюджет `OCR_MAX_PAGES=30` на документ, и сканы сверх него остаются без текста.

|---|---|---|
| `SITE_ADDRESS` | `:80` | Адрес сайта. Доменное имя включает HTTPS |
| `JWT_SECRET`, `INTERNAL_TOKEN` | — (обязательно) | Подпись токенов; общий секрет api ⇄ ml |
| `AUDIT_FILE` | `/data/audit.jsonl` | Копия журнала действий строками JSON рядом с данными; в базе журнал есть всегда |
| `AUDIT_WEBHOOK_URL` | — | Куда дублировать записи журнала (POST с телом записи). **Выключено по умолчанию:** закрытый контур, 152-ФЗ |
| `AUDIT_TELEGRAM_TOKEN`, `AUDIT_TELEGRAM_CHAT` | — | Отправка записей в Telegram-бот: время МСК, логин, действие и итог, адрес и браузер. Тоже выключено по умолчанию |
| `OPEN_ACCESS` | `false` | Вход без пароля под любой активной учётной записью: на странице входа — кнопки ролей (инспектор, руководитель, администратор, ML-инженер). Роли и журнал действий остаются, вход по паролю тоже работает. **Только на время экспертизы** — организаторы попросили открыть стенд (29.09); на стенде включён до конца экспертизы |
| `AUDIT_TELEGRAM_IP` | `149.154.167.220` | За каким адресом закрепить `api.telegram.org` в контейнере api: из Yandex Cloud часть адресов Telegram не отвечает |
| `DEMO_PASSWORD` | — | Пароль демо-пользователей. Без него логин = пароль, поэтому **в образе (`NODE_ENV=production`) api с пустым значением не стартует** и пишет, что делать. Локальная разработка через `npm run dev` работает как раньше |
| `OCR_DEVICE` | `cpu` | `cpu`, `gpu` или `auto` |
| `ML_EXTRAS` | `ocr embeddings` | С чем собирается образ ML. `embeddings` — Sentence-BERT: torch для процессора и веса MiniLM внутри образа, около +1,45 ГБ; в работе сеть не нужна (`HF_HUB_OFFLINE=1`). Образ без него — `ocr` |
| `SBERT_ENABLED`, `SBERT_MAX_LABELS`, `SBERT_BUDGET_S` | `false`, `30000`, `1800` | Sentence-BERT — запасной путь извлечения числовых параметров, где правила молчат. Спрашивается, только если правила молчат во всей стадии; основной лимит — число подписей на задачу (детерминированный), бюджет по часам — аварийный. Каждый процесс ML с ним держит около 1 ГБ памяти: на ВМ с 8 ГБ — вместе с `ML_WORKERS=1`. На стенде выключен: 29.09 на «Алтуфьевское, 79Б» (76 документов) проверка шла 447 с вместо 266 с, память ML 2,3 ГБ вместо 1,3 ГБ, найдено 2 значения, новых кандидатов нет |
| `OCR_MAX_PAGES` | `30` | Бюджет OCR на документ на CPU (около минуты на страницу). `0` — без ограничения |
| `ML_WORKERS` | `2` | Параллельные задачи разбора |
| `ML_API_LOGIN`, `ML_API_PASSWORD` | `ml`, `DEMO_PASSWORD` | Учётка ML-инженера для `inspector-ml train`: выгрузка GOLD-набора и регистрация модели. Применяет модель сам api: в запросе сравнения идёт текущая одобренная (`versions.model_version`), нет одобренной — работают только правила |
| `ML_JOB_TIMEOUT_S` | `1800`, на стенде без видеокарты `5400` (`setup.sh`) | Сколько api и ML ждут одну задачу. Разбор, снятый ML по таймауту, не повторяется: файл в ошибке, проверка идёт дальше. До 27.09 в контейнер ML переменная не передавалась, и он сдавался через 600 с |
| `ML_PROBE_GRACE_S` | `30` | Через сколько секунд после отправки api начинает сверять задачу с ML: задачи, которые ML потерял при перезапуске, уходят заново сразу, а не по дедлайну |
| `ML_CPUS` | половина ядер в варианте cpu через `./start.sh`, иначе `0` | Потолок процессора для контейнера ml, ядер. PaddleOCR на процессоре берёт все ядра на каждого воркера — без потолка скан на 4-ядерной машине держит 400 % и api с интерфейсом встают. `0` — без потолка |
| `LOGIN_MAX_FAILURES`, `LOGIN_MAX_FAILURES_PER_IP`, `LOGIN_WINDOW_S` | `5`, `20`, `900` | Ограничение неудачных входов: на пару «логин + адрес» и на адрес за окно в секундах. Упёрся — 429 с `Retry-After`; учётная запись целиком не блокируется |
| `COMPOSE_PROFILES` | — | `mlops` — MLflow по `/mlflow/` (~350 МБ); `./start.sh --mlflow` допишет сам. С мониторингом — `monitoring,mlops` |
| `MLFLOW_URL` | `http://mlflow:5000/mlflow` | Куда api пишет прогоны ML-контура. MLflow не запущен — api работает как обычно |
| `TRUST_PROXY` | `1` | Сколько прокси перед api доверять (`X-Forwarded-For`). В образе api стоит за Caddy — 1; без этого все клиенты для api — один адрес |
| `MATRIX_ACTIVE_PARAMS` | `all` | Активные параметры при первом запуске: `all` — все 132, или список кодов. На работающей базе — `matrix-import.js --activate all --apply` |
| `IMPORT_DIR` | `./dataset` | Папка с комплектами на ВМ: серверный импорт и пакеты мока (только чтение) |
| `RIN_URL` | `http://rin-mock:4020` | Внешняя ИС. Пусто — обмен выключен |
| `RIN_TOKEN`, `RIN_SECRET`, `RIN_SYSTEM_NAME`, `RIN_POLL_INTERVAL_S` | dev-значения | Мок и коннектор, [services/rin-mock](../../services/rin-mock/README.md) |
| `RIN_MAX_FILE_MB`, `RIN_MAX_PACKAGE_MB` | `1024`, `4096` | Пределы файла и пакета из внешней ИС: больше — пакет не принимается, причина в статусе обмена; реестр пакета — до 10 МБ |

### Если сборка образа ML падает на загрузке весов

PaddleOCR выбирает источник весов сам — HEAD-запрос к HuggingFace, AIStudio, ModelScope и BOS
с таймаутом в одну секунду, кто ответил первым. Поэтому в обоих образах
`PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True` и `PADDLE_PDX_MODEL_SOURCE=huggingface` стоят
в `ENV` **до** шага прогрева весов. Не переносите их вниз: сборка станет зависеть от того,
какой CDN сегодня быстрее отвечает с вашей машины.

Если источник весов недоступен вовсе, собирайте без прогрева и подмонтируйте веса томом —
все нужные модели весят около 20 МБ:

```bash
docker compose -f docker-compose.app.yml --env-file .env.stand build --build-arg OCR_WARMUP=0 ml
# в docker-compose.app.yml у сервиса ml: - ./models/paddlex:/opt/paddlex
```

## Данные на стенде

- **Кеш разбора с GPU** (ADR-0007): файлы из предрасчёта отвечают сразу, без OCR. Загрузка архива:

  ```bash
  docker compose -f docker-compose.app.yml cp cache.tar.gz ml:/tmp/
  docker compose -f docker-compose.app.yml exec ml inspector-ml cache import /tmp/cache.tar.gz
  docker compose -f docker-compose.app.yml exec ml inspector-ml cache stats     # что приехало
  ```
- **Демо-объекты**:
  - комплект положите в `IMPORT_DIR` на ВМ;
  - загрузите его из интерфейса (серверный импорт) или командой `./start.sh import <папка> "<имя объекта>"` — путь относительно `IMPORT_DIR`, лимиты интерфейса (50/200 МБ) не действуют;
  - под капотом это `POST /api/v1/documents/import`. Вызывать его руками через `curl -d` из Git Bash нельзя: кириллица в аргументе уходит не в UTF-8, и api отвечает `FST_ERR_CTP_INVALID_CONTENT_LENGTH`. Нужен curl — тело в файл и `--data-binary @файл`;
  - реестр файлов — в корне папки комплекта;
  - через интерфейс комплект можно загрузить и целиком — архивом .zip до 200 МБ или папкой
    (кнопка папки в интерфейсе): стадия берётся по папкам, реестр из корня находится сам.
- **Пакет для автозабора из «РиН»:**

  ```bash
  docker compose -f docker-compose.app.yml exec rin-mock \
    node src/make-package.mjs "/import/<папка>" --object-id ALT79B --name "ЖК «Алтуфьевское ш., 79Б»" --out /data/packages
  ```
- **Резервная копия базы** — без остановки: `./scripts/stand-backup.sh`. Хранятся последние 3 копии в `data/backup/`. На стенде запускается таймером `inspector-backup.timer` каждую ночь в 03:15 (ставит `setup.sh`); без systemd подойдёт cron: `15 3 * * * cd /opt/inspector && ./scripts/stand-backup.sh`. **RPO по факту — сутки**, а не 15 минут из ТЗ: для стенда соревнования этого достаточно; нужно чаще — тот же скрипт по cron раз в 15 минут, он копирует без остановки.
- **Обновление матрицы без потери данных** — `./start.sh` делает это сам при каждом запуске (сверка с `data/matrix/params.csv`, 26.09): в базу матрица из файла попадает только пустую, и без сверки стенд считал бы по старым шаблонам. Вручную — `matrix:import` в контейнере api. `db:reset` во время экспертизы недопустим: он пересоздаёт базу. Сначала план, потом `--apply`:
  ```bash
  docker compose -f docker-compose.app.yml --env-file .env.stand exec api     node --disable-warning=ExperimentalWarning dist/cli/matrix-import.js
  docker compose -f docker-compose.app.yml --env-file .env.stand exec api     node --disable-warning=ExperimentalWarning dist/cli/matrix-import.js --activate M-010 --apply
  ```
  Активность сама не меняется, новые параметры приходят выключенными, версия матрицы создаётся при реальных изменениях. Перезапуск api не нужен. Подробности — [docs/domain/matrix.md](../domain/matrix.md#как-обновить-матрицу-в-работающей-базе).
- **Очистка кеша растров** — `./scripts/stand-cache-clean.sh`, таймер `inspector-cache-clean.timer` по воскресеньям в 04:30, сразу после ночной копии. Растры страниц копятся, пока эксперты листают чертежи (около 500 КБ на лист), а предела объёма у кеша нет: таймер и есть предел. Удалять их безопасно — лист отрисуется заново примерно за 0.15 с. Кеш **разбора** (`parsed/`) команда не трогает: его восстановление стоило бы часов OCR.

## Проверка и обслуживание

```bash
./start.sh check                                                                   # адрес отвечает, интерфейс отдаётся, вход работает
./start.sh logs                                                                    # логи api и ml
./scripts/stand-logins.sh [--follow | --all]                                       # кто заходил: логин, адрес, браузер (с Mac — yc-stand.sh logins)
./scripts/stand-smoke.sh https://<стенд> inspector "<DEMO_PASSWORD>" pd.pdf rd.pdf  # сквозной сценарий: загрузка и протокол
docker compose -f docker-compose.app.yml --env-file .env.stand ps                  # состояние и healthcheck
git pull && ./start.sh                                                             # обновление, данные в томах сохраняются
```

`stand-smoke.sh` нужен `python3` (разбор JSON ответа); `./start.sh check` обходится одним `curl`.

**Работа без интернета** — проверяется одной командой на уже собранных
образах, рабочий стенд она не трогает (отдельный проект compose, свои тома, после прогона всё удаляется):

```bash
./scripts/stand-offline-check.sh     # KEEP=1 — оставить контур для разбора, OUT=папка — куда положить протокол
```

Скрипт поднимает api, ml и мок «РиН» во внутренней сети Docker ([infra/stand/offline.yml](../../infra/stand/offline.yml)),
убеждается изнутри контейнера, что наружу не выйти (HuggingFace, CDN весов PaddleOCR, голый IP), прогоняет
контрольный комплект, где один акт ИД подан сканом, и требует протокол `FULL` с тремя кандидатами, распознанный
скан (`quality.pages_ocr > 0`) и логи ml и api без попыток выйти в сеть. Веб (Caddy) не поднимается: он занял бы
порт стенда, а наружу ходит только за сертификатом, когда в `SITE_ADDRESS` задан домен.

Прогон 23.09 на рабочей станции (4 ядра, вариант cpu, `ML_CPUS=2`): изоляция подтверждена, протокол за 84 с,
скан распознан на весах из образа, обращений наружу нет. Выгрузки этого прогона — [docs/examples](../examples/README.md).

**Мониторинг:**
1. Запустите `docker compose -f docker-compose.app.yml --env-file .env.stand --profile monitoring up -d`.
2. Откройте Grafana через SSH-туннель: `ssh -L 3001:127.0.0.1:3001 <ВМ>` → `http://localhost:3001`.

## Стенд в Yandex Cloud (ADR-0007)

Стенд должен работать всю экспертизу (30.09–14.10) и на презентации 23.10. Решение по железу —
[ADR-0007](../adr/0007-stand-cpu-precomputed-cache.md): одна ВМ без GPU, тяжёлый разбор
посчитан заранее и перенесён кешем.

### 1. Создать ВМ

Параметры ВМ, статический адрес и группа безопасности собраны в `infra/stand/yc-stand.sh`.
Сначала проверка облака и план — оба ничего не меняют:

```bash
./infra/stand/yc-stand.sh preflight   # профиль, сеть и подсеть, образ Ubuntu, ключ SSH, свободные имена
./infra/stand/yc-stand.sh plan
```

Команды под обычный профиль `yc`, флаги сверены со справкой `yc` 1.37; на живом облаке они ещё не
выполнялись, поэтому прочитайте план глазами. Создание — отдельным шагом и только явно (повторный
запуск пропускает уже созданное):

```bash
APPLY=1 ./infra/stand/yc-stand.sh create
```

> **Доступ к облаку.** Профиль `yc` настраивает администратор командой `yc init` на той машине, где идёт
> развёртывание; скрипты пользуются уже настроенным профилем. Ключи и токены по переписке не
> передаём. Секреты самого стенда генерирует `setup.sh` на ВМ — см. следующий шаг.

Получится: Ubuntu 24.04 LTS, 2 vCPU (100 %), 8 ГБ RAM, 50 ГБ сетевого SSD, статический публичный
адрес, в группе безопасности открыты только 22, 80 и 443.

### 2. Настроить ВМ

```bash
./infra/stand/yc-stand.sh bootstrap                                   # код в /opt/inspector
./infra/stand/yc-stand.sh ssh sudo /opt/inspector/infra/stand/setup.sh
```

Репозиторий приватный, поэтому ВМ читает его своим **deploy-ключом** (только чтение): первый
`bootstrap` создаёт ключ на ВМ и печатает команду `gh repo deploy-key add …`, после неё повторный
`bootstrap` клонирует `main`. Токенов GitHub на ВМ нет.

Сборка на ВМ не проходит (из облака не видно Docker Hub, PyPI или HuggingFace) — готовые образы
архивом: `sudo STAND_IMAGES=<архив ./scripts/images.sh save --cpu> /opt/inspector/infra/stand/setup.sh`.

`setup.sh` идемпотентен и делает всё остальное: ставит Docker, создаёт `.env.stand` со свежими
секретами, поднимает приложение, включает таймеры (сторож, ночная копия базы, недельная очистка
кеша растров), прогоняет
`stand-smoke.sh`. Пароль демо-пользователей он генерирует сам и печатает **один раз** — потом его
можно прочитать только из `.env.stand` на ВМ.

Адрес сайта берётся по внешнему IP через sslip.io (`51-250-10-20.sslip.io`), Caddy выпускает на него
сертификат Let's Encrypt. Свой домен — `STAND_DOMAIN=stand.example.ru sudo -E ./infra/stand/setup.sh`.

Секретов нет ни в git, ни в облачных метаданных: они рождаются на самой ВМ.

### 3. Сторож доступности

`inspector-watchdog.timer` раз в 5 минут дёргает `/health` и после трёх неудач подряд перезапускает
контейнеры: `api` и `ml`, если ответ пришёл, но статус не `ok`, и всё вместе, если ответа нет вовсе.
Упавшие контейнеры compose поднимает и сам (`restart: unless-stopped`) — сторож нужен для случая,
когда процесс жив, а сервис не отвечает.

```bash
systemctl status inspector-watchdog.timer
journalctl -u inspector-watchdog.service -n 50
```

Порог и адрес меняются переменными `WATCHDOG_LIMIT` и `STAND_URL` в юните.

Все три таймера зовут скрипты из `scripts/`, а те подхватывают `.env.stand` через `--env-file`:
в `docker-compose.app.yml` секреты объявлены как `${VAR:?…}`, и без файла compose обрывается на
**любой** команде, включая `ps` и `exec`. В CI тех же переменных хватает из окружения, файла там нет.
