# 0007. Стенд без GPU: тяжёлый разбор считаем заранее, образ ML — в двух вариантах
- Статус: принято, дополнено 2026-09-21 и 2026-09-22
- Дата: 2026-09-19
- Автор: Команда

## Контекст

**Что сдаём.** Dockerfile и образы, зависимости, открытые веса, README развёртывания и публичный стенд. Стенд должен работать всю экспертизу (30.09–14.10) и на презентации 23.10.

**Ресурсы.** Стенд — в Yandex Cloud: доступа к GPU нет, только обычные ВМ.

**Производительность OCR:** на CPU 58–89 с на страницу, на RTX 3050 — 1,2–3 с. В скрытой части датасета 8 864 страницы без текстового слоя: около недели на CPU против примерно 3 часов на GPU.

## Решение

1. **Стенд — одна ВМ без GPU.** 2 vCPU (100 %), 8 ГБ RAM, 50 ГБ сетевого SSD, статический IP, Ubuntu LTS, Docker Compose: api, web за HTTPS, ml в режиме CPU, rin-mock. ВМ работает непрерывно до 23.10.
2. **Тяжёлый разбор считаем заранее на GPU.** Разбор с OCR кешируется по sha256 файла и `PARSER_VERSION` (`parsed/{sha256}/{version}.json`, REQ-PRS-07). Так же должны кешироваться и другие дорогие шаги ML, если появятся.
   - `PARSER_VERSION` замораживается (см. дополнение 2026-09-22).
   - Предрасчёт проходит по всем PDF датасета, открытой и скрытой части. Закрытые материалы организатора не трогаем.
   - Архив кеша переносится на стенд.

   Те же файлы на стенде отвечают из кеша сразу. Новые файлы разбираются на CPU с бюджетом OCR: только страницы без текстового слоя и нужные активным параметрам, лимит `OCR_MAX_PAGES`.
3. **Честность.** Кеш хранит тот же результат, который посчитал бы сам стенд, — это кеш по содержимому, а не заготовленные ответы. README описывает кеш и как его пересобрать. `force_reparse` считает заново.
4. **Образ ML — два варианта.**
   - CPU — для стенда и ноутбука.
   - GPU — CUDA и `paddlepaddle-gpu`, для проверяющего стенда (H100 80 ГБ); устройство выбирается само (`OCR_DEVICE=auto`).

   Веса OCR (`PP-OCRv5_mobile_det`, `eslav_PP-OCRv5_mobile_rec`) лежат внутри образа, работа без интернета. LLM по умолчанию выключена, веса — отдельным скриптом загрузки (ADR-0006).
5. **Сборка и данные.**
   - Образы собираются на ВМ стенда из `main` и в CI (проверка Dockerfile, без публикации). Платный реестр не нужен.
   - Данные лежат в volume на диске ВМ.
   - Один снимок диска после настройки плюс ночная копия базы SQLite.
6. **Не используем.**
   - Прерываемые ВМ — останавливаются минимум раз в сутки, стенд должен быть доступен.
   - GPU в облаке — доступа нет.

## Последствия

- Кеш разбора выгружается и загружается командами `inspector-ml cache export / import`; предрасчёт идёт на GPU, в образе — GPU-вариант зависимостей и веса OCR.
- Образы CPU и GPU, compose приложения, README сдачи и сборка в CI; стенд — с HTTPS, демо-данными и паролями демо-пользователей не по умолчанию.
- Если разбор меняется после заморозки (новая `PARSER_VERSION`), предрасчёт повторяем: 3–4 часа GPU.
- Если на стенд загрузят изменённые файлы (другой sha256), разбор пойдёт на CPU медленно. Время ограничивает бюджет OCR.
- Стенд работает на CPU, тяжёлый разбор посчитан заранее и лежит в кеше по содержимому; на GPU тот же конвейер идёт примерно в 50 раз быстрее.
- Уточняет [ADR-0005](0005-local-first.md): разработка по-прежнему локальная без Docker, облачная ВМ — только для стенда.

## Дополнение 2026-09-21: проверяющий стенд — с GPU, наш — по-прежнему без

Проверка идёт на **одном NVIDIA H100 80 ГБ, 24 ядра / 48 потоков, до 640 ГБ RAM, от 300 ГБ диска**,
GPU передаётся в контейнер через NVIDIA Container Toolkit.

**Что это меняет.**

1. **GPU-вариант образа перестал быть запасным.** Нормативы производительности проверяются именно
   в GPU-конфигурации. Его сборка проверяется в CI.
2. **Предрасчёт кеша остаётся, но у него другая роль.** На проверяющем стенде OCR идёт на H100, и кеш
   не нужен. Кеш обслуживает **наш публичный стенд** (2 vCPU) и обязан оставаться необязательным:
   образ без кеша должен работать, просто медленнее.
3. **Потолок OCR зависит от устройства.** На CPU `OCR_MAX_PAGES=30` спасает от многочасового
   разбора скана. На GPU потолок только портит качество: страница распознаётся около секунды.
   В `docker-compose.gpu.yml` он `0` — это часть конфигурации проверки.
4. **Видеопамять придётся делить.** Карту могут одновременно использовать несколько контуров.
   Значит «занять всё, что есть» — не нейтральное поведение: нужен явный предел потребления VRAM
   у PaddleOCR и у LLM, если она включена.
5. **Свой публичный API подключать нельзя.** Образ обязан быть самодостаточным: мок «РиН»
   поднимается в том же compose, модели лежат внутри образа, интернет в работе не нужен.

## Дополнение 2026-09-22: заморозка разбора

Предрасчёт корпуса идёт 6–7 часов на видеокарте. Поздняя заморозка дала бы готовый кеш уже после
сдачи, и публичный стенд на 2 vCPU распознавал бы сканы по минуте на страницу. Поэтому `PARSER_VERSION`
заморожен 22.09 (`0.3.0`: таблицы пересобираются после OCR), предрасчёт — в ночь, архив — на стенд.

После заморозки правки, меняющие выход разбора, не принимаем — кроме тех, что чинят поломку.
Docling остаётся за заморозкой.

Такая поломка нашлась: 515 страниц с нечитаемым текстовым слоем выглядели исправными и молча
разбирались в мусор. `PARSER_VERSION` поднят до `0.4.0`, предрасчёт повторён.

**Правило, которое из этого следует:** архив предыдущей версии не удаляется, пока новый не собран
и не проверен `cache verify`. Пока обе версии есть, откат стоит одну команду; без старого архива
неудачный ночной прогон оставил бы стенд вообще без кеша.
