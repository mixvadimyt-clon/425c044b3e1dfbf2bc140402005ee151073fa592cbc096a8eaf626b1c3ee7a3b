# 0005. Локальный запуск без Docker, стек ТЗ — через адаптеры
- Статус: принято
- Дата: 2026-09-17
- Автор: Команда

## Контекст
Проверяющим важно увидеть работающий сценарий: загрузить PDF и получить анализ. Контейнеризация и облачная ВМ требуют времени на поддержку и не добавляют ценности демо. У разработчиков разные машины.

## Решение
- По умолчанию всё запускается локально, одной командой (`scripts/start-local.sh`), без Docker.
- api: SQLite через встроенный `node:sqlite` (без нативных модулей и сервера БД), файлы в `var/storage`, пароли — `crypto.scrypt`.
- api ⇄ ml: HTTP-задачи (`POST /v1/jobs` + callback). Сообщения — те же Envelope, что для RabbitMQ.
- ml: кеш парсинга по sha256 в `var/cache` (Redis — опциональный адаптер).
- ML-заглушка внутри api (`ML_TRANSPORT=stub`) — фронтенд и демо работают без Python.
- `docker-compose.yml` остаётся как опциональный «полный контур» из ТЗ (PostgreSQL, Redis, RabbitMQ, MinIO, ClamAV, мониторинг) и не является обязательным.
- Облачную ВМ пока не используем.

## Дополнение 2026-09-17: сдача в образах
- HTTP вместо RabbitMQ по умолчанию — допустимый аналог стека.
- Для **сдачи** нужны Dockerfile или образы, зависимости, открытые веса и **публичная ссылка на стенд**. Поэтому:
  - разработка остаётся локальной без Docker;
  - к финалу собираем образы `api`, `ml`, `web` — та же локальная конфигурация (SQLite, файлы в volume), без обязательной тяжёлой инфраструктуры;
  - стенд — ВМ в Yandex Cloud: размер и предрасчёт кеша — [ADR-0007](0007-stand-cpu-precomputed-cache.md).

## Последствия
- Требования ТЗ к RabbitMQ/Redis закрываются адаптерами и конфигурацией, а не обязательной инфраструктурой.
- SQL пишем переносимым, чтобы при необходимости перейти на PostgreSQL.
- `node:sqlite` помечен в Node 22 как experimental: предупреждение подавляется, API стабилен для наших задач; минимальная версия Node — 22.13.
