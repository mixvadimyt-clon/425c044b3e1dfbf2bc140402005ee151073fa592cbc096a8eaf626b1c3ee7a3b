# Протокол проверки и карточка доказательства

> ⚠️ Обязательная форма протокола задана **Приложением № 2** ТЗ, которого у нас пока нет. Ниже — структура по REQ-CMP-08 и REQ-CMP-09. Когда получим образец, приведём к нему экспорт.
> JSON-схема: `Protocol` в `contracts/openapi/inspector-api.v1.yaml`.

## Структура

```
Протокол проверки № <process_id>, версия <n>
├─ Шапка
│   объект (наименование, адрес, застройщик, подрядчик, № разрешения)
│   инспектор, даты создания/финализации
│   matrix_version · model_version · dataset_version · input_manifest_hash
├─ Статус загрузки документов      → PD_* / RD_* / ID_*
├─ Тип проверки                    → FULL / PD_RD_ONLY / …
├─ Реестр входных файлов           → имя, стадия, шифр, редакция, статус утверждения, SHA-256
├─ Сводка                          → счётчики по статусам
├─ (1) Комплектность и сопоставимость
│       MISSING_EVIDENCE · NOT_APPLICABLE · NOT_COMPARABLE · CLARIFICATION_REQUIRED
├─ (2) Предварительные кандидаты   → CANDIDATE (+ статус решения инспектора)
├─ (3) Подтверждённые нарушения    → CONFIRMED_VIOLATION
├─ (4) Проверенные отрицательные   → NEGATIVE_VERIFIED
└─ (5) Гипотезы свободного поиска  → SUSPICION
```

MISSING_EVIDENCE дополнительно выводится **отдельным перечнем** (REQ-VER-07): что нужно запросить или дозагрузить.

## Карточка доказательства (REQ-CMP-09)

| Поле | Откуда |
|---|---|
| `finding_id` | `checks.id` |
| Код параметра или правила | `param_code` (+ `rule_key`) |
| expected / actual (+ delta, единица) | compare-движок |
| Для **каждого** источника: `file_id`, SHA-256, стадия, шифр, редакция, статус утверждения, лист и страница, bbox/polygon | `evidence_fragments` |
| Обоснование | `rationale` + нормативная ссылка |
| Уровень риска | `risk_level` (только очерёдность!) |
| Решение инспектора и причина | `decision.action`, `reason_code`, `comment`, кто и когда |
| Ссылка на согласованное изменение | `approved_change_ref` |

## Правки инспектора

- **Редакция.** Инспектор выбирает авторитетную редакцию и связь с предшественником, основание обязательно (`PATCH /files/{id}`). Остальные метаданные он **не правит**.
- **Доказательства.** Добавить, исправить или удалить фрагмент можно через `POST /findings/{id}/evidence`. Создаётся **новая версия** группы с автором, временем, причиной и ссылкой. Машинная версия сохраняется, история лежит в `Finding.evidence_history`.
- **Перенос решений.** Решения и правки доказательств переносятся в новые версии протокола, если машинные доказательства не изменились.
- **Массовое решение.** `POST /findings/bulk-decision` принимает только CONFIRM или CLARIFY и только для кандидатов одного параметра. Массового отклонения нет.

## Экран верификации (ориентир для FE)

> Одно рабочее окно, карточка и **синхронные панели по стадиям — ПД, РД и ИД отдельно**. Панелей столько, сколько стадий есть в доказательствах. Макет ниже — упрощённый; актуальный — в [services/web.md](../services/web.md).

```
┌──────────────── очередь кандидатов (фильтры: раздел / приоритет / статус) ────────────────┐
│ ▸ M-055 · Плита П-2 · HIGH · ожидает         ▸ M-041 · Дверь Д-3 · HIGH · ожидает ...    │
└───────────────────────────────────────────────────────────────────────────────────────────┘
┌── Карточка ───────────────────┐ ┌── ПД: 25-01-КР, изм.2, утв., л.7 ─┐ ┌── РД: 25-01-КЖ … ──┐
│ Класс прочности бетона        │ │                                   │ │                     │
│ Ожидается: B30 (ПД)           │ │   [PDF-страница с подсветкой      │ │  [PDF с подсветкой] │
│ Фактически: B25 (ИД)          │ │    bbox EXPECTED]                 │ │                     │
│ Обоснование: понижение класса │ │                                   │ │                     │
│ Норматив: …                   │ └───────────────────────────────────┘ └─────────────────────┘
│ [✓ Подтвердить] [✗ Отклонить] [? Уточнить]   (горячие клавиши: 1 / 2 / 3, →: следующий)   │
└───────────────────────────────────────────────────────────────────────────────────────────┘
```

Цель — **не больше 3 осознанных действий от открытия карточки до сохранённого решения** (REQ-VER-10):

- «Подтвердить»: открыть карточку → «Подтвердить» (2 действия).
- «Отклонить»: открыть карточку → «Отклонить» → причина (3 действия). Выбор причины сразу сохраняет решение с шаблонным комментарием; комментарий можно дописать заранее.
- «Уточнить»: 2 действия.

## Экспорт

`GET /api/v1/protocols/{id}/export?format=json|pdf|docx|xml|gold`. Экспорт отражает **текущее** состояние решений инспектора. Прежние версии протокола выгружаются с полнотой комплекта и метаданными файлов на момент своего сравнения (снимок в `protocols.snapshot`). Файлы финализированного протокола сохраняются в `var/storage/protocols/{process_id}/v{n}-{время финализации}.{pdf|docx|xml}` и отдаются повторно без пересборки; после отмены финализации и повторной финализации протокол собирается заново. Каждая выгрузка пишется в аудит (`exportProtocol`: формат, из кеша ли, время).

| Формат | Реализация (`services/api/src/modules/export/`) | Что внутри |
|---|---|---|
| `json` | `Protocol` как есть | машиночитаемый, для РиН и интерфейса |
| `pdf` | `pdf.ts`: pdfmake + DejaVu Sans (кириллица; пакет `dejavu-fonts-ttf`, свободная лицензия), A4 альбомная | печатная форма (ниже); заголовок раздела — строка шапки таблицы, поэтому не отрывается и повторяется на новой странице |
| `docx` | `docx.ts`: библиотека `docx`, та же форма | редактируемая версия для инспектора; колонки заданы в twip (иначе LibreOffice сжимает таблицы) |
| `xml` | `xml.ts` без зависимостей, пространство имён `urn:inspector-ai:protocol:1` | структура JSON плюс полнота комплекта и замечания; символы, запрещённые в XML 1.0, вычищаются |
| `gold` | `gold.ts`, схема `GoldExport` (контракт v0.5) | **выгрузка по листу «СХЕМА GOLD»** Приложения 1 — см. ниже |
| `submission` | `submission.ts`, схема `SubmissionExport` (контракт v0.6) | **ответ участника в формате организаторов** (`submission_schema.json` из датасета) — это и есть выходной JSON для сдачи и оценки. Запись на атомарную проверку: `parameter_code` — внешний код (`KR-055`), `location` — `rule_key`, значения по стадиям, `violation_label` и `protocol_status`, доказательства — стадия, `file_id` из реестра и номер страницы |

**Соответствие статусов в `submission`:** `CANDIDATE` и `CONFIRMED_VIOLATION` → `VIOLATION_PRESENT` (`protocol_status` — `CRITICAL` для приоритета HIGH, иначе `WARNING`); `NEGATIVE_VERIFIED` → `NO_VIOLATION` / `OK`; `MISSING_EVIDENCE` → `MISSING_DOCUMENT` / `<стадия>_MISSING`; `NOT_COMPARABLE` и `CLARIFICATION_REQUIRED` → `COMPARISON_IMPOSSIBLE`; `NOT_APPLICABLE` не выгружается. `criticality` — «Критическое (приостановка работ)» для HIGH и «Существенное (предписание)» для MEDIUM, как в каталоге организаторов. **Гипотезы свободного поиска** выгружаются в тех же `checks[]` с кодом `FREE-<ТЕМА>-<NNN>` (как `FREE-HEATING-001` в эталоне организаторов; решение 2026-09-18): тема — по марке или разделу документа-источника (ОВ / ИОС4 → HEATING, ВК → WATER, КЖ / КР → STRUCT, АР → ARCH…), номер — по порядку внутри темы. Не выгружаются отклонённые инспектором, переведённые в кандидаты (они уже есть как проверки) и гипотезы с уверенностью ниже `SUBMISSION_FREE_MIN_CONFIDENCE` (0,5) — это регулятор precision и recall. `location` у гипотез пустой, `violation_label` — `VIOLATION_PRESENT` (на уточнении — `COMPARISON_IMPOSSIBLE`).

**Печатная форма** (`report.ts`, общая для PDF и DOCX; уточним по Приложению 2): сведения о проверке и версии → статус загрузки, тип проверки, полнота комплекта, реестр → замечания по комплекту (однотипные схлопываются) → реестр входных файлов с `file_id` и SHA-256 → сводка → таблицы 1–5 (источники с шифром, изменением и страницей; решения инспектора с причиной и комментарием) → «Что нужно запросить или дозагрузить» → подпись инспектора. Единицы пишутся только к числам («B30», а не «B30 Марка (B)»).

**Выгрузка GOLD** — запись на атомарный finding (`CANDIDATE`, `CONFIRMED_VIOLATION`, `NEGATIVE_VERIFIED`; кандидат на уточнении остаётся `CANDIDATE` с `completeness_status = CLARIFICATION_REQUIRED`) и на гипотезу (`SUSPICION`, `matrix_code = null`, `rule_version = free-search:<метод>@<модель>`):

- `finding_id` — стабильный `finding_key` (одинаков во всех версиях протокола), `internal_id` — id записи;
- `object_id` — `external_id` объекта, `file_id` источников — `file_id` из реестра (иначе внутренний);
- `source_expected_*` / `source_actual_*` — первый фрагмент роли, полные списки — `source_expected[]` / `source_actual[]`; `bbox_polygon` — polygon или bbox в долях [0;1];
- `approved_change_ref` — из решения инспектора или `NONE`; `expert_*` — кто, когда, код причины, комментарий;
- `split` — только у записей, прошедших курирование (`dataset_items.curation_status = APPROVED`);
- параметры без finding для оценки (`MISSING_EVIDENCE`, `NOT_APPLICABLE`, `NOT_COMPARABLE`) — в `not_evaluated[]`.
