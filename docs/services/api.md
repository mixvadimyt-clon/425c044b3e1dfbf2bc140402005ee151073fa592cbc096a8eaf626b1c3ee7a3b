# Сервис `api` (Node.js)

> Документ обновляется в том же PR, что и код.
> Команды запуска — [services/api/README.md](../../services/api/README.md).

## Назначение

Центральный сервис: REST API по OpenAPI, авторизация, загрузка файлов, реестр, машина состояний, оркестрация ML, протоколы и их версии, верификация, аудит, экспорт, администрирование, GOLD, интеграция с РиН. Только этот сервис пишет в БД.

## Стек

- Node.js **≥ 22.13**, TypeScript, **Fastify 5**;
- `fastify-openapi-glue`: маршруты, валидация запросов и сериализация ответов строятся из `contracts/dist/inspector-api.v1.json`;
- БД — встроенный `node:sqlite`, SQL-миграции в `src/db/migrations/`, без ORM;
- `@fastify/jwt` + `crypto.scrypt`, `@fastify/multipart`, `pdf-lib`, `ajv`;
- `pino` (JSON-логи), `prom-client` (`/metrics`);
- `vitest`.

## Ключевые решения

- **Загрузка.** Поток пишется во временный файл, одновременно считаются sha256 и размер. Дальше: лимиты 50 МБ на файл и 200 МБ на пакет (413 для всего пакета), формат по magic bytes, у PDF — заголовок и `%%EOF` плюс число страниц через pdf-lib, ClamAV (если включён). Файл сохраняется в `raw/{sha256}`, поэтому одинаковое содержимое хранится один раз. Повторная загрузка того же содержимого в проверку — новая запись с `duplicate_of` и предупреждением `DUPLICATE_CONTENT`; в сравнение она не идёт.
- **Реестр файлов** («Перечень ИД» ред. 1.1, [domain/registry.md](../domain/registry.md)): файл `registry` (CSV/XLSX/JSON) или JSON `manifest` при загрузке, `registry_path`/автопоиск при импорте, `POST /processes/{id}/registry` — после загрузки (перезапуск сравнения, `METADATA_CHANGE`). Поля реестра важнее оценки по имени и ML (`metadata_source=MANIFEST`). `file_id`, занятый в объекте другим содержимым, → `FILE_ID_CONFLICT`. Связи редакций — по `predecessor_id`/`successor_id` или `predecessor_file_name`.
- **Полнота** (`completenessOf`): строки реестра и `expected[]` — ожидаемый состав; `X_UPLOADED` только при подтверждении реестром; итоговый `status` — худшее из замечаний (`NO_REGISTRY`, `NOT_IN_REGISTRY`, `SHA256_MISMATCH`, `AMBIGUOUS_REVISION` → `CLARIFICATION_REQUIRED`; нечитаемые → `NOT_COMPARABLE`; нехватка → `MISSING_EVIDENCE`). `PARTIALLY_LOADED` — только при известном пробеле. Подробности — [domain/statuses.md](../domain/statuses.md) §2–3.
- **Исключение из сравнения** (`exclusionOf`): дубликат, `SUPERSEDED`/`CANCELLED`, есть заменяющая редакция, инспектор исключил. Явный выбор инспектора важнее статуса. Заменённые редакции уходят в `CompareRequest.excluded_files`, дубликаты не отправляются совсем.
- **Серверный импорт** (`POST /documents/import`): папка внутри `IMPORT_ROOT` (по умолчанию `dataset/`), без лимитов 50/200 МБ. Имена сегментов пути можно указывать исправленными. Стадия берётся из имени папки комплекта. Защита от выхода за корень — `realpath`. На выборке датасета: 78 файлов за 9,7 с, 2 действительно повреждённых PDF отклонены (19 копий «… 2024.pdf» с v0.4 сохраняются как дубликаты).
- **Правки инспектора**: `PATCH /files/{id}` — только `is_authoritative`, `predecessor_id` и основание (`METADATA_READONLY` на прочие поля). `POST /findings/{id}/evidence` — новая версия `evidence_groups` (`source=INSPECTOR`). При пересчёте сравнение идёт с последней машинной версией (`modelGroupOf`).
- **Массовое решение**: `POST /findings/bulk-decision` — только CONFIRM и CLARIFY, один параметр одного протокола, в одной транзакции.
- **Автозапуск.** `auto_start=true` (по умолчанию): после загрузки сразу стартует анализ — полный для новой проверки, инкрементальный для дозагрузки. Инспектору не нужны лишние клики.
- **Стадия файла.** Реестр → подсказка пользователя (`stage_hints`) → папка комплекта → оценка по имени → ML.
- **Оркестрация.** Состояние хранится в БД (`processes`, `files`, `ml_jobs`), поэтому переживает перезапуск. Ретраи: до `ML_MAX_RETRIES` повторов, затем `FAILED` и уведомление ADMIN. Таймауты проверяются таймером `sweep()`. Результат без активной задачи (устаревший) игнорируется.
- **Сверка задач с ML** (`Orchestrator.reconcile`, каждые `ML_SWEEP_INTERVAL_MS`). Очередь ML живёт в памяти процесса и пропадает при его перезапуске, поэтому api спрашивает ML о каждой задаче старше `ML_PROBE_GRACE_S` (`GET /v1/jobs/{id}` с `x-internal-token`): ML её не знает — задача отправляется заново сразу (`ML_JOB_LOST`, считается попыткой); результат готов, а callback не дошёл — api забирает его сам; задача в очереди или в работе — дедлайн продлевается, второй экземпляр в ML не уходит. ML недоступен — работает обычный дедлайн (`ML_NO_RESPONSE`). Разбор, который ML сам снял по таймауту (`TIMEOUT`), не повторяется: файл сразу `FAILED` с причиной, проверка идёт дальше без него, повторный запуск анализа вернёт его в работу. Проверено вживую 23.09: ML перезапущен посреди разбора — проверка дошла до протокола через 2,5 минуты, раньше висела до дедлайна (30 минут на стенде, на тяжёлом скане — до полутора часов с повторами).
- **Версии протокола.** Каждый `CompareResult` создаёт новую версию. При `INCREMENTAL` нетронутые параметры копируются из прошлой версии. Решение инспектора (и его правки доказательств) переносится, если у finding с тем же `finding_key` совпадает набор `(sha256, page)` доказательств последней машинной версии. Иначе ставится `evidence_changed=true` и решение сбрасывается в `PENDING`.
- **Статусы.** `READY → VERIFYING → COMPLETED` вычисляются по решениям (`syncVerificationStatus`). Финализация возможна, только когда нет `CANDIDATE` в `PENDING`. Отмену финализации может выполнить только ADMIN или SUPERVISOR, причина пишется в аудит.
- **Кандидаты.** Очередь верификации (`finding_status=CANDIDATE`) — это findings, у которых модель поставила `CANDIDATE`, включая уже решённые. Поэтому инспектор видит свой прогресс.
- **Процент соответствия** = NEGATIVE_VERIFIED / (NEGATIVE_VERIFIED + CANDIDATE в ожидании + CONFIRMED_VIOLATION).
- **Аудит.** Хук `onResponse` пишет все изменяющие операции и экспорт: operationId, пользователь, IP, User-Agent, детали из обработчика. Оркестратор пишет в тот же журнал действия системы (`system.analysis_started`, `system.file_parsed`, `system.file_failed`, `system.job_retry`, `system.compare_started`, `system.protocol_created`, `system.process_failed`) — `GET /audit?actor_type=SYSTEM`.
- **Файлы.** Различаются по SHA-256; содержимое лежит в хранилище по ключу `raw/{sha256}` (один экземпляр на любое число загрузок), в БД — ссылка (`storage_key`) и метаданные: стадия, шифр, редакция, статус и дата утверждения, заголовок, кто и когда загрузил.
- **Внутренний callback** `/internal/ml/results` принимается только с localhost или с заголовком `x-internal-token`. Payload валидируется по `contracts/dist/ml-events.v1.json`.
- **Логи** — pino JSON с полями `timestamp, level, service="api", message, request_id`.
- **Экспорт** (`modules/export/`, [domain/protocol.md](../domain/protocol.md#экспорт)): JSON, PDF, DOCX, XML, выгрузка по схеме GOLD и ответ в формате организаторов (`submission`) из одной модели (`report.ts`). Финализированный протокол кешируется в `protocols/{process_id}/v{n}-{время финализации}.*`. На выборке датасета (57 файлов) PDF собирается за 0,2 с.
- **Обмен с внешней ИС** (REQ-INT-01…07; API внешней ИС — `contracts/openapi/rin-external.v1.yaml`, мок — `services/rin-mock`). Включается `RIN_URL`.
  - *Результаты → внешняя ИС.* Финализация ставит в `integration_outbox` снимок `InspectionResult` (подтверждённые нарушения, версии, реестр входных файлов); `POST /inspection/{id}` — повторная отправка. Доставка — `POST {RIN_URL}/api/v1/results` с bearer-токеном, подписью `x-signature` (HMAC-SHA256 тела, мок УКЭП) и ключом идемпотентности `<process_id>:v<версия>`. На 5xx и таймаут — повторы через 1, 5 и 15 минут (`RIN_RETRY_DELAYS_S`, всего 4 попытки), всё это время `sync_status = PENDING_SYNC`; после них или на 4xx — `SYNC_FAILED` и уведомление финализировавшему инспектору. Протокол и решения обмен не меняет (REQ-INT-04). Если финализацию отменили до доставки — отправка останавливается. Состояние — `GET /inspection/{id}/sync`, pull-модель — `GET /inspection/{id}`.
  - *Документы → Инспектор* (REQ-INT-06). Опрос `GET {RIN_URL}/api/v1/packages` раз в `RIN_POLL_INTERVAL_S` или по `POST /integration/pull`. Объект — по `external_id` (нет — создаётся). Файлы скачиваются потоком и сверяются по sha256 пакета, `.zip` распаковывается, реестр пакета применяется, загружает технический пользователь «<система> (автозабор)» (войти под ним нельзя). Нет проверки — новая с автозапуском; есть незавершённая — дозагрузка; идёт обработка — пакет ждёт следующего опроса; протокол финализирован — пакет `DEFERRED` и уведомление `NEW_DOCUMENTS_AVAILABLE`, проверку создаёт инспектор (`POST /integration/packages/{id}/apply`). Обработанные пакеты помнятся по `package_id` (`integration_inbox`).
  - Журнал системы: `system.integration_queued / _delivered / _retry / _failed / _cancelled`, `system.integration_package_applied / _deferred / _failed`. Настройки и очередь — `GET /integration/status`.
- **ML-контур** (REQ-ML-01…07) — воспроизводимый контур дообучения:
  - *GOLD-черновик* — из решений инспектора (CONFIRM → POSITIVE, REJECT → NEGATIVE), куратор одобряет (`POST /ml/dataset-items/{id}/curate`);
  - *версия набора* (`POST /ml/dataset-versions`) — накопительная: прежние записи плюс одобренные новые с полным доказательством (`excluded` — кто не прошёл и почему). Разбиение по объекту: часть фиксируется при первом выпуске, новый объект — по sha256(object_id) и `split_ratio` либо явно по `object_splits` (контракт 0.22.0: когда объектов мало и хеш может оставить VALIDATION пустым; поменять часть уже выпущенного объекта нельзя — `409 SPLIT_FIXED`). Для записи сохраняется снимок GOLD-записи, поэтому выгрузка `GET /ml/dataset-versions/{v}/export` (JSONL, строки — канонический JSON, порядок TRAIN → VALIDATION → HIDDEN_TEST, внутри — по item_id) воспроизводится байт в байт, а `split_hashes` — SHA-256 строк каждой части: обучающий скрипт проверяет их без пересериализации;
  - *реестр моделей* (`POST /ml/models` — отчёт `inspector-ml train`): хеши частей должны совпасть с версией набора (`DATASET_HASH_MISMATCH`), сервер сам считает приёмочные проверки — пороги §14 (P ≥ 0.90, R ≥ 0.80, F1 ≥ 0.85, FPR ≤ 0.10 обязательны; OCR, EM, связка, локализация — если измерены) и регрессию против текущей модели: Recall и FPR в целом и по каждой категории — не больше 2 п.п. Решения (`/decision`): APPROVE — только при прохождении проверок (пересчитываются на момент решения), REJECT, ROLLBACK — текущая модель откатывается на предыдущую или на «только правила». Всё с комментарием и ответственным в `ml_retraining_log`;
  - *недельный отчёт* (`GET /ml/reports/weekly?week=YYYY-Www`, неделя по МСК): решения, отклонения по причинам и разделам, параметры с ложными срабатываниями, рекомендации по причинам (кому и что чинить), очередь куратора и невыпущенные записи.
- **Нереализованных операций контракта нет** (ответ 501 остаётся для будущих).

## MLflow — витрина ML-контура

[`src/modules/mlops/mlflow.ts`](../../services/api/src/modules/mlops/mlflow.ts). Источник истины — api
(версии GOLD-набора, реестр моделей, решения); MLflow получает копию прогонами: выпуск версии набора —
эксперимент `inspector-datasets`, регистрация модели — `inspector-models` с метриками §14 и разрезом по
категориям, решение по модели — метки на её прогоне. Запись «по возможности»: MLflow выключен или не
отвечает — api работает дальше, в логе предупреждение.

Доступ: MLflow за Caddy по `/mlflow/`, своей авторизации у него нет. `POST /admin/mlflow/session` (ADMIN,
ML_ENGINEER) ставит cookie `inspector_mlflow` с токеном, подписанным HMAC на производном от
`JWT_SECRET` ключе; Caddy на каждый запрос спрашивает `GET /internal/auth/mlflow` (`forward_auth`).
Токен сессии не входит в api, JWT входа не открывает MLflow. Сервис — профиль compose `mlops`
(`./start.sh --mlflow`), MLflow 3.16.1, ~350 МБ: фоновые задачи MLflow выключены, телеметрия тоже.
Проверено вживую 24.09: без cookie 401, с cookie интерфейс и API MLflow, прогоны видны.

## Ограничение попыток входа

[`src/auth/throttle.ts`](../../services/api/src/auth/throttle.ts). Неудачные входы
считаются в скользящем окне `LOGIN_WINDOW_S` (15 мин) по двум ключам: пара «логин + адрес» —
`LOGIN_MAX_FAILURES` (5), адрес по всем логинам — `LOGIN_MAX_FAILURES_PER_IP` (20). Упёрся — `429
TOO_MANY_LOGIN_ATTEMPTS` с `Retry-After`, пароль при этом не проверяется. Успешный вход обнуляет пару,
но не адрес.

- **Учётная запись целиком не блокируется.** Демо-учётки общие — `inspector` открывают проверяющие
  и разработчики; блокировка по логину отдала бы постороннему кнопку «запереть проверяющих».
- **Адрес клиента за Caddy** — из `X-Forwarded-For`, доверие ровно `TRUST_PROXY` хопам (в образе 1):
  берётся адрес, дописанный самим Caddy, подставленное клиентом левее не учитывается. При `npm run dev`
  `TRUST_PROXY=0`: api открыт напрямую, и заголовку верить нельзя.
- Счётчики в памяти процесса: api один, сброс при перезапуске перебор не ускоряет.
- Видно в метриках: `http_requests_total{route="/api/v1/auth/login",status_code="429"}`, алерт
  `LoginBruteForce`; в журнале действий — вход с `blocked: true`.

## Журнал действий пользователей

Пишется **всегда в базу** (`audit_log`): кто, что сделал, над каким объектом и сущностью,
с какого адреса и с какой строкой браузера, роль на момент действия, статус ответа. Читается
через `GET /audit` (администратор и супервизор) с фильтрами по пользователю, объекту, действию,
типу актора и датам.

Кроме базы, запись уходит в настраиваемые каналы (`modules/notify.ts`):

| Канал | Настройка | По умолчанию |
|---|---|---|
| Файл JSON Lines | `AUDIT_FILE` | включён на стенде (`/data/audit.jsonl`) |
| Произвольный вебхук | `AUDIT_WEBHOOK_URL` | выключен |
| Telegram-бот | `AUDIT_TELEGRAM_TOKEN`, `AUDIT_TELEGRAM_CHAT` | выключен |

**Внешние каналы выключены намеренно.** Документы госнадзора и 152-ФЗ — это закрытый контур,
и отправка действий пользователей наружу должна быть решением того, кто разворачивает систему,
а не поведением из коробки. Ни один канал не может сломать запрос: ошибка записи логируется
и проглатывается, отправка идёт без ожидания ответа, с таймаутом в 3 секунды.

## Подвязка под электронную подпись

`POST /files/{file_id}/signature` принимает открепленную подпись (`.sig`, `.p7s`, `.sgn`, до
256 КБ), кладёт её в хранилище под `signatures/{sha256}` и показывает в `FileInfo.signature`.

**Проверки подписи нет, и мы её не заявляем:** `verification` всегда `NOT_VERIFIED`, а
`signature_status` документа по-прежнему берётся из реестра комплекта. Доступа к УКЭП на
соревновании не дают (REQ-INT-02), поэтому вывод о подлинности был бы выдумкой. Место под
`VALID` / `INVALID` в контракте уже есть — когда появится служба проверки, меняется только
реализация, а не контракт и не интерфейс.
