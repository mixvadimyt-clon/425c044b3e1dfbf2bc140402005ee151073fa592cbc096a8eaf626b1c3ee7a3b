# Сервис `web` (React)

> Документ обновляется в том же PR, что и код. Версия 0.3 (2026-09-17): дизайн по референсу.

## Назначение

Рабочее окно инспектора: загрузить комплект, увидеть расхождения на страницах ПД, РД и ИД, принять решение не больше чем за 3 действия. Плюс администрирование матрицы, аудит и ML-раздел.

**Требования к интерфейсу:**

- **Главный критерий — удобство инспектора:** время от открытия протокола до сохранения решений по всем кандидатам.
- **Сквозной сценарий из нескольких экранов**, в котором есть весь описанный функционал, а не экран на каждый модуль ТЗ.
- **Одно рабочее окно:** карточка доказательства и **синхронные панели по стадиям — ПД, РД и ИД отдельно**. В каждой панели файл, шифр, редакция, статус утверждения и переход к доказательству.
- **«3 клика»** = не больше трёх осознанных действий **от открытия карточки** до сохранённого решения.
- **Инспектор может править доказательства** (добавить, исправить, удалить фрагмент) — это сохраняется новой версией. **Метаданные файла он не правит**, только выбирает авторитетную редакцию и указывает основание.
- **Массовое подтверждение** кандидатов одного параметра допустимо. Массового отклонения быть не может.

## Стек

- **React** + TypeScript + **Vite**;
- **Ant Design 5** (тёмная тема `theme.darkAlgorithm` по умолчанию, переключатель на светлую, локаль `ru_RU`), `@ant-design/icons`;
- `react-router`, `@tanstack/react-query`;
- `openapi-fetch` + `openapi-typescript`: типы из `contracts/dist/inspector-api.v1.json`, **руками DTO не пишем**;
- `react-pdf` (pdf.js) для страниц и слоя разметки;
- ESLint, Prettier, Vitest, Testing Library.

### Два режима центра

| Режим | Когда | Что показывает | Данные |
|---|---|---|---|
| **Доказательства** (основной) | выбран кандидат | **2–3 синхронные панели по стадиям ПД / РД / ИД** — по одной на каждую стадию из фрагментов карточки. Пустая стадия: «нет доказательств» + кнопка «Дозагрузить». Заголовок панели: файл, шифр, редакция, статус утверждения, лист и страница, кнопка «к доказательству» (прокрутка и подсветка bbox) | `Finding.evidence_group.fragments[]` (stage, file_id, page, bbox, document_code, revision, approval_status, sheet) + `GET /files/{id}/content` |
| **Сравнение листов** и **гипотезы** в общем списке проверки | кандидаты и гипотезы в одном списке, фильтр из двух разделов; центр «Панели ПД / РД / ИД» или «Сравнение листов» | листы разных стадий, совмещённые (наложение или рядом, масштаб), области различий с подписями, «Соответствие N%» пары. Список: сначала кандидаты, затем гипотезы (оранжевая полоса); фильтры «Кандидаты» (Все / Ожидают / Подтверждено / Отклонено / Уточнено) и «Гипотезы» (Все / Ожидают / Уточнено / Отклонено / Кандидаты), заголовок раздела скрывает группу, поиск общий. У гипотезы в центре панели ПД / РД / ИД с её областью или сравнение листов, справа карточка и решение («Сделать кандидатом», «Отклонить», «Уточнить»); в полном экране список и проверка — плавающие панели «Показать / Свернуть». Из таблицы гипотез протокола и из уведомления ведёт `/verification?object=…&view=hypotheses` (открывает гипотезу, ждущую решения) | `GET /protocols/{id}/page-pairs` (`left`, `right`, `diff_regions`, `homography`, `compliance_percent`), `GET /processes/{id}/suspicions`, `POST /suspicions/{id}/decision`, `POST /suspicions/{id}/promote`, `GET /notifications` |

Фрагменты рисуются поверх страницы pdf.js, координаты в долях страницы: `left = x0 * width`, `top = y0 * height`. Цвета: EXPECTED (ПД, эталон) — синий, ACTUAL — оранжевый, MANUAL (добавлено инспектором) — пунктир.

### Откуда данные

| Элемент | API |
|---|---|
| Выбор объекта | `GET /objects` (`indicator`, `last_process_id`, `external_id`), «+ Новый объект» — `POST /objects` |
| «Загрузить» и drag-drop | `POST /documents/upload`: `object_id` или `process_id`, `auto_start=true`, **`registry` (файл реестра CSV/XLSX/JSON — обязателен по «Перечню ИД»)** или `manifest` (JSON), `stage_hints`. В ответе у файла `error` или `warnings[]`. Затем опрос `GET /processes/{id}/status` каждые 2 с |
| «Загрузить реестр» (если его нет или нужна замена) | `POST /processes/{id}/registry` (multipart `registry`) → `RegistryApplyResult` (`matched_files`, `completeness`, `analysis_started`) |
| Индикатор «Комплект: ПД ◐ РД ◐ ИД ○» и страница «Комплектность» | `ProcessInfo.upload_status` + **`ProcessInfo.completeness`** (`status`, `registry`, `registry_file_name`, `expected_total`, `present_total`, `missing[]`, **`issues[]`**, `note`). `status`: COMPLETE — «Полный», MISSING_EVIDENCE — «Не хватает документов», NOT_COMPARABLE — «Есть нечитаемые файлы», CLARIFICATION_REQUIRED — «Требует уточнения». При `registry = ABSENT` — баннер и кнопка «Загрузить реестр» |
| «Загруженные PDF» | `GET /processes/{id}/files`: стадия, `metadata_source`, `external_file_id`, `approval_status`, `signature_status`, статус обработки, число страниц, отклонённые файлы с причиной; `excluded_from_comparison` + `exclusion_reason` — приглушить (заменённая редакция, дубликат) |
| Выбор авторитетной редакции | меню файла «⋮» → «Сделать эталонной редакцией» или «Указать предыдущую редакцию» → `PATCH /files/{id}` с `is_authoritative` / `predecessor_id` + **обязательное основание** (`comment`, `reference`). Другие поля API отклонит (`METADATA_READONLY`) |
| Замечания | текущая страница — `GET /protocols/{id}/findings?file_id=…&evidence_page=…`; все — `?finding_status=CANDIDATE` |
| Карточка | `Finding`: параметр, `rule_key`, expected / actual / delta, `rationale` (+ `rationale_source`), норматив, приоритет проверки, `evidence_changed`, `decision_history`, **`evidence_history`** (версии: MODEL / INSPECTOR, кто, когда, причина) |
| Решение | `POST /findings/{id}/decision`: `CONFIRM` / `REJECT` (`reason_code` + `comment`) / `CLARIFY` |
| «✎ Править доказательства» | режим правки на панелях: нарисовать bbox (добавить фрагмент с ролью и значением), удалить фрагмент, указать причину и ссылку → `POST /findings/{id}/evidence` |
| «☐ выбрать все по параметру» | `POST /findings/bulk-decision` (`action`: CONFIRM или CLARIFY, `finding_ids` одного параметра). Кнопки «Отклонить» в массовом режиме **нет**. В списке: флажки у кандидатов без решения, после первой отметки другие параметры недоступны, панель «Подтвердить (N)» (с подтверждением) и «Уточнить (N)» (комментарий обязателен); правила выбора — `canSelectForBulk`, `bulkCandidatesOf` в `shared/verification.ts` |
| Сравнение листов и гипотезы | `widgets/CompareWorkspace.tsx`, `ComparePages.tsx`, `SuspicionsPanel.tsx` | переключатель центра; пары из `GET /protocols/{id}/page-pairs`; наложение правой страницы через `homography` (`homographyToCss`, `mix-blend-mode: multiply`, ползунок прозрачности «РД поверх ПД») или страницы рядом; области `diff_regions`: красные (`finding_id`, клик открывает карточку), жёлтые (`suspicion_id`; подпись «только в ПД/РД/ИД» — цветом стадии вместо жёлтого, `regionColor`), серые (различие без записи, без клика); сдвиг и масштаб ограничены границами панели (`clampPan`); гипотезы `GET /processes/{id}/suspicions`: `POST /suspicions/{id}/decision` (`DISMISS` / `CLARIFY`, комментарий обязателен) и `POST /suspicions/{id}/promote` (параметр из `GET /admin/params`, доказательства гипотезы плюс рамки, нарисованные на страницах «Рядом»); решать и переводить в кандидаты — только инспектор и супервизор; покрытие графического поиска (`api/visualCoverage.ts`, `widgets/VisualCoverage.tsx`, `GET /protocols/{id}/visual-coverage`): полоса между панелью управления и страницами пары «Проверено N из M листов, K пар из L» (проверено = листы из `sheets`, с которыми сравнили хотя бы одну пару; всего = проверено плюс `skipped_total`; счётчики стадий не берём: векторные мозаики входят и в кандидаты, и в мозаики), пометка «ограниченный прогон» с действовавшими лимитами (листов на стадию, пар, секунд), список «Пропущено N» с причиной по-русски (`LIMIT`, `PAIRS_LIMIT`, `TIMEOUT`, `MOSAIC`, `NO_DRAWING_REGION`) и «открыть лист» (пара листа, если она есть, иначе сам лист одной страницей); лист подписан шифром документа из списка файлов комплекта; если в список вошли не все пропущенные, дописано «и ещё N», страницы с большим текстом упомянуты отдельной строкой; без пропусков и лимитов одна строка «Все листы-чертежи проверены», нет чертежей: «Листы-чертежи в комплекте не найдены»; 404 (старый ML, графический поиск выключен, нет ПД) и экран очереди дообучения: блока нет; в полном экране одна строка |
| «Протокол» | `GET /protocols/{id}`: 5 таблиц, версии (`GET /processes/{id}/protocols`), экспорт, «Завершить» / «Отменить финализацию» |

### Термины интерфейса

Тексты для пользователя пишем по этой таблице (сверено с [glossary.md](../glossary.md)); имена в коде, API и коды статусов не меняются.

| Что | Как называем в интерфейсе | Не пишем |
|---|---|---|
| Здание или комплект документов | **проект** (объект оставляем только про идентификатор во внешней ИС) | «объект» в подписях, колонках, сообщениях |
| Найденное моделью расхождение, ждущее решения | **кандидат** | «несоответствие» (кроме слов «протокол несоответствий») |
| Что модель нашла (в пояснениях) | **расхождение** | |
| Кандидат, подтверждённый инспектором | **нарушение** | нарушение до решения инспектора |
| Чтение файлов системой | **разбор**, «Разобран» | разбор в значении «решение по записи» |
| Записи, которые инспектор отклонил, для администратора | **записи для дообучения** (меню и блок дашборда), «Ждут решения», «Решения приняты» | «К разбору», «Разобрано» |
| Действие и состояние | «Завершить проверку»; «Финализирован», «Финализированные проекты», «Откатить финализацию» (термин из ТЗ, глоссарий: финализация — кнопка «Завершить») | |
| Что не хватает в комплекте | **комплектность** | «замечания по комплекту» |

### Правила UX (обязательные)

- **≤ 3 действий от открытия карточки до сохранённого решения:**
  - подтвердить: карточка → «Подтвердить» (2);
  - отклонить: карточка → «Отклонить ▾» → причина (3). **Выбор причины сразу сохраняет решение**, комментарий по шаблону причины (дописать можно заранее в поле);
  - уточнить: карточка → «Уточнить» (2).
- После решения фокус сам переходит на следующий ожидающий кандидат, панели перелистываются к его доказательствам.
- Горячие клавиши: `1`, `2`, `3` — решения, `←` / `→` — кандидаты, `N` — следующий без решения, `PgUp` / `PgDn` — страницы, `E` — правка доказательств, `F` — во весь экран, `Esc` — выход из режима или закрытие формы, `Shift + /` — справка; в форме комментария `Enter` отправляет, `Shift + Enter` — новая строка. У администратора в разборе дообучения: `1` отправить, `2` не отправлять.
- Синхронная прокрутка и масштаб панелей. Клик по области открывает её карточку, клик по карточке ведёт к доказательствам.
- «Приоритет проверки» (HIGH / MEDIUM / LOW) — это не «серьёзность нарушения».
- Комплектность и MISSING_EVIDENCE — **отдельно** от кандидатов, с кнопкой «Дозагрузить».
- После `FINALIZED` все изменяющие действия скрыты. «Отменить финализацию» — только ADMIN и SUPERVISOR, с причиной.
- Ошибки API показываются русским текстом из `Error.message`: 400, 409 и 413 объясняют, что делать дальше.
- Пометка «ML-заглушка» в `rationale` — демо-данные, показывать как есть.

## Состояние реализации (2026-09-19)

К api подключены вход, объекты, загрузка, верификация и протокол. Админка пока на моках: данные лежат в `src/pages/protocol/protocolData.ts` и `src/shared/retrainQueue.ts` (`localStorage`), поля названы как в контракте. Демо-проекты `src/shared/projects.ts` показываются только когда сервер недоступен (запасной режим, плашка на экране).

Слой api — `src/api/`: `projects.ts` (объекты и проверки), `upload.ts` (загрузка с прогрессом, реестр, проверка формата и размера), `processes.ts` (статус, файлы, `PATCH /files`), `findings.ts` (несоответствия и решения), `protocols.ts` (версии протокола, финализация, экспорт, передача во внешнюю ИС). Типы генерируются из контракта (`npm run gen`), DTO руками не пишутся.

| Часть | Где | Что делает |
|---|---|---|
| Список проектов | `app/providers/ProjectProvider.tsx`, `useProjects` | объекты из `GET /objects` со стадиями из `upload_status`, выбранный проект; выбор попадает в список «Проект» в шапке и запоминается при переходах по меню. **Роли.** По коду api решения, разделение, правку доказательств и завершение проверки может только `INSPECTOR` и `SUPERVISOR`; у `ADMIN` и `ML_ENGINEER` эти действия скрыты (`canDecide` в верификации, `canFinalizeRole` в протоколе), доступен просмотр. Отмена финализации — `ADMIN` и `SUPERVISOR`. Страница «Администрирование» — только `ADMIN`. Журнал аудита в api общий (`audit_log`), роль пользователя хранится в самой записи (`AuditEntry.user_role`, контракт 0.11.0) — не вычисляется заново при чтении.

**Режимы данных и состояние системы.** Демонстрационный режим включается только сборкой с `VITE_DEMO_MODE=true` (`app/config.ts`, по умолчанию выключен): проекты и решения берутся из моков и нигде не сохраняются. Без него `ProjectProvider` никогда не подставляет моки: `mode` = `live` (данные сервера), `offline` (сервер недоступен и данных нет — вместо страницы ошибка «Нет связи с сервером», `ApiUnavailable`), `stale` (сервер недоступен, показаны последние загруженные данные). Под шапкой красная (`demo`, `offline`) или оранжевая (`stale`) полоса с кнопкой «Повторить»; в явном демо-режиме других предупреждений нет, чтобы не повторяться; метка «ДЕМО-ДАННЫЕ» у заголовка разбора для дообучения (`DemoTag`) показывается только в этом режиме — раздел «Администрирование» и разбор для дообучения на api теперь настоящие данные, не моки. В шапке `SystemStatus`: точки API (`GET /health`), «Разбор» (по статусам проверок из списка проектов: в работе, ошибка) и внешней ИС (`GET /integration/status`, только ролям с доступом), опрос раз в 30 с; правила — `summarizeSystem` в `api/system.ts`.

**Стиль.** Основной цвет `#12988C` задан в теме Ant Design (`AntdConfigProvider`), кнопки одинаковые (без тени, скругление 8). Тёмная тема — нейтральные серые без синего оттенка; выбранный пункт меню и списков светло-серый с белым текстом, обычные кнопки серые (зелёные только основные). Синий остался только в цветах стадий (ПД синий, ИД фиолетовый): по докам ожидаемое значение подсвечивается синим. Экраны рассчитаны на ширину 1024–1920 px.

Если времени меньше, станции 2 и 3 уходят в слово («комплект загружен и разобран заранее»), остаётся 225 секунд, станции 5 и 7 не трогаем.

### Что проверить на каждой станции перед показом

- Станция 4: в списке и в шапке карточки у кандидатов M-078 видно «пом. N» (без него девять кандидатов выглядят одинаково), системы в значениях ПД и РД читаются, на листах ПД и РД стоят рамки. Источник «OCR» у значения из плана РД объясняется одной фразой: подписи систем на планах нарисованы шрифтом САПР. ⬜ сверить после пересборки.
- Станция 6: гипотеза на «Тюменской, 5» одна, помещения названы (266, 267, 270, 271, 272), листы ПД (стр. 99) и РД открываются по клику. Уверенность у гипотезы 0,55: так и должно быть. ⬜ сверить после пересборки.
- Станция 5: клик по рамке открывает нужный лист, таблица по стадиям не обрезана, решение попадает на ту находку, о которой говорим.
- Станция 7: на ограниченном прогоне (стенд без видеокарты) видно пропущенные листы с причиной, на GPU-прогоне видно, что проверено всё.
- Станция 9: плашка «Передано» появилась. Если «Передаётся», пауза 5–10 секунд и обновить страницу.

### Если что-то пошло не так

- Разбор идёт дольше 15 секунд: не ждать, открыть уже разобранный проект и вернуться к загрузке на словах.
- Кандидатов не те: не показывать вслепую, свериться с таблицей ожидаемых значений комплекта.
- Живое демо не работает: запасное видео, ссылка на слайде 8.

### Что ждёт от других

- Вентиляция и тёплый пол влиты в `main` 17.10.
- Для станций 4 и 6 нужен GPU-прогон с OCR планов (`CAD_OCR_ENABLED`): на стенде без видеокарты находок по вентиляции не будет.
- Пересборка стенда 20.10, после неё прогон сценария на финальном стенде.

## Запуск


- `inspector/inspector` — верификация;
