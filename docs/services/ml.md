# Сервис `ml` (Python)

> Документ обновляется в том же PR, что и код. Версия 0.6 (2026-09-19): OCR, разбор PDF и метаданные, HTTP-задачи и кеш, каркас сервиса.

## Назначение

Сервис делает следующее:

- парсинг PDF, DOCX и XML;
- классификация качества страниц, OCR;
- макет и таблицы, метаданные из штампа;
- извлечение значений по матрице (**132 параметра M-001…M-132, начинаем с 2: M-002, M-055**);
- совмещение и визуальное сравнение чертежей;
- движок правил и выбор редакций;
- гипотезы;
- офлайн-оценка по §14.

Требования: REQ-PRS-*, REQ-CMP-*, REQ-SUS-*, REQ-ML-* ([../TZ.md](../TZ.md)).

## Исходные условия для ML

- **Метрики.** Главные — precision, recall и F1 выявления нарушений; единица оценки — атомарная точка `object_id + param_code (+ rule_key)`.
- **Эталон — ПД**, РД и ИД сравниваются с ней.
- **Реестр файлов обязателен** («Перечень ИД» ред. 1.1, [domain/registry.md](../domain/registry.md)). Если `CompareFile.metadata_source = MANIFEST`, поля из реестра не переопределять. `CompareFile.external_file_id` — `file_id` заказчика (его пишем в GOLD); заменённые и аннулированные редакции приходят в `CompareRequest.excluded_files`, дубликаты не приходят. `approval_status`: DRAFT / APPROVED / FOR_CONSTRUCTION / SUPERSEDED / CANCELLED / UNKNOWN.
- **Пилотная разметка** (Приложение 1, лист «ПРИМЕРЫ РАЗМЕТКИ»): в основном изменения назначения и площадей помещений на планах (ПД АР ↔ РД АР). Для нашего объекта — ALT79B-V01: ПД АР стр. 19–20 ↔ РД АР стр. 4–5.
- **Свободный поиск — только расхождения между ПД, РД и ИД.** Соответствие нормам (СП, СНиП) не проверяем, `NORMATIVE_ANALYSIS` не делаем.
- **Входные данные:** векторные PDF из САПР **со слоями** — текстовый слой и OCG пригодятся. DWG не нужен. Раздел может состоять из нескольких файлов. Будут повёрнутые страницы, плохие сканы, нестандартные CropBox и MediaBox, печати поверх текста; текст хуже 300 dpi и рукопись → `LOW_QUALITY` / `ABSTAIN`.
- **В выборке есть реально повреждённые PDF** (`8. Раздел 8 ЖС-РД-270121-П-ООС*.pdf` обрезаны) — api их отклоняет, но парсер тоже должен падать корректно (`CORRUPTED_FILE`).
- **Модели:** только локальные, открытые веса, лицензия для государственного использования ([ADR-0006](../adr/0006-ml-stack.md), таблица лицензий). Без моделей на сотни ГБ, квантизация — плюс.
- **Дообучение:** воспроизводимый контур (сбор, проверка полноты доказательств, разбиение по object_id, хеши) и **настоящее дообучение**.
- **Данные** — 18 объектов датасета организаторов.

## Стек ([ADR-0006](../adr/0006-ml-stack.md))

| Этап | Технология | Пакет |
|---|---|---|
| Загрузка, текстовый слой, геометрия страниц | PyMuPDF | `pymupdf` |
| Качество страницы (текст / скан / чертёж; OK / LOW_QUALITY / ABSTAIN) | custom Python | — |
| Резервный OCR | PaddleOCR (кириллица) | `paddleocr`, `paddlepaddle` — extra `ocr` |
| Макет и таблицы | Docling + свои правила | `docling` — extra `layout` |
| Структурированное извлечение и объяснения | Qwen через OpenAI-совместимый API | `httpx` (или `openai`) — extra `llm` |
| Сопоставление сущностей | правила | `rapidfuzz` |
| Запасной путь извлечения числовых параметров ([ниже](#sentence-bert-в-продукте-2809)) | Sentence-BERT `paraphrase-multilingual-MiniLM-L12-v2`, флаг `SBERT_ENABLED` | `sentence-transformers`, torch для процессора — extra `embeddings` |
| Совмещение чертежей | OpenCV ORB + RANSAC + homography | `opencv-python-headless`, `numpy` |
| Визуальные различия | OpenCV absdiff / contours | то же |
| Сервис | FastAPI | `fastapi`, `uvicorn`, `pydantic` v2, `pydantic-settings`, `structlog`, `prometheus-client` |

Базовая установка (`uv sync`) должна работать **без** тяжёлых extras. Extras ставятся командой `uv sync --extra ocr --extra layout`. **OCR обязателен:** в скрытой части датасета 55 % страниц без текстового слоя, поэтому OCR сделан раньше извлечения значений.

**LLM:**

- включается переменной `LLM_ENABLED=true`;
- адрес задаётся в `LLM_BASE_URL`: vLLM на сервере или Ollama локально (`http://localhost:11434/v1`), модель — в `LLM_MODEL`;
- без LLM конвейер обязан работать;
- ответ LLM всегда проверяется правилами и привязывается к bbox, иначе в кандидаты он не попадает;
- облачные LLM API запрещены.

## Запуск (локально, без Docker)

Подробности и таблица переменных — [services/ml/README.md](../../services/ml/README.md).

```bash
cd services/ml
uv sync                 # базовые зависимости + dev; тяжёлые компоненты — через --extra
uv run gen              # модели контрактов из contracts/dist/ml-events.v1.json (в git не идут)
uv run pytest
uv run inspector-ml serve
```

`GET /health` отвечает по контракту и показывает, что реально установлено:

```json
{ "status": "ok", "version": "0.1.0", "capabilities": { "pdf": true, "cv": true, "ocr": false, "docling": false, "embeddings": false, "llm": false } }
```

- `status = ok`, пока доступен базовый путь (PyMuPDF + OpenCV); иначе `degraded`.
- `capabilities` определяются по наличию модулей из extras, `llm` — по `LLM_ENABLED`.
- `GET /metrics` — формат Prometheus (`ml_build_info`, `ml_http_requests_total`, `ml_http_request_duration_seconds`).
- Логи — один JSON-поток в stdout (`timestamp`, `level`, `service`, `message`, `request_id`); логи uvicorn идут туда же.
- Версия Python закреплена в `services/ml/.python-version` (3.12), зависимости — в `uv.lock`.
- Пути `STORAGE_DIR` и `CACHE_DIR` из `.env` считаются от корня репозитория, поэтому api и ml видят одни и те же файлы.

## Как api общается с ml (контракт `contracts/events/ml-events.v1.yaml`, v0.3)

```
api ──POST {ML_URL}/v1/jobs  (Envelope{type, payload, reply_to})──▶ ml   → 202 {message_id, state: QUEUED}
ml  ──POST {reply_to}        (Envelope{ml.parse.result | ml.compare.result})──▶ api → 204
```

- `reply_to` = `http://localhost:3000/internal/ml/results`. Если api задал `INTERNAL_TOKEN`, ml возвращает его в заголовке `x-internal-token`.
- Задачи выполняются в фоне: очередь внутри процесса (`asyncio` + пул процессов для тяжёлого CPU). Повторный `message_id` не запускает задачу второй раз.
- `GET /v1/jobs/{message_id}` — состояние задачи для отладки. `GET /health` — `capabilities` (ocr, docling, llm, cv).
- Ошибку отдаём результатом со `status=FAILED` и `error{code, message, retryable}`. api сам повторит задачу, если `retryable`.
- Файлы: `S3Ref{bucket: "local", key}` → путь `{STORAGE_DIR}/{key}`. api и ml запускаются на одной машине и видят общую папку `var/storage`.
- Для проверки без api: `inspector-ml parse <pdf>` и `inspector-ml compare <папка>`.

### Что уже работает

- **Идемпотентность.** Повтор `POST /v1/jobs` с тем же `message_id` не запускает работу второй раз,
  а возвращает текущее состояние. Результат лежит в `GET /v1/jobs/{message_id}` независимо от того,
  дошёл ли callback, — api может забрать его сам.
- **Хранение результатов (ревью п. 3).** Результат пишется ещё и на диск, в `CACHE_DIR/jobs/{message_id}.json`,
  и переживает перезапуск ml: `GET` отдаёт его, а повтор задачи с тем же `message_id` работу не запускает.
  Живёт `ML_JOB_TTL_S` (48 часов), в памяти — не больше `ML_JOB_MEMORY_MAX` (50) готовых задач, остальные
  читаются с диска. Из памяти вытесняется только результат, который удалось записать на диск: кончилось место —
  результат остаётся в памяти, а не пропадает совсем. Запись идёт не в цикле событий (`asyncio.to_thread`): большой
  результат сравнения не останавливает `/health` и `GET /v1/jobs`. Задача, которая стояла в очереди или шла в момент
  перезапуска, теряется: `GET` отвечает 404, и api повторяет отправку с тем же `message_id`.
- **Очередь.** `asyncio`-очередь и пул процессов (`ML_WORKERS`, по умолчанию 2). `ML_EXECUTOR=thread`
  переключает пул на потоки — это нужно тестам и отладке. Таймаут берётся из `options.timeout_s`,
  иначе из `ML_JOB_TIMEOUT_S`; после таймаута пул пересоздаётся, чтобы зависшая задача не занимала воркера.
  **Процесс зависшей задачи убивается** (ревью п. 4), в Linux — вместе с его группой. Иначе он доедал бы
  процессор стенда до конца, а при `ML_JOB_TIMEOUT_S=5400` это полтора часа. Рабочий процесс записывает свой PID
  в `CACHE_DIR/jobs/{message_id}.pid`. Убийство одного процесса ломает весь пул, поэтому задачи, которые шли в нём
  рядом, получают `BrokenProcessPool` и один раз перезапускаются в новом пуле, а не падают. На стенде это может стоить
  соседней задаче ещё одного полного сравнения — для соревнования принимаем, дальше — отдельный процесс на задачу.
  **Пул, сломанный не нами, тоже пересоздаётся**: ядро убило процесс по нехватке памяти, он
  упал в paddle или torch. Раньше пул оставался сломанным, и все следующие задачи падали `INTERNAL` до ручного
  перезапуска ml при зелёном `/health`. Задача, которая роняет процесс и на повторе, уходит в `INTERNAL`, но пул после
  неё снова целый. **При остановке ml** процессы идущих задач убиваются: рабочие процессы — главы своих групп, и Ctrl+C
  терминала до них не доходит. Процесс убивается по PID из файла: если задача закончилась ровно на таймауте, а
  процесс уже взял следующую, убьём её — редкий случай, известный.
- **Callback.** `POST {reply_to}` с `Envelope`, `correlation_id` = `process_id`, заголовок
  `x-internal-token` (если задан). Повторы при недоступности api — через 1, 5 и 15 секунд.
  **Только на разрешённый адрес** (ревью п. 2): `reply_to` должен совпадать по схеме, хосту и порту с
  `API_URL` или с одним из `ML_CALLBACK_ORIGINS` (через запятую). `localhost`, `127.0.0.1` и `::1` считаются одним
  адресом. На чужой адрес результат не уходит: `callback_rejected` в журнале, `ml_callbacks_total{outcome="rejected"}`,
  а результат остаётся в `GET /v1/jobs`. В compose `API_URL` у ml и `API_PUBLIC_URL` у api — оба `http://api:3000`,
  локально — `http://localhost:3000`, так что настраивать ничего не нужно.
  Если у ml задан `INTERNAL_TOKEN`, он же требуется во входящих запросах, иначе `401`.
- **Кеш (REQ-PRS-07).** Ключ — `sha256 + PARSER_VERSION`, значение — `parsed/{sha256}/{version}.json`
  в `STORAGE_DIR`, индекс — в `CACHE_DIR`. Повторная загрузка того же файла (в том числе в другую
  проверку) отвечает `from_cache = true` мгновенно. `options.force_reparse` кеш игнорирует.
  Хеш файла пересчитывается только при промахе кеша: на попадании это лишние секунды на файлах в гигабайты.
  Запись атомарная — во временный файл рядом и `replace`: процесс могут убить посреди записи.

**Коды ошибок** (`error{code, message, retryable}`):

| Код | Когда | `retryable` |
|---|---|---|
| `FILE_NOT_FOUND` | файла нет по ключу `S3Ref` | да (файл может ещё копироваться) |
| `SHA256_MISMATCH` | хеш файла не совпал с заявленным в запросе | нет |
| `CORRUPTED_FILE` | PDF не открывается, защищён паролем или в нём нет страниц; DOCX не zip или без `word/document.xml`; XML не разбирается | нет |
| `UNSUPPORTED_FORMAT` | формат `OTHER` (архивы, DWG, изображения): лежит в комплекте карточкой, не разбирается | нет |
| `UNREADABLE` | ключ вне `STORAGE_DIR` или не локальный bucket | нет |
| `TIMEOUT` | задача не уложилась в `timeout_s` | да |
| `ENGINE_NOT_READY` | движок сравнения недоступен | нет |
| `INTERNAL` | всё остальное | да |

**Про «битые» файлы.** PyMuPDF восстанавливает повреждённый xref и открывает обрезанные PDF
(так было с `F0418`, который организаторы исключили из датасета). Поэтому «не открылся» —
не единственный признак: документ без страниц тоже считается `CORRUPTED_FILE`.

## Разбор документа

Что попадает в `ParsedDocument` помимо страниц и блоков.

**Классификатор страницы** (`quality/page_classifier.py`) даёт две независимые характеристики:

| Что | Значения | Как определяется |
|---|---|---|
| вид листа | `text` / `scan` / `drawing` | растр закрывает больше 60 % листа и текста нет → скан; лист крупнее A3 или тяжёлый поток отрисовки → чертёж |
| качество | `OK` / `LOW_QUALITY` / `ABSTAIN` | меньше 10 символов → `LOW_QUALITY` (страницу заберёт OCR); совсем пустая страница → `ABSTAIN` (OCR не поможет) |

Порог в 10 символов **подобран по разметке организаторов**, а не на глаз: в `page_index.jsonl`
у каждой страницы есть поле `needs_ocr`. На 60 файлах обучающей части (3472 страницы, из них
996 с `needs_ocr`) правило совпало с разметкой **на всех страницах**: ни одного пропуска,
ни одного ложного срабатывания. При пороге 20 точность падает до 0.982, при 200 — до 0.861.
Проверка повторяется командой `inspector-ml dataset calibrate <корень dataset>`
(на 40 файлах равномерной выборки — 1777 страниц, accuracy 1.0).

**Метаданные из основной надписи** (`layout/title_block.py`, `metadata/`): шифр, стадия, марка,
изменение, дата, статус утверждения и подписи, соответствие страниц листам. Блоки штампа
помечаются `type: title_block` — фронт может подсвечивать их отдельно.

Что показала сверка на 40 файлах (`inspector-ml dataset metadata`):

- **стадия — 0.92** по кураторскому полю `files_index.stage`;
- **марка** совпадает в 40 % случаев, но расхождения в основном не наши ошибки: организаторы
  пишут раздел ПД (`VK`, `SS`), а мы — марку комплекта из шифра (`ИОС`, `КЖ`). В бою марку
  всё равно даёт реестр (`metadata_source = MANIFEST`), наша — перекрёстная проверка;
- **шифр** извлекается у 97 % файлов; сверять его с `META-DOC-CODE` бессмысленно — это машинная
  предразметка, у актов туда попадает «ВН.ТЕР.Г» из адреса.

Важные частности, найденные на данных:

- «Взамен инв. №» — штатное поле штампа по ГОСТ, а **не** признак заменённой редакции: по нему
  нельзя ставить `SUPERSEDED`, иначе файл вылетит из сравнения;
- короткие марки (`ПЗ`, `СС`, `ГП`) нельзя искать в свободном тексте — берём их только из шифра,
  имени файла или поля «Марка». Имя файла обязательно: в корпусе марка часто есть только там;
- одно упоминание акта освидетельствования не делает том исполнительной документацией —
  нужны хотя бы два признака;
- номер листа в штампах САПР часто записан без слова «Лист», поэтому `sheets[].sheet` пока
  заполняется не всегда; в бою диапазон листов приходит из реестра (`sheet_page_range`).

**Стадия: порядок признаков (25.09).** На обучающих объектах против стадии из папки
(«Стадия П», «Стадия РД», «ИД») классификатор давал 213 верных из 259, теперь — **246**. Порядок —
от надёжного к косвенному ([`metadata/classify.py`](../../services/ml/src/inspector_ml/metadata/classify.py)):

1. поле «Стадия» в основной надписи;
2. имя акта («АОСР №1.1_П от …») — ИД, хотя в имени стоит «П»;
3. буква стадии **прямо перед маркой**: «ЖС-РД-270121-**П-ИОС**5.1» — ПД. «РД» в начале этого
   шифра — номер проекта, и прежнее «есть РД — значит РД» отправляло в РД весь ПД Алтуфьевского
   2024 года;
4. два и больше признака ИД в тексте;
5. **перевес** признаков РД или ПД в тексте, а не «кто проверен первым»: КР2 Новослободской
   упоминает «основной комплект» и уходил в РД;
6. одиночная буква стадии в шифре или имени — последней: «П-2025-04-266» бывает номером проекта
   и у рабочей документации.

Из 13 оставшихся ошибок шесть — исполнительные чертежи и акты в папке «Рабочая и исполнительная
документация»: классификатор ставит им ИД и, похоже, прав.

**Метаданные пересчитываются при попадании в кеш** ([`metadata/facts.py`](../../services/ml/src/inspector_ml/metadata/facts.py),
`describe`): ≈0.15 с на том в 150 МБ, без OCR и без смены `PARSER_VERSION`. Поэтому правки
классификатора доходят до кеша на стенде сразу, а имя файла берётся у этой загрузки, а не у
предрасчёта. Сохранённые в кеше метаданные больше ничего не решают.

**Дополнительные сведения** лежат в том же словаре метаданных. Первые восемь контракт принял
в `DocumentMetadata` 0.6.0 , `developer_org` — в 0.7.0 . Api отдаёт их в `FileInfo`:

| Поле | Что |
|---|---|
| `project_code` | шифр проекта — шифр документа до стадии и марки: «ЖС-РД-270121-П-АР» → «ЖС-РД-270121» |
| `language` | `ru` / `en` / `mixed` по доле кириллицы; латинские марки (B25, A500C) документ русским быть не мешают |
| `scan_share` | доля страниц, прошедших OCR |
| `file_size`, `pdf_version`, `pdf_producer`, `pdf_creator`, `encrypted` | из заголовка PDF, страницы не читаются |
| `developer_org` | организация-разработчик ПД/РД: «ООО «ГЕНПРОЕКТ»»; уверенность — `field_confidence.developer_org` |

Число страниц и страницы с текстовым слоем уже идут в `FileQuality`. Дату загрузки и источник
знает api (кеш общий для одинаковых файлов), фамилии из штампа не собираем — персональные данные.

**Организация-разработчик** ([`metadata/organization.py`](../../services/ml/src/inspector_ml/metadata/organization.py)).
По ГОСТ Р 21.101 она стоит в графе 9 основной надписи отдельной строкой, на титуле — вверху и в подписи
«Генеральный директор ООО …». Как выбираем:

1. **Штамп важнее титула.** Том субподрядчика открывается титулом генпроектировщика («БратКом-групп»),
   а графа 9 называет того, кто том выпустил («ТСП»). Из штампа берётся организация, которая стоит
   **хотя бы на двух листах**: в приложения записок вшиты письма с ТУ и сертификаты, и на их бланке
   организация («ПАО «МГТС»», «АО «ОЭК»», «ЗАО «Рувинил»») тоже стоит отдельной строкой внизу справа,
   но на одном листе.
2. Иначе — титул, **последний** из первых трёх листов, где есть организация: за титулом генпроектировщика
   идёт титул субподрядчика.
3. Строка — организация, только если перед ней пусто или роль разработчика («Разработчик»,
   «Генеральный директор», «ГИП»), а после названия пусто или реквизиты. Отсекаются заказчик
   (в той же строке, строкой выше «Заказчик:» или «В ПРОИЗВОДСТВО РАБОТ», строкой ниже, как в штампе
   топоплана),
   специализированный застройщик («СЗ …», «С3 …»), изыскатель подосновы («Масштаб 1:500» /
   «ООО «Планета Изысканий»»), «© ГБУ «Мосгоргеотрест»», упоминания в тексте («гуп «Мосводосток»
   или по его указанию» — сокращения правовых форм принимаются только заглавными).
4. Название приводится к «ООО «…»»: полные формы сокращаются, кавычки — ёлочками и парами, разрядка
   («В Е Л Е С») снимается, обрезанное переносом берётся полным, если оно встретилось где-то целиком.
5. **ИД — пусто:** в актах несколько организаций в разных ролях, графы 9 нет. **ИП — только «ИП»:**
   название индивидуального предпринимателя — фамилия человека (152-ФЗ).

Уверенность: 0.9 — штамп и титул совпали, 0.8 — только штамп, 0.6 — только титул, 0.5 — штамп
на одном листе.

**Замер 25.09** на кеше 0.4.0, **только обучающие объекты** (Новослободская, Алтуфьевское, «Пример
нарушений»; Речников — скрытая тестовая часть — исключён): значение у **всех 150 томов ПД и РД**.
Ручная проверка: 40 случайных томов — 39 верно; единственную ошибку (штамп «В ПРОИЗВОДСТВО РАБОТ»
заказчика и название «ПРОЕКТНАЯ КОМПАНИЯ «ГЕОСТРОЙПРОЕКТ»» в три строки) исправил, поэтому
отдельно **свежая выборка из 30 томов, которых правила не видели: 28 верно, 2 правдоподобно,
неверных нет**. Оговорка: часть правил я подбирал, глядя и на тома Речникова (серия «22-14-П-…»),
до того как заметил, что они в том же кеше; цифры выше посчитаны без них. Одна организация может прийти
двумя написаниями: «ТСП» в штампе и «ТЕХНОЛОГИИ СТРОИТЕЛЬНОГО ПРОЕКТИРОВАНИЯ» на титуле — аббревиатуру
с полным названием не сводим.

**Слои PDF (OCG)** читаются по флагу `PARSE_READ_LAYERS` (по умолчанию выключено): в корпусе
в слоях лежит около 1 % текстовых фрагментов, а разбор дорожает примерно на треть. Имена слоёв
осмысленные («Размеры», «Координаты», «ОТКЛОНЕНИЯ») и пригодятся на чертежах.

**Команды для работы с выгрузкой:**

```bash

uv run inspector-ml dataset calibrate "<корень dataset>"      # классификатор страниц против needs_ocr
uv run inspector-ml dataset metadata "<корень dataset>"       # стадия, марка и шифр против разметки
```

## OCR

Распознавание включается для страниц, которые классификатор пометил `LOW_QUALITY`
(читаемого текста нет). Это не частный случай, а половина скрытой тестовой части:
**55 % её страниц без текстового слоя**.

Как устроено:

1. **Рендер.** `page.get_pixmap()` в оттенках серого. Растр PyMuPDF уже повёрнут по `/Rotate`,
   поэтому координаты строк нормализуются по размеру изображения и попадают в ту же систему,
   что и bbox текстового слоя.
2. **Ограничение размера.** Лист A0 при 300 dpi — это 14000 × 9900 пикселей; рендер
   масштабируется до `OCR_MAX_PX` по длинной стороне.
3. **Плитки.** Большие листы режутся на перекрывающиеся плитки `OCR_TILE_PX` с запасом
   `OCR_OVERLAP_PX`: иначе мелкие надписи на чертеже теряются. Строки, разрезанные границей
   плитки, сшиваются по общему тексту в полосе перекрытия (`ocr/render.stitch`, с `0.5.0`),
   оставшиеся повторы склеиваются по IoU, строки выдаются по рядам — см. «Стыки плиток» ниже.
4. **Движок.** `OCR_ENGINE`: `paddle` (основной, кириллическая модель), `tesseract` (запасной,
   `rus+eng`), `none` (выключить). Если выбранного движка нет, берётся любой установленный,
   а если их нет вовсе — страницы просто остаются `LOW_QUALITY`, разбор не падает.
5. **Результат.** Блоки распознавания выглядят как блоки текстового слоя, но несут `confidence`
   и `quality`; у страницы `source = OCR` и `ocr_confidence`. Страница со средней уверенностью
   ниже `OCR_MIN_CONFIDENCE` остаётся `LOW_QUALITY` — значения с неё брать рискованно.
6. **Бюджет.** `OCR_MAX_PAGES` ограничивает число распознаваемых страниц на документ:
   в ИД встречаются сканы на сотни листов, и распознавать их целиком нужно не всегда.
   `options.force_ocr` из `ParseRequest` распознаёт всё, даже страницы с текстом.

**Версии и модели — три грабли, на которые мы наступили при установке.**

1. **PaddleOCR 2.x не работает с paddlepaddle 3.x**: старые модели PP-OCRv3 падают на
   `fused_conv2d` («OneDnnContext does not have the input Filter»). Extra `ocr` требует
   `paddleocr >= 3.5` и `paddlepaddle >= 3.0`.
2. **oneDNN (MKLDNN) роняет PP-OCRv5 на paddlepaddle 3.3**
   («ConvertPirAttribute2RuntimeAttribute not support»): новый исполнитель PIR не умеет
   переводить атрибут-массив вещественных в рантайм-атрибут oneDNN-инструкции. Проверено
   **и в Windows, и в Linux (WSL, Ubuntu 26.04) — ошибка одинаковая**, флаги
   `FLAGS_enable_pir_api=0` и `FLAGS_enable_pir_in_executor=0` не помогают. Поэтому движок
   создаётся с `enable_mkldnn=False`: медленнее, но работает.
3. **Серверный детектор `PP-OCRv5_server_det` валит процесс** (segmentation fault) уже на
   странице A4 в 150 dpi; мобильный работает. И детектор, и распознаватель закреплены явно
   (`PP-OCRv5_mobile_det`, `eslav_PP-OCRv5_mobile_rec`): если указать только детектор,
   PaddleOCR берёт латинскую модель распознавания и читает «ГОСТ» как «ROCT».

Веса скачиваются при первом запуске, дальше берутся из кеша; установка занимает около 900 МБ,
поэтому extra остаётся необязательным.

### Таблицы после распознавания

У страницы без текстового слоя `chars == 0`, поэтому при первом проходе таблицы не собирались —
собирать было не из чего. Дальше `_apply_ocr()` подставлял распознанные блоки, но **разбор таблиц
второй раз не запускался**, и скан отдавал текст без единой таблицы. Значения мы берём как раз
из таблиц: акты, журналы, спецификации, экспликации.

Чинится одним ходом: `layout.rows.rows_from_blocks()` собирает строки не из слов, а из готовых
блоков с нормализованным bbox. Детектор PP-OCRv5 внутри таблицы режет по ячейкам, поэтому
распознанная строка ведёт себя как слово, и дальше работает та же сборка, что и для текстового
слоя — колонки, полосы, ячейки с координатами.

**Сколько это стоило корпусу.** Пересобрал таблицы по блокам, уже лежащим в предрасчитанном кеше,
без повторного распознавания:

| | |
|---|---:|
| Распознанных страниц в корпусе | 11 719 |
| Из них теперь дают таблицу | **6 477 (55 %)** |
| Ячеек, которых разбор не отдавал | **370 429** |
| В среднем ячеек на такую страницу | 57 |

На реальном реестре АОСР (скан, 5 колонок) собирается 204–243 ячейки на страницу против нуля.

**Честная оговорка про извлечение.** На двух проверенных актах ИД (`АОСР №3А-БСС`, `АОСР №10БЗ`)
M-055 находил «Стена в грунте» = B25 и **до** правки: там марка стоит в сплошном тексте, а
конструкция — в шапке акта, и работал текстовый путь. То есть правка закрывает структурную дыру
и возвращает 370 тысяч ячеек, но прибавку в извлечении на активных параметрах я пока не показал —
её даст generic-путь по матрице, который ищет значение по заголовку столбца.

**Версия разбора поднята до `0.3.0`:** результат разбора изменился, и предрасчитанный кеш `0.2.0`
на стенде больше не подойдёт — нужен новый прогон (6–7 часов на GPU).

### Уверенность в доказательстве — своя, а не средняя по странице

`EvidenceFragment.confidence` раньше заполнялся полем `ocr_confidence` страницы, то есть **средней
уверенностью по всем распознанным строкам листа**. Это вводит в заблуждение: на странице, где всё
распознано чисто, а нужное число — на 0.45, инспектор увидел бы 0.88 и доверял бы значению больше,
чем следует. Для надзорной задачи это прямой вред.

Теперь `extract/api.py` берёт уверенность у блоков OCR, накрывающих рамку доказательства, и
выбирает **минимум**: ячейка таблицы склеивается из нескольких распознанных строк и не надёжнее
худшей из них. Если подходящих блоков нет — значение пришло из текстового слоя — остаётся прежнее
поведение, то есть `None`.

Блоки уже несут `confidence` в разобранном JSON, поэтому **разбор не менялся и `PARSER_VERSION`
поднимать не пришлось**: правка живёт на этапе извлечения и предрасчёт не затрагивает.

Проверено на настоящем акте ИД (`АОСР №3А-БСС`): у страницы средняя 0.8192, а у строки, из которой
взят класс бетона, — 0.9904.
### Ориентация строк отнимала половину текста страницы

PaddleOCR по умолчанию включает четвёртую модель — `PP-LCNet_x1_0_textline_ori`, классификатор
ориентации строки. Предполагается, что она находит строки, набранные вверх ногами, и разворачивает
их перед распознаванием. На наших сканах она делала обратное: разворачивала нормальные строки и
превращала их в мусор. Вместо

> ООО «АПСАЙД ИНЖИНИРИНГ», ОГРН 1167746504540, ИНН 7743157043

распознаватель выдавал `O`, `.`, `OOO`, `() п - o) )`.

Замер на трёх сканах, 12 страниц в 300 dpi, `use_textline_orientation` с ней → без неё:

| Документ | Строк | Символов | Средняя уверенность |
|---|---:|---:|---:|
| Акт ИД F0008 | 291 → 316 | 7655 → **12913** | 0.821 → 0.880 |
| Акт ИД F0014 | 232 → 266 | 7605 → **13074** | 0.822 → 0.921 |
| Скан-образец | 736 → 791 | 7161 → **9258** | 0.864 → 0.965 |

Текста распознаётся в полтора-два раза больше, и уверенность растёт на всех трёх документах —
то есть модель не «спорная», а вредная на нашем материале. Объяснение простое: страницы приходят
к нам уже повёрнутыми по `/Rotate` из PyMuPDF, разворачивать в них нечего, и классификатор
работает на шуме.

Попутно выключение даёт две вещи: подъём движка ускоряется с 5.1 с до 0.7 с, и из сборки уходит
зависимость от четвёртого файла весов.

**Это меняет результат разбора**, поэтому правка едет вместе с `PARSER_VERSION 0.3.0` и попадает
в общий пересчёт кеша перед заморозкой.

### Движок живёт столько же, сколько рабочий процесс

PaddleOCR поднимает веса при первом распознавании и держит их в экземпляре, а экземпляр
создавался на каждую задачу разбора — модель поднималась заново для каждого документа. Пул
процессов задачи переживает, поэтому `ocr.engines.build_engine` кеширует движок по его
параметрам (`lru_cache`), и следующая задача получает прогретый.

Замер на двух настоящих актах ИД (`АОСР №3А-БСС`, `АОСР №10БЗ`, вместе 5 распознанных страниц):

| | Было | Стало |
|---|---:|---:|
| Первый документ в процессе | 9.3 с | 4.1 с |
| Второй | 5.5 с | 4.4 с |
| **Итого** | **14.8 с** | **8.5 с** |

На второй задаче экономия меньше: веса уже в памяти операционной системы, но обёртку PaddleOCR
приходилось собирать заново.

**Кеш процессный.** При `ML_EXECUTOR=process` (умолчание) в каждом рабочем процессе своя копия
весов и одновременного доступа к движку не возникает. При `ML_EXECUTOR=thread` — режим тестов и
отладки — задачи делят процесс, и один движок зовут из нескольких потоков: создание модели
закрыто замком, но само распознавание PaddleOCR потокобезопасным не заявлено. Для боевого режима
это неважно, для отладочного — приемлемо.

### OCR на видеокарте: проверено и защищено от тихой подмены

Проверяющий стенд — H100 80 ГБ, и **нормативы производительности организаторы меряют в
GPU-конфигурации**. Значит GPU-вариант образа больше не запасной.

**Версии подтверждены на живой карте.** Установленная сборка `paddlepaddle-gpu==3.3.1` с индекса
`cu126` сообщает `CUDA 12.6`, `cuDNN 9.5.1` и список архитектур
`paddle.version.cuda_archs = [61, 70, 75, 80, 86, 89, 90]`. **SM90 — это Hopper, то есть H100**,
он в сборке есть; база образа `nvidia/cuda:12.6.3-cudnn-runtime-ubuntu24.04` ей соответствует.

**Предел видеопамяти работает.** `FLAGS_gpu_memory_limit_mb` — верное имя флага: paddle его
читает (`paddle.get_flags`). Поставил 512 МБ на карте с 4 ГБ — распознавание отработало, пик
памяти под тензоры 69 МБ. То есть 20 ГБ из `docker-compose.gpu.yml` распознаванию не мешают
с огромным запасом; настоящим потребителем станет языковая модель, и бюджет стоит выбирать
под неё, а не под OCR.

**Тихая подмена устройства закрыта.** Запасные наборы параметров в `PaddleEngine._build`
намеренно выбрасывают `device` — без этого старые сборки PaddleOCR не поднимались. Цена была
такая: при `OCR_DEVICE=gpu` первая же неудача уводила распознавание на процессор, и знали мы
об этом только из записи уровня `debug`. Страница на процессоре стоит около минуты против
секунды на карте — на проверяющем стенде это проваленный норматив без признаков в логе.

Теперь после инициализации устройство определяется и пишется в `paddle_ready` уровнем `info`,
а явный `gpu`, оказавшийся на процессоре, — ошибка. Проверено на живой карте:

| Настройка | Карта | Что происходит |
|---|---|---|
| `OCR_DEVICE=gpu` | видна | `paddle_ready device=gpu:0 requested=gpu` |
| `OCR_DEVICE=gpu` | скрыта | понятная ошибка вместо молчаливого процессора |
| `OCR_DEVICE=auto` | скрыта | уходит на процессор и **пишет об этом** `device=cpu` |

**В `GET /health` добавлена возможность `ocr_gpu`** — видно ли распознаванию карту прямо сейчас.
Это позволяет проверить стенд до первой задачи, не разбирая документ. Модель при этом
не поднимается: смотрим только сборку paddle и число видимых карт.

**Образ прогнан на живой карте.** Docker поставлен, проброс карты работает.
Проверено **изнутри контейнера**, запущенного с `--gpus all`:

| Что | Результат |
|---|---|
| Сборка paddle в образе | `paddle 3.3.1, CUDA 12.6, cuDNN 9.5.1` |
| Карта видна контейнеру | `NVIDIA GeForce RTX 3050 Laptop GPU, SM86` |
| `capabilities` из `/health` | `ocr: true`, **`ocr_gpu: true`** |
| Устройство после инициализации | `paddle_ready requested=gpu device=gpu:0` |
| Разбор настоящего скана акта ИД | 8 страниц, 2 распознаны, 181 блок, 4 таблицы |
| Скорость распознавания | **2.4 с на страницу** |

Для сравнения: тот же акт в том же образе, но на процессоре — **34.3 с на страницу**. Разница
в четырнадцать раз, и именно она стоит за решением мерить нормативы в GPU-конфигурации.

Защита от тихой подмены сработала как задумано: при явном `OCR_DEVICE=gpu` движок поднялся
на `gpu:0` и записал это уровнем `info`. Окажись он на процессоре — была бы ошибка, а не молчание.

**Оговорка про способ проверки.** Шаг `uv pip install paddlepaddle-gpu` в самом `docker build`
у меня не проходит: официальный индекс `www.paddlepaddle.org.cn` с этой машины недоступен
(таймаут подключения, одинаково из WSL и из контейнера). Поэтому колесо поставлено в контейнер
из кеша `uv` — сборка paddle та же самая, но собрать образ целиком одной командой локально
нельзя. В CI этот шаг проходит, образ там собирается штатно.

**Прогрев весов в образе зависит от того, какой хостер ответит первым.** PaddleOCR подбирает
источник моделей сам: HuggingFace → AIStudio → ModelScope → BOS, берёт первый, ответивший
на HEAD-запрос **с таймаутом в одну секунду** (`_healthcheck_timeout = 1` в paddlex). Из
контейнера на моей машине HuggingFace отвечает за 4.8 с, то есть в секунду не укладывается,
и выбор падает на китайский `cdn-lfs-cn-1.modelscope.cn`, который отваливается по таймауту
и роняет сборку.

Проверил на том же образе: с `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True` прогрев идёт
с HuggingFace и укладывается в 7 секунд. В `infra/docker/ml-gpu.Dockerfile` эта переменная уже
есть, но задаётся **после** шага прогрева, поэтому на него не влияет.

### Страница с нечитаемым текстовым слоем уходит в распознавание

Встречается шрифт без дескриптора и без годного `ToUnicode`. PyMuPDF честно отдаёт текст, но
кириллица в нём превращается в кашу:

```
Ɉ5M5EF6> E >7D4=<G5==>= >F65FEF65==>EFLN   → Общество с ограниченной ответственностью
ɋɪɨɤɢ ɫɬɪɨɢɬɟɥɶɫɬɜɚ ɧɟ ɩɨɞɥɟɠɚɬ           → Сроки строительства не подлежат
```

Опасна такая страница тем, что **выглядит исправной**: символы есть, значит `chars > 0`,
классификатор ставит `OK`, распознавание не запускается, а извлечение работает по мусору
и молча ничего не находит.

На корпусе это **515 страниц из 17 344 с текстовым слоем (3.0%)** в 16 документах:

| Где | Страниц |
|---|---:|
| `036-21-ИГИ-Т`, изыскания (ПД и РД) | 434 |
| **ПД / ИОС** — инженерные системы | **53** |
| ПД / АР, ПОС, ЭОМ, НВК, РД / КР | 24 |
| ИД / ПОД | 4 |

Строка про ИОС здесь важнее остальных: `АНО-150321-1-П-ИОС5.1.1` потерял 37 страниц из 41,
а ИОС4 — это отопление и вентиляция, раздел, в котором живут `FREE-HEATING-001` и шесть проверок
публичного эталона про приборы в помещениях.

**Как ловим.** Буквы из латиницы-расширенной и МФА (`Ɉ`, `Ȼ`, `ɟ`, `ɪ`), которых в наших
документах не бывает, **вместе с** долей кириллицы ниже половины. Оба условия обязательны:
по одной «экзотике» сработала бы страница с формулой, по одной доле — честный лист с латинскими
обозначениями. Проверка идёт по странице целиком, а не по блоку: на подписи к чертежу доля
ничего не значит, поэтому ниже 80 букв не судим вовсе.

**Чего не ловим:** текст, раскодированный целиком в латиницу и цифры, без «экзотики».
Ошибаемся в сторону «читается» намеренно: лишний OCR стоит минуту на страницу, а ложное
`LOW_QUALITY` выбросило бы годный текст.

Правка меняет разбор, поэтому `PARSER_VERSION` → `0.4.0` и повторный предрасчёт.

### Как мы измеряем качество OCR

Организаторы оценивают OCR по Accuracy, но размеченного эталона распознавания у нас
нет — их пилот на 300 страниц имеет статус SILVER (машинная предразметка, «ни одна строка не
проверена человеком»). Поэтому эталон берём из самих документов: **страницы с текстовым слоем
рендерятся и распознаются принудительно, а текстовый слой служит истиной**.

```bash
uv run inspector-ml eval ocr "<pdf из dataset>" --pages 5 --dpi 200
```

Считаем двумя способами:

- **по странице** (`page_character_accuracy`) — формула ТЗ как есть: 1 − Levenshtein / символов по
  тексту всей страницы. Эталон и распознавание перед сравнением выстраиваются одинаково — по рядам
  сверху вниз, в ряду слева направо, по рамкам строк (`in_rows`). Поэтому не важно, как движок нарезал
  строки и в каком порядке отдал блоки; важно, одинаково ли разложились ряды (таблицы, чертежи);
- **построчно** (`character_accuracy`): пары «строка эталона — распознанная строка» выбираются по всей
  странице сразу, от самых похожих (`fuzz.ratio`), непарные строки эталона идут в ошибки целиком. Не
  зависит от порядка, но штрафует нарезку: если OCR разбил строку эталона на два куска, второй — ошибки.

До 25.09 была только построчная, и с изъяном: строки эталона по очереди забирали самую похожую из
оставшихся по `WRatio`, а он ставит 90 за вхождение подстроки. Единица «м» уводила строку
«Мягкая защита стен…», и та оставалась без пары. Такая метрика поощряла повторы: лишние копии строк
из зон перекрытия плиток подставлялись вместо уведённых. На одной и той же выдаче OCR старая метрика
давала 0.61, исправленная — 0.747. WER теперь тоже считается по тексту в порядке рядов.

**Замеры на корпусе** (PaddleOCR mobile, 150 dpi, CPU этой машины, `enable_mkldnn=False`):

| Что | Character Accuracy | Покрытие | Уверенность | Секунд на страницу |
|---|---:|---:|---:|---:|
| Текстовый том ПД (вёрстка, таблицы) | **0.78** | 1.00 | 0.97 | 89 |
| Чертёж ПЗУ (генплан, мелкие выноски) | 0.28 | 0.66 | 0.88 | 36 |

На сканах исполнительной документации распознавание выглядит хорошо и по делу: со страницы акта
освидетельствования получаем 77 строк и 4093 символа со средней уверенностью **0.94**, включая
марку бетонной смеси «БСт В15П4F(I)150W6» и номера паспортов — ровно то, что нужно для M-055.

Чертежи распознаются заметно хуже (мелкий повёрнутый текст, выноски), но это не блокер:
в корпусе у чертежей почти всегда есть текстовый слой, а OCR нужен прежде всего сканам ИД.

**Важно для M-055:** OCR уверенно читает латинскую «B» в обозначении класса бетона как
кириллическую «В» — символы выглядят одинаково, и по контексту (русский текст вокруг) модель
выбирает кириллицу. Значит нормализация «В25 → B25» при извлечении обязательна не только для текстового
слоя, но и для распознанного текста. Тест `tests/test_ocr_engine.py` принимает оба алфавита
и фиксирует это поведение.

**Тесты OCR.** Обычный прогон идёт на фейковом движке — extra `ocr` для него не нужен.
Настоящий движок проверяется отдельным тестом (`ML_TEST_OCR=1 uv run pytest tests/test_ocr_engine.py`),
и для него нужен системный шрифт с кириллицей: встроенные шрифты PyMuPDF рисуют кириллицу
как пустоту, и распознавать в тесте оказалось нечего — из-за этого тест сначала падал.

**Производительность — узкое место.** 36—89 секунд на страницу означает, что сплошной OCR
всей исполнительной документации (8324 страницы у Речникова) нереален: это десятки часов.
Отсюда три решения: распознаём только страницы `LOW_QUALITY`, ограничиваем бюджет
`OCR_MAX_PAGES`, и в первую очередь смотрим страницы, относящиеся к активным параметрам.

**Где считать замеры.** На CPU это потолок, а вот на видеокарте разница принципиальная:

| Замер (одна и та же страница, 150 dpi) | Windows CPU | WSL CPU | WSL + GPU |
|---|---:|---:|---:|
| Страница скана акта (сырой вызов движка) | 83.5 с | 57.9 с | **1.2 с** |
| `inspector-ml eval ocr` целиком (рендер + OCR + метрика) | 88.9 с | 59.7 с | **3.0 с** |
| Тесты | 154 passed, 2 skipped | 154 passed, 2 skipped | 154 passed, 2 skipped |

**GPU ускоряет распознавание примерно в 50 раз**, и это меняет постановку: сплошной OCR
исполнительной документации Речникова (8324 страницы) на CPU занял бы почти неделю, а на одной
RTX 3050 — около трёх часов. Ради этого и стоит держать прогоны в Linux.

**Точность от устройства не зависит** — проверено прямым сравнением на одних и тех же страницах
и настройках: CPU 0.7518, GPU 0.7511 (разница — округление). Если числа Accuracy в разных
прогонах расходятся, дело всегда в одном из двух:

| Что меняли | Character Accuracy |
|---|---:|
| 2 страницы, `max_px=2000`, плитка 2000 | **0.7811** |
| те же 2 страницы, `max_px=4000`, плитка 1600 (умолчания) | 0.7511 |
| 4 страницы, `max_px=4000`, плитка 1600 | 0.6092 |

Первое — **параметры рендера и нарезки**: при уменьшении растра до 2000 пикселей и одной плитке
на страницу качество на 3 п.п. выше, чем при рендере до 4000 с нарезкой. Значит умолчания
`OCR_MAX_PX` и `OCR_TILE_PX` стоит подбирать так же, как подбирался порог классификатора.
Второе — **выборка страниц**: у четырёх страниц среднее ниже, потому что в них попала страница 85
с точностью 0.39 и наибольшим весом (5399 символов эталона). Сравнивать Accuracy можно только
при одинаковых страницах и одинаковых настройках рендера.

### Стыки плиток (`PARSER_VERSION 0.5.0`, 25.09)

Лист A4 при 300 dpi — 2480 × 3508 px, плитка 1600 с перекрытием 160: граница x = 1600 проходит
почти через каждую строку текста. Левая плитка видела «ограниченно», правая — «енной», рамки
пересекались только в полосе перекрытия, и склейка по IoU ≥ 0.4 оставляла обе половины. На выходе —
«ограниченно енной», «СТРОИТЕЛЬНО ЕЛЬНОГО», распознанного текста на 7 % больше эталона.

Теперь (`ocr/render.stitch`):

1. строка, срезанная верхним или нижним краем плитки, уступает целой копии из соседнего ряда плиток:
   полоса перекрытия (160 px) выше строки текста, и там строка видна целиком;
2. строки, разрезанные вертикальной границей, сшиваются: общий кусок ищется в хвосте левой половины
   и в начале правой (столько символов, сколько помещается в пересечение рамок), шов — его середина;
   если общего текста нет — середина пересечения рамок по оценке ширины символа. Строка через три
   плитки сшивается по цепочке. Кусок, целиком лежащий под рамкой соседа, уступает ему; соседние
   ячейки, рамки которых не заходят друг на друга, не трогаются;
3. остальные повторы (строка целиком в полосе перекрытия) — по IoU, как раньше;
4. строки выдаются **по рядам**: раньше сортировка по точному верхнему краю ставила «с ограниченной»
   (верх 99.8 px) перед «Общество» (100.3 px).

**Замер** (60 постоянных страниц `eval cv --ocr-pages 60`, GPU, 300 dpi, метрика с исправленным
сопоставлением строк):

| Вариант | Построчно | По странице | Текст / чертежи (по странице) | WER | с/стр |
|---|---:|---:|---|---:|---:|
| `0.4.0`: плитки 1600, склейка по IoU | 0.747 | 0.812 | 0.818 / 0.785 | 0.71 | 2.12 |
| **`0.5.0`: плитки 1600, сшивка стыков** | **0.817** | **0.880** | **0.896 / 0.812** | **0.60** | 2.05 |
| страница целиком, 4000 px | 0.828 | 0.885 | 0.900 / 0.819 | 0.57 | 1.81 |
| страница целиком, 2000 px | 0.900 | 0.876 | 0.904 / 0.757 | 0.56 | 1.28 |

Улучшение и на тексте, и на чертежах; по странице просела одна страница из 60, на 0.01 (F0112 стр. 2).

**Почему не «страница целиком»**, хотя она не хуже и быстрее: на процессоре она вдвое тяжелее по
памяти — **3.6 ГБ против 1.8 ГБ** на рабочий процесс (одна страница A4, `OCR_DEVICE=cpu`), а на стенде
у всего Docker 5.75 ГБ. Настройки распознавания обязаны быть одинаковыми в предрасчёте и на стенде:
ключ кеша — только `sha256 + PARSER_VERSION`, поэтому отдельного значения `OCR_TILE_PX` для GPU нет.

**Построчная метрика любит 2000 px** (0.900) не за распознавание: при меньшем растре детектор чаще
собирает строку целиком, как в текстовом слое, а построчное сравнение штрафует нарезку. По странице
2000 px не лучше 4000 на тексте и заметно хуже на чертежах.

Что осталось ниже порога ТЗ 0.95: четыре страницы, где текстовый слой неполный (часть текста — картинкой,
распознано в 2–12 раз больше слоя, по странице 0), две страницы одного тома F0112 (распознаётся меньше
половины слоя) и порядок рядов в таблицах и на чертежах.

Как поднять окружение в WSL — [services/ml/README.md](../../services/ml/README.md#замеры-и-прогоны-в-wsl).
Главное: окружение создаётся **вне репозитория** (`UV_PROJECT_ENVIRONMENT=~/.venvs/inspector-ml`),
иначе `uv sync` затрёт windows-venv в `services/ml/.venv`. Выбор устройства — `OCR_DEVICE`
(`auto` по умолчанию: с `paddlepaddle-gpu` движок сам возьмёт видеокарту).

## DOCX и XML (REQ-UPL-02)

api принимает PDF, DOCX и XML с первой загрузки, а разбирались до 26.09 только PDF: на DOCX и XML задача разбора
отвечала `UNSUPPORTED_FORMAT`, и файл оставался в комплекте без значений. Теперь все три формата дают
один и тот же `ParsedDocument` — дальше извлечение, сравнение и гипотезы не знают, из чего страница.

**Условные страницы** ([`ingest/flow.py`](../../services/ml/src/inspector_ml/ingest/flow.py)). У DOCX и
XML нет геометрии: Word раскладывает текст сам при печати, у XML страниц нет вовсе. А извлечению нужны
блоки для шаблонов матрицы и ячейки таблиц для якорей (`extract/tables.named_row` собирает строку по
высоте ячеек). Поэтому поток абзацев и таблиц раскладывается по страницам A4 в порядке документа: абзац —
блок на своей высоте (длинный — на несколько строк), строка таблицы — ячейки на одной высоте с колонками
равной ширины **и** ещё блок текста строки («Площадь застройки м² 4 200,0»), чтобы значение находили и
шаблоны, и якоря. 50 строк на страницу, не поместившаяся таблица продолжается на следующей своей
таблицей. `source` страницы — `DOCX` или `XML` (`TextSource` контракта), `quality` — `OK`, распознавания
нет. Доказательство указывает на такую страницу и фрагмент текста — другого места у этих форматов нет.

**DOCX** ([`ingest/docx.py`](../../services/ml/src/inspector_ml/ingest/docx.py)) читается стандартной
библиотекой (`zipfile` + `ElementTree`), без новых зависимостей в образе:

- абзацы — текст прогонов `w:t`; табуляция и перенос — пробел; явный разрыв страницы и «с новой
  страницы» — новая условная страница;
- таблицы — объединённые по горизонтали ячейки (`w:gridSpan`) занимают свои колонки, поэтому колонка
  значения ТЭП одна и та же во всех строках;
- элементы управления содержимым (`w:sdt`: титульный лист, оглавление) — как обычный текст;
- колонтитулы — блоками `title_block` на первую страницу: в них штамп с шифром и стадией, по ним
  классификатор определяет стадию и марку так же, как по штампу PDF;
- не берутся сноски, примечания, надписи в фигурах, встроенные чертежи.

**XML** ([`ingest/xmldoc.py`](../../services/ml/src/inspector_ml/ingest/xmldoc.py)) разбирается без
знания схемы: каждый атрибут и листовой элемент — строка «имя | значение»; если у родителя рядом
наименование и значение (`<Наименование>Площадь застройки</Наименование><Значение>4200,0 м²</Значение>`),
они собираются в одну строку — тогда показатель находится по якорям матрицы. Внешние сущности
`ElementTree` не загружает (проверено тестом), «миллиард смеха» останавливает expat.

**Метаданные.** Свойства PDF (`pdf_version`, `pdf_producer`, `pdf_creator`, `encrypted`) у DOCX и XML
пустые: PDF узнаётся по сигнатуре `%PDF-` в первом килобайте, потому что в хранилище файл лежит без
расширения. Размер, язык и доля скана (0) считаются как у PDF.

**`PARSER_VERSION` не поднимался.** Разбор PDF не изменился, а DOCX и XML раньше в кеш не попадали
(ответ `UNSUPPORTED_FORMAT` не кешируется), так что кеш 0.5.0 на стенде остаётся верным.

**Что видит инспектор.** Просмотрщик интерфейса рисует PDF; для доказательства из DOCX или XML страницы
на экране нет; интерфейс должен показать фрагмент текста.

Тесты — [`tests/test_docx_xml.py`](../../services/ml/tests/test_docx_xml.py): файлы собираются в тесте
из строк XML, проверены страницы, объединённые ячейки, штамп в колонтитуле, `w:sdt`, извлечение M-001
из ТЭП в Word и в XML и M-016 своим извлекателем, битые файлы, внешние сущности и задача разбора целиком.

## Извлечение параметров

Извлечение отвечает на вопрос движка сравнения: «какие значения параметра есть в этих документах
и где именно они лежат». Вход — разобранный JSON, выход — `Extraction` с `rule_key`,
нормализованным значением и `EvidenceFragment` (файл, страница, bbox, цитата).

### Таблицы собираются из слов, а не из блоков

Значения живут в таблицах: ТЭП в пояснительной записке, экспликации помещений на листах АР,
спецификации материалов в КЖ. Блоки PyMuPDF для них не годятся — один блок склеивает несколько
строк («-3.1 Автостоянка 840,7 / -3.2 Тамбур-шлюз 4,9 …») и теряет координаты ячейки, а именно
ячейка нужна как доказательство.

Поэтому [`layout/rows.py`](../../services/ml/src/inspector_ml/layout/rows.py) собирает строки из
слов (`get_text("words")`): слова с перекрывающимися вертикальными отрезками — одна строка,
большой горизонтальный зазор — граница ячейки. Дальше **таблица ищется от колонок, а не от
строк**: строка на листе САПР идёт через весь лист и собирает и ячейки экспликации, и подписи
чертежа, а между строками таблицы вклинивается строка с размерами. Колонка же видна сразу —
полтора десятка ячеек с общим левым краем и ровным шагом. Соседние колонки связываются по
**построчному** совпадению ячеек: у подписей чертежа его нет.

`page.find_tables()` как основной путь не используется. Проверены все способы его ускорения из
документации и issues PyMuPDF, замеры — на PyMuPDF **1.28.2** (последняя версия, где разработчики
как раз оптимизировали `find_tables()`; на более старой мерить смысла нет):

| Вариант | Лист АР A1, экспликация | Строк экспликации | Лист КЖ A0 | ТЭП A4 |
|---|---:|---:|---:|---:|
| `find_tables()` по умолчанию | 2 735 мс | **6 из 16** | 2 135 мс | 219 мс |
| `horizontal/vertical_strategy="lines"` | 2 735 мс | 6 из 16 | 2 260 мс | 208 мс |
| `snap_tolerance=5, join_tolerance=5` | 2 508 мс | **0 из 16** | 2 270 мс | 209 мс |
| `find_tables(clip=…)` по якорю | 1 534 мс | **16 из 16** | 144 мс | — |
| **сборка по словам** | **60 мс** | **16 из 16** | **117 мс** | **12 мс** |

Что из этого следует:

- **стратегии и допуски не помогают.** `lines` даёт тот же результат (на листах САПР разлиновка
  и так есть, алгоритм её и без того видит), а загрубление `snap`/`join` качество **портит** —
  строки экспликации склеиваются полностью;
- **`clip` помогает по-настоящему** — и по времени (в 1.8 раза), и по качеству: без него
  `find_tables()` принимает линии чертежа за разлиновку и отдаёт одну «таблицу» на весь лист,
  где строки экспликации склеены. Но `clip` нужно откуда-то взять — то есть сначала всё равно
  надо найти таблицу, а это и есть исходная задача. Единственный доступный якорь — заголовок
  («Экспликация помещений …»), и он появляется только на этапе извлечения;
- **при равной полноте разница в скорости — 25–30 раз.** На четырёх листах экспликаций
  (F0104 стр. 22–24, F0103 стр. 19) оба способа дают одни и те же **61** строку помещений:
  `find_tables(clip=…)` за 13.9 с, сборка по словам — за 0.46 с. Ни один из них не является
  надмножеством другого: на листе АТЗ мы находим «1.2» и «1.3», которых нет у `find_tables()`,
  и не находим «1.9» и «1.10», которые есть у него.

Поэтому основной путь — сборка по словам: она даёт то же качество, работает одинаково на A4 и A0,
не требует знать положение таблицы заранее и укладывается в бюджет разбора. `find_tables(clip=…)`
остаётся кандидатом на точечное уточнение уже найденных областей, если понадобится (вместе
со сравнением с Docling).

### M-002 «Общая площадь здания»

Три вида атомарных точек:

- `Общая площадь здания` — строка ТЭП. Наименования в документах разные («Площадь жилого здания»
  в ПД Новослободской), поэтому строка ищется по списку синонимов, а значение берётся как
  **самая правая** числовая ячейка строки: левее стоят колонка «по ГПЗУ» (часто прочерк) и
  единицы измерения.
- `Экспликация помещений <N>-го этажа` — итог по этажу, последняя сумма под таблицей.
- `пом. <номер>` и `пом. <номер> (назначение)` — **две** точки на строку экспликации:
  в пилоте ALT79B-V01 нарушением было и изменение площади, и подмена назначения
  помещения.

Три проверки отсекают ложные экспликации на листах планировок, где рядом с планом стоят
поквартирные таблицы:

1. **номер помещения — только полный**: «-3.1», «1.09» или сквозной «012». Поквартирные
   экспликации нумеруют помещения с единицы внутри каждой квартиры, и «пом. 1» встречается на
   листе десятки раз, означая разное. Обе разметки организаторов (ALT79B «1.09» и Тюменская
   «012») используют полные номера;
2. **этаж в номере совпадает с этажом в заголовке** экспликации;
3. **площадь записана с десятой долей** («840,7»): целые числа в той же колонке — это размеры в
   миллиметрах с плана.

Без них на 48-страничном ПД АР находилось 1593 «значения», из которых верными были 93.

**Синонимы наименования — из матрицы, а не из кода.** `semantic_anchors` параметра приходят в
`CompareRequest.matrix`, и своей копии списка в ML нет: матрицу правят без релиза сервиса, а две
копии разошлись бы молча. Для
M-002 там лежат и «площадь жилого здания», и «общая площадь объекта», и «площадь здания».
Команды без api (`eval`) читают тот же `data/matrix/params.csv`, из которого матрицу загружает
api — [`matrix.py`](../../services/ml/src/inspector_ml/matrix.py), флаг `--matrix` меняет путь.

Одна тонкость: в `semantic_anchors` M-002 лежат якоря **двух** видов точек — наименования строки
ТЭП и приметы экспликации («Экспликация помещений», «Итого по этажу»). В строку ТЭП вторые не
идут: их обслуживает своя ветка (заголовок ищется регуляркой, итог этажа — по положению под
таблицей), а иначе итог этажа уехал бы вторым значением в точку «Общая площадь здания» и на
каждом листе экспликаций появлялась бы лишняя контрольная точка с чужим значением.

### M-055 «Класс прочности бетона»

Марку находит регулярка матрицы; сложность в том, **к чему** она относится. В комплекте
Новослободской это написано пятью способами, и все пять разбираются:

| Где | Как выглядит | Откуда берётся конструкция |
|---|---|---|
| Общие данные ПД (КР2, стр. 49) | `· фундаментная плита  B40` | своя строка, ячейка левее |
| Спецификация материалов РД (КЖ1.1.1, стр. 27) | `ГОСТ 26633-2015 ┃ B40,F150,W6, м3 ┃ 1520` | заголовок спецификации над таблицей |
| Сплошной текст ПД (КР1, стр. 17) | «монолитной ж/б «стены в грунте» (бетон класса В25 …)» | то же предложение, косвенный падеж |
| Общие указания РД (КЖ1.1.2, стр. 4) | «Класс бетона … для стен В60» | та же строка |
| Акт освидетельствования ИД (стр. 2 и 5) | «Устройство стены в грунте» … «партии БСТ В25» | шапка акта, до 4 страниц назад — **только в документе с шапкой «АКТ освидетельствования»** |

Марка, у которой конструкцию узнать не удалось, **не выдаётся**: с пустым `rule_key` движок
сравнения сложил бы разные элементы в одну контрольную точку и выдал ложное расхождение.

Наименование конструкции сопоставляется **по формам слов** — без морфологического анализатора и
без внешних моделей (`lexicon.same_word`): общее начало не короче 4 букв, и оба остатка — падежные
окончания, включая нулевое. «Фундаментная плита» находит «фундаментной плиты» и «ж/б фундаментную
плиту», «ростверк» — «ростверка» и «ростверков», «лестницы» — «лестниц», а «стена»
со «стендом» и «плита» с «плиткой» не склеиваются.

Перенос конструкции на соседние страницы работает **только в актах**. В томах ПД и РД конструкция,
упомянутая где-то на странице, чужой марке не хозяйка: замер 25.09 на обучающих объектах нашёл там
21 документ ПД и 9 РД с такими привязками, почти сплошь ложными («…кроме фундаментной плиты
выполнены из бетона класса В60» → плита B60). Шапка «АКТ освидетельствования» ищется на каждой
странице, а не на первой: файл ИД бывает сшивкой актов по этажу с описью в начале. В ИД обучающей
части после ограничения остались все 34 документа. Аббревиатур («БСС», «СВГ») в словаре намеренно нет — они входят в шифры и номера актов, и
по ним конструкция определялась бы неверно.

Отдельное правило: у вертикальных конструкций класс меняется по высоте здания, и отрицательная
отметка уточняет точку до «Вертикальные конструкции **подземной части**» — ровно так её назвал
эксперт организаторов. Без уточнения B60, B50 и B40 сложились бы в одну точку, и проверка ушла бы
в «нужен выбор источника».

Это правило **наше**, а не из матрицы, и мы его оставили: обе
точки сразу — с уточнением и без — отдавать не будем, лишняя бьёт по precision, а F1 весит 60
баллов. Живёт правило в `_qualify`
([`extract/lexicon.py`](../../services/ml/src/inspector_ml/extract/lexicon.py)) вместе со
словарём наименований конструкций: наименование конструкции — это имя атомарной точки
(`rule_key`), поля для него в матрице нет. Если в скрытой части организаторы назовут точку
иначе, крутить надо там.

### M-058 «Толщина фундаментной плиты / ростверка» и M-009 «Абсолютная отметка 0.000»

Свои извлекатели с ключом точки: [`extract/foundation.py`](../../services/ml/src/inspector_ml/extract/foundation.py)
и [`extract/elevation.py`](../../services/ml/src/inspector_ml/extract/elevation.py). Шаблоны
матрицы для этих параметров не работают — у них свой разбор.

**M-058.** Ключ — конструкция («Фундаментная плита», «Ростверк», те же имена, что у M-055),
значение — толщина в мм. Пишут трояко: «Толщина фундаментной плиты … 1000мм и 1200мм»,
«Фундамент … в виде монолитной железобетонной плиты толщиной 1200 и 1500 мм», «фундаментная
плита, h=1200 мм». Толщина засчитывается, только если **ближайшая** названная конструкция — наша:
«под телом фундаментной плиты … бетонная подготовка толщиной 100 мм», «фундаментная плита
приямка, h=900», «H плиты 400мм» не проходят — каждая дала бы ложное уменьшение. **Одно значение
на конструкцию в документе — самая тонкая зона:** движок при разных значениях одной стадии просит
выбрать источник, а триггер матрицы — уменьшение толщины. Все толщины остаются в `raw_value`.

**M-009.** Ключ — «Отметка 0.000», значение — абсолютная отметка в метрах. Разбор идёт от
«абсолютной отметки» к числу за ней; относится ли она к нулю, решает фраза: в ней должна быть
названа отметка 0,000 или «отметка нуля», и между ними — никакой другой относительной отметки
(«котлован до отм. -9.950 (абс. отм. 150.000)»). Разные значения в одном документе не сводятся
к одному: в томе сноса у каждого здания свой ноль.

| Параметр | Документов на обучающих объектах | Эталон организаторов |
|---|---:|---|
| M-058 | 6 | KR-058: ПД 1000/1200, РД 1200/1500 → уменьшения нет, как в ответе |
| M-009 | 45, во всех трёх стадиях | PZ-009: 159,95 = 159,95, как в ответе |

### M-041 «Ширина эвакуационных выходов (дверей)»

[`extract/doors.py`](../../services/ml/src/inspector_ml/extract/doors.py). Точка одна —
«Эвакуационный выход», значение — **наименьшая** ширина в документе, в метрах (триггер — предел
«< 0.9 м в РД/ИД», и отвечает за него самая узкая дверь); все ширины — в `raw_value`: «0,9 м; 1,3 м».

Два источника:

1. **Спецификация заполнения проёмов** (источник РД по матрице): строки «Д-6 … противопожарная …
   2100 | 1300», размеры в миллиметрах. Шапку детектор склеивает в «Высота Ширина Масса», поэтому
   ширина — второе из двух чисел-размеров, если «высота» в шапке раньше «ширины». Наименование и
   заголовки разделов («Витражные двери») часто остаются текстовыми блоками — они берутся по
   высоте строки и ближайшему заголовку выше. **Строка засчитывается, только если она про дверь
   на пути эвакуации** — наружную, входную, витражную, противопожарную: дверь санузла 0.7 м дала
   бы ложное «< 0.9».
2. **Текст записки и ПБ**: «ширина выходов из подземной автостоянки в лестничные клетки принята 1,0 м».
   Нужны и слова про ширину выхода или двери, и путь эвакуации рядом. Отсекаются: лифт («кабина
   лифта … шириной дверного проёма 800 мм»), вентиляция («гибкая вставка 900 х 900 мм … выход»),
   марши и площадки, цитаты СП («должна быть не менее 1,2 м»), расчётная «требуемая» ширина —
   если в предложении есть «фактическая ширина», берётся она. Единицы приводятся к метрам (мм, см).

**Замер 25.09, обучающие объекты:** документов со значением — ПД 10, РД 2 (было ПД 4, РД 0,
общей регуляркой матрицы); ложного «800 м» от кабины лифта больше нет. В РД — две
спецификации АР: витражные двери 2,0 м и противопожарные 0,9–1,3 м. Марки дверей вида «ДПС 21-10»
(высота и ширина в дециметрах) не берутся: без признака пути эвакуации они потащили бы и внутренние
двери.

### M-003 «Полезная / Расчётная площадь»

[`extract/useful_area.py`](../../services/ml/src/inspector_ml/extract/useful_area.py). Общая регулярка
матрицы брала любое «расчётная / полезная площадь … число», и на обучающих объектах больше половины
значений были чужими: удельные «на 1 место» и «на 1-го учащегося», «минимальная расчётная площадь —
45 м²» спринклерной секции, «расчётная площадь розлива 0,25 м²» (ТХ), «F — полезная площадь склада»
из формулы, «расчётные площадки» моделирования рассеивания (ООС) и цифра 2 из «м2» вместо 8 526,1.

Теперь: строка ТЭП (таблица) важнее текста — если она есть в документе, текст не смотрим; в названии
показателя и рядом с числом нет ничего из этого списка; число — после слов, а не цифра единицы;
не меньше 100 м². **Замер 25.09, обучающие объекты:** было 18 значений в 8 документах, стало 7 в 4
(ПД 2, РД 2) — все из строк ТЭП: «Расчётная площадь здания — 8010,1», «Расчетная площадь — 8 526,1».
Оговорка: «расчётная площадь» раздела энергоэффективности (5559,7 м²) — площадь по методике
энергопаспорта, и с ТЭП пояснительной записки она может законно не совпадать.

**M-001 «Площадь застройки»** своего извлекателя не получил: общий путь на обучающих объектах находит
его в 9 документах ПД и 2 РД, и значения верные (1225,8; 3009,4; 4650,91 м²). Сомнительны два:
«54,7» — похоже, колонка «%» в ТЭП ПЗУ (самая правая числовая ячейка), и «31» — застройка
вспомогательного сооружения. Отдельный разбор колонок ТЭП — если это станет давать кандидатов.

### M-016 «Суточный расход водопотребления» и M-074 «Диаметры выпусков К1/К2»

Повод — пара ИОС3.2 со стенда (26.09): в РД поменяли суточный расход, а протокол вышел пустым.
Регулярки обоих параметров — дословные названия, и **на обучающих объектах они не находили ни одного
значения**: в документах так не пишут.

**M-016** — [`extract/water_flow.py`](../../services/ml/src/inspector_ml/extract/water_flow.py).
Суточный расход живёт в тексте записки («Q = 123,576м3/сут.», «общее водопотребление: 53,22 м3/сут»)
и в таблице расходов ВК / ИОС2 (шапка «м³/сут | м³/ч | л/с», строка «Хозяйственно-питьевой водопровод,
В1 | 0,30 | 9,16 | …»). В таблице число берётся из колонки под шапкой «м³/сут», подпись строки — только
левее этой колонки (правее бывают примечания к листу).

Контрольных точек три, по системе из подписи или текста перед числом: «Водопотребление» (В1, ХВС),
«Горячее водоснабжение» (Т3, ГВС), «Водоотведение» (К1, канализация, стоки). Внутри документа по
каждой берётся наибольшее значение — итог баланса, а не «в т.ч.». Отсекаются:

- нагрузка и отбор по техническим условиям («подключаемой нагрузки … 107,5 куб.м/сут»);
- пожаротушение, полив, технологические нужды, дренаж;
- доли потребителей («в т.ч. столовая: …»);
- пустые бланки;
- страницы про период строительства (водопонижение, приток в котлован, бытовой городок).

**M-074** — [`extract/sewer_outlets.py`](../../services/ml/src/inspector_ml/extract/sewer_outlets.py).
Диаметр выпуска записан подписью на плане или схеме: «Выпуск К1 Ø110», «Выпуск 1-К1 ∅160 в футл.»,
«Выпуск бытовой / канализации К1-1 Ф100». Реже — фразой записки: «три выпуска … Д100 с системы К1»,
«выпусков хозяйственно-бытовой канализации … Ø100мм».

Точка — «Выпуск К1-1» (номер «1-К1» и «К1-1» сводится к одному), без номера — «Выпуски К1» / «Выпуски К2».
Значение — наибольший диаметр точки: триггер матрицы — уменьшение диаметра выпуска в РД. Все
диаметры остаются в `raw_value`. Отсекаются футляры и гильзы («в стальном футляре Ø325х7мм»),
стояки («Ст К2-6»), строки спецификации без слова «выпуск», системы К3/К4 и серии чертежей.
Строка таблицы чертежа — склейка подписей со всего листа, поэтому она делится по каждому «Выпуск»
и берётся, только если выпуск не подписан отдельным текстом.

**Замер 26.09, обучающие объекты, кеш 0.5.0:**

| Параметр | Было (регулярка матрицы) | Стало |
|---|---|---|
| M-016 | 0 значений | 13 значений в 8 документах (ПД 4, РД 4) |
| M-074 | 0 значений | 53 значения в 9 документах (ПД 6, РД 3) |

Ложных значений в выдаче нет. Пара ИОС3.2 со стенда: M-016 даёт ПД 123,576 и РД 125,576 м³/сут, то
есть расхождение по матрице. M-074 — Ø100 в обеих стадиях, расхождения нет, и это верно.

Попутная находка: в объекте П-2025-04.266 горячая вода — 0,53 м³/сут в ИОС2.1 и 0,52 в ВК2 РД.

Оговорка по разделу: M-016 в матрице отнесён к ПЗ, и движок сначала ищет его в ПЗ/ОПЗ стадии. Если
ПЗ в комплекте нет, он ищет во всех документах стадии — как на стенде. Баланс водопотребления
чаще лежит в ИОС2/ИОС3/ВК.

### Что считается значением в ячейке

Значением строки бралась **самая правая ячейка, в которой нашлось число**. Ревью предупреждало,
что на многоколоночных таблицах это будет ошибаться, и оказалось право — но по другой причине,
чем предполагалось. Дело не в выборе колонки: `number` находит число почти в любой ячейке.

| Ячейка | `number` видит | Что это на самом деле |
|---|---:|---|
| `м2` | 2 | единица измерения |
| `не более 30 000` | 30 000 | норматив ГПЗУ, а не показатель проекта |
| `26.03.23` | 26.03 | дата |
| `Экспликация помещений 1 этажа` | 1 | заголовок таблицы |

В строке ТЭП такие ячейки стоят рядом с показателем, и самая правая из них выигрывала: **площадь
застройки превращалась в норматив «не более 7000»**.

Правило теперь одно и простое — `normalize.only_number`: **ячейка-значение это число и, возможно,
единица измерения; если есть что-то ещё, это не значение**. Отдельно отбрасываются даты: они
проходят как числа и по форме, и по остатку.

**Замер по корпусу** (строки, где якорь матрицы совпал и в строке нашлось число):

| | Было | Стало |
|---|---:|---:|
| Таких строк | 91 | 33 |
| Из них неоднозначных | 47 (52 %) | **7 (21 %)** |

Падение общего числа — это и есть убранные ложные значения. Оставшиеся неоднозначности в основном
безобидны: одно и то же число продублировано в соседних колонках.

**Где мы теперь молчим.** Если в строке остались только единица и норматив, значение не выдаётся
вовсе — раньше выдавался норматив. Настоящий показатель в таких строках лежит в колонке, которую
мы не видим, и честнее воздержаться. Полное решение — декларативная привязка к заголовку столбца
(`row_anchors` / `value_header` в матрице), это уже изменение матрицы.

Сверка с эталоном организаторов после правки — прежние **7 из 7** по ключу, значению и странице.

### Ведущий ноль — не величина

На живом прогоне пилота «Общая площадь здания» извлеклась как **2.22 м²** при уверенности 0.998.
Источник — строка `Общая площадь помещений — 02.22` на **распознанном плане**: там сотни обрывков
размеров, и строка показателя подхватила первый попавшийся.

Поэтому `only_number` отвергает число с ведущим нулём перед второй цифрой: `02.22`, `007`, `01,5`.
Величину так не пишут — так выглядят месяц с годом, индекс, номер по порядку или код. Ноль перед
запятой при этом остаётся значением: `0,45` — обычная запись величины меньше единицы.

Проверено по всему корпусу, **1 690 137 ячеек таблиц**. Значение теряют 22 434 ячейки, и среди
самых частых нет ни одной измеренной величины:

| Что отсеклось | Ячеек |
|---|---:|
| `08.25`, `09.22`, `07.22`, `03.23` — месяц с годом | ~1400 |
| `08.04.2025`, `09.02.2022` — даты | ~600 |
| `0089`, `0001`, `0057`, `0330` — индексы и коды | ~700 |
| `00`, `000`, `01`, `08` — нумерация листов | ~600 |
| `POCC RU…PA02.B.13158/21` — номер сертификата | 102 |

На той же строке пилота теперь берётся **2796.0** — значение, согласованное с остальными
документами комплекта (2789.1, 2797.1, 2579.6).

**Разбор это не меняет:** правило живёт на этапе извлечения, `PARSER_VERSION` поднимать не нужно
и предрасчёт не затрагивается.

### Экспликации теряются на многоблочных листах — известный дефект

Из 130 страниц пилота с заголовком «Экспликация помещений» разбираются **4**. Это и есть причина,
по которой на живом прогоне 61 проверка из 67 ушла в `NOT_COMPARABLE`: сравнивать почти нечего.

Причина не в разном написании номеров. **Экспликация на листе САПР разложена в два-три блока
рядом**, продолжая нумерацию:

```
row 4:  col1='1' 'Тамбур'        col2='15.6'   │  col3='11' 'Зона мойки'      col4='107.8'
row 5:  col1='2' 'Торговый зал'  col2='742.0'  │  col3='12' 'Сервисная зона'  col4='1290.2'
```

`_rooms` подбирает к колонке номеров любую колонку площадей правее и оставляет пару, где строк
больше. Получается номер из первого блока и площадь из второго: у «пом. 1.1» в двух документах
одного объекта выходили разные площади — 107.8 и 1290.2, причём 1290.2 принадлежит помещению 12.

Отсюда же и «наименование тянет числа из соседних строк»: в поле наименования лежит площадь
соседнего блока.

Есть и второй слой: экспликации на листах АР нумеруют помещения подряд — 1, 2, 3, — а такие
номера `ROOM_NUMBER` отвергает намеренно (на поквартирных планах «пом. 1» бессмыслен). Под
заголовком с этажом номер однозначен и должен дописываться этажом: «7» → «1.7». Этаж назван
в **65 %** заголовков пилота и в **99 %** заголовков пакета участникам.

**Прототип правки сделан и откачен 22.09.** По счётчикам выигрыш крупный — 4 страницы → 62,
70 точек → 2012, общих ключей ПД ↔ РД 0 → 24. Но на части листов номер по-прежнему брался
из одного блока, а площадь из другого: полосы строк слипаются между блоками. Влить это значило бы
добавить в протокол около 480 строк, часть из которых неверна, — инспектор увидел бы десятки
«площадь изменилась» там, где изменился только блок, из которого прочитано число.

**Что нужно для настоящей починки:** делить многоблочную экспликацию по геометрии (тройки
«№ — наименование — площадь» повторяются с постоянным шагом по X), а не подбирать колонки
перебором. И разметка на десяток листов, чтобы мерить числом, а не глазами.

Цена вопроса: **11 проверок публичного эталона из 15 — про помещения**.

### Нормализация

`В25` (кириллица) → `B25`, `17 140,2` → `17140.2`, `кв. м` → `м²`. Кириллица в марках — не
мелочь: на одной странице ПД (КР2, стр. 49) рядом стоят `фундаментная плита B40` латиницей и
`пилоны, колонны, стены В60` кириллицей, а OCR на русском тексте почти всегда выбирает
кириллическую «В» (грабли 5). Без приведения `B40` из РД и `В40` из ПД — разные строки.

Мягкий перенос `U+00AD` приводится к обычному дефису: в тексте PDF он стоит на месте настоящего
дефиса («1-го этажа», «Тамбур-шлюз»), и без этого ни этаж из заголовка, ни номер помещения не
разбирались.

### Что показывает сверка с эталоном

```bash
uv run inspector-ml eval extract <путь к dataset/>
```

Команда проходит публичную разметку TRAIN (`data/samples/public_gold_checks.jsonl`) и проверяет
три вещи: нашли ли точку, совпало ли значение и попали ли **в ту же страницу**, что эксперт
(локализация «файл + страница» весит 15 баллов из 100 в оценке организаторов).

| Параметр | Точек эталона | Ключ | Значение | Страница |
|---|---:|---:|---:|---:|
| **M-055** (`KR-055`) | 7 | **7 / 7** | **7 / 7** | **7 / 7** |
| M-002 (`PZ-002`) | 0 | — | — | — |

Семь точек — это три атомарные проверки KR-055 со всеми ссылками на доказательства: «Стена в
грунте» B25 (ПД F0105 стр. 17 → РД F0137 стр. 1 → ИД F0004 стр. 5), «Фундаментная плита» B40
(ПД F0106 стр. 49 → РД F0140 стр. 27) и «Вертикальные конструкции подземной части» B60
(ПД F0106 стр. 49 → РД F0141 стр. 4).

**M-002 в публичном эталоне не размечен** — ни одной проверки с кодом `PZ-002` там нет, поэтому
цифры по нему привести не из чего. Проверено вручную на Новослободской: ТЭП ПЗ (F0101, стр. 9)
даёт 17 140,2 м², экспликации АР (F0104, стр. 22–24) — 93 значения по трём подземным этажам, АТЗ
(F0103, стр. 19) — экспликацию первого этажа.

## Пары листов

Инспектору нужно видеть два листа рядом: «вот этот план в проектной, а вот он же в рабочей».
`cv/pairing.py` решает, какой лист какому соответствует; наложение и поиск различий — `cv/sheetdiff.py`.

Движок принимает пары отдельным списком и сам проставляет `CheckResult.page_pair_key`
(`compare/pagepairs.py`) — от извлечения требуется только вернуть `page_pairs`.

### Почему по штампу пары не находятся

Первая версия сопоставляла листы по наименованию из графы 4 — и давала 20 пар на 6 799 листов
ПД. Причина не в метрике: **в графу 4 на разных стадиях пишут разное**.

- **ПД, раздел АР:** «План 4, 8 этажей на отм. +13.750 +27.950», «Фасад в осях 1/1 – 1/7».
  Пишут, **что изображено**.
- **РД, тот же раздел:** «Архитектурные решения надземной части. Планы Р 16», «Кровля Р 5».
  Пишут **раздел и номер листа**.

Сравнивать нечего. Нужен признак, который переживает переход от стадии к стадии.

### Отметка уровня как подпись изображённого

Такой признак на чертеже есть: **отметки уровня**. По СПДС их пишут в метрах с тремя знаками
после запятой и со знаком — `+13.750`, `-5.400`. План четвёртого этажа несёт свою отметку и в
проектной, и в рабочей документации, потому что это одно и то же место в здании.

Берутся они из уже разобранного JSON (`cv/fingerprint.py`), поэтому **растр не нужен и
`PARSER_VERSION` не меняется**: шесть с половиной часов предрасчёта переделывать не пришлось.

Ключевая деталь — **редкость отметки**. `+0.000` стоит на сотне листов и не различает ничего,
`+43.925` — на двух, и его совпадение почти доказывает пару. Поэтому вес отметки равен логарифму
обратной частоты по самому комплекту (та же идея, что IDF в поиске), а сходство листов — это
взвешенный коэффициент Жаккара. Обычный Жаккар тут обманывает: два листа с единственной общей
`+0.000` дали бы формальную единицу. Частая отметка получает вес около нуля сама собой, без
списков исключений.

Отдельный порог `MIN_SHARED_WEIGHT` отбрасывает слабые совпадения целиком — и он задан **в
весах, а не в количестве отметок**: две редкие доказывают больше, чем пять общеупотребительных.

### Правило графы 4

Наименование листа ПД не сопоставляется с наименованием РД, но само по себе оно — утверждение о
содержимом: «План 4, 8 этажей **на отм. +13.750 +27.950**». Из него работают два правила:

- **Возражение.** Если у листа-кандидата нет **ни одной** из названных отметок, изображено там
  другое место, и пара отменяется независимо от сходства текстов. Это правило сняло пару
  «ПД стр. 51 (отм. +10.200, +24.400) ↔ РД стр. 24», где общих отметок не было вовсе, а оценку
  набрал похожий текст чертежа.
- **Довод.** Если названная отметка у кандидата есть, к оценке идёт прибавка тем большая, чем
  реже эта отметка в комплекте.

Достаточно **одной** общей отметки: в ПД на листе рисуют несколько типовых этажей сразу
(«План 5, 9 этажей»), а в РД каждый этаж идёт своим листом, и совпасть может только часть.
Когда отметок у второго листа нет совсем — а на сканах их часто не видно, — правило молчит:
молчание не возражение.

### Как устроено целиком

1. **Отметки уровня** — главный признак, вес по редкости.
2. **Графа 4** — возражение и довод, см. выше.
3. **Наименование листа** из графы 4 (`layout.title_block.sheet_title`).
4. **Номер листа** — прибавка к оценке, когда числа совпали.
5. **Текст листа** — подстраховка, вес меньше.
6. **Группировка по марке раздела** с учётом того, что в ПД это КР, а в РД тот же раздел КЖ.
7. **Назначение один к одному**: жадный проход по убыванию оценки, лист не может быть парой
   сразу к двум. Так требует контракт: `CheckResult.page_pair_key` — одно поле, и страница,
   входящая в две пары, делает его неоднозначным.

Быстро: **210 мс** на 6 799 × 838 листов Речникова. Полный перебор дал бы миллионы сравнений,
поэтому сначала идёт отбор кандидатов, и он идёт двумя путями сразу — по наименованию через
`rapidfuzz.process.cdist` (матрица сходства целиком в C) и по отметкам через обратный индекс
«отметка → листы». Один путь не заменяет другой: верная пара ПД ↔ РД сходится по отметкам, а по
наименованию не попала бы даже в список кандидатов.

### Четыре ошибки, которые пришлось исправить по дороге

Каждая давала уверенные, но бессмысленные пары — и каждая видна только на реальных данных:

| Что было | Во что выливалось | Чем исправлено |
|---|---|---|
| Сравнивали **штамп целиком** | Лучшей парой выходило «москва 2025 г» ↔ «москва, 2025 г»: в штампе лежат подписи граф и название объекта | Извлечение графы 4 отдельно (`sheet_title`) |
| Метрика `token_set_ratio` | Она сравнивает **пересечение** множеств токенов и даёт 100 %, когда токены одной стороны — подмножество другой. Скан, где OCR распознал одну цифру «4», «полностью совпадал» с любым листом, где эта цифра есть | `token_sort_ratio` — сравнивает строки целиком и штрафует за разницу в длине |
| Чёрный список реквизитов | Перечислить всё нельзя: в графу 4 лезет то название объекта, то адрес, то фамилия ГИПа. На Речникове лучшие пары сошлись на адресе «нагатинский затон, улица речников, участок 7/7» | Правило по данным: наименование, повторяющееся в стадии чаще пяти раз, — реквизит, а не имя листа |
| Обычный Жаккар по отметкам | Два листа с единственной общей `+0.000` получали формальную единицу | Вес отметки по редкости и порог на **вес** пересечения, а не на число отметок |

### Сколько пар получается

| Объект | Листов ПД / РД | Было (по тексту) | Стало |
|---|---|---:|---:|
| Речников (скрытая часть) | 6 799 / 838 | 20 | **42** |
| Новослободская | 2 067 / 194 | 1 | **1** |
| Тюменская | 4 949 / 837 | 0 | **0** |

На Речникове **30 пар из 42 держатся на отметках** — по тексту их было не найти. Отметки есть у
360 из 646 пригодных листов ПД и у 469 из 541 листов РД.

У Новослободской и Тюменской прибавки нет, и это не порог: **в этих комплектах нет
соответствующих листов**. У Новослободской ПД раздела КР — почти целиком текстовый том, а РД —
армирование лестниц и плит; таких листов в ПД просто нет. У Тюменской на стороне РД всего
62 пригодных листа, почти все — вентиляция.

**ПД ↔ ИД не сопоставляется вовсе (0 пар)**, хотя отметки в ИД есть. Это ожидаемо: исполнительная
документация здесь — акты освидетельствования скрытых работ, а не чертежи. Акт с чертежом рядом
не кладут, он сверяется по параметру.

### Чем проверяли без разметки

Размеченных пар в корпусе нет — ни у организаторов, ни у нас. Поэтому две косвенные улики:

1. **Объявленная отметка.** Из 42 пар у 13 в графе 4 ПД названа отметка; у парного листа РД она
   есть во всех 13. Оговорка: это правило теперь участвует в оценке, поэтому проверка
   не полностью независима — она показывает, что правило работает, а не что пары верны.
2. **Порядок листов.** Этажи в комплекте идут подряд, и верные пары обязаны ложиться
   возрастающей цепочкой. Так и вышло, причём эта улика от оценки не зависит вовсе:
   - `F0253 → F0332`: страницы 49, 51, 52, 53, 54 легли на 5, 7, 8, 9, 10 — **пять листов подряд
     с постоянным сдвигом −44**;
   - `F0270 → F0408`: 6 пар, пять возрастаний из пяти возможных.

### Что осталось

- **Порядок как решающий довод.** Сейчас при споре двух листов ПД за один лист РД выигрывает тот,
  у кого выше оценка; выравнивание последовательностей разрешило бы спор правильнее.
- **Растр.** Отметок нет на фасадах, разрезах и узлах, а в сканах ИД нет и текста. Для них нужен
  кеш рендеров (`renders/{sha256}/{page}.png`) — и он нужен для визуального diff в любом случае,
  так что подпись листа и визуальный diff поделят один растр. Перцептивный хеш для чертежей плох
  (лист почти белый, после уменьшения всё вырождается в одинаковый серый) — вместо него сетка
  плотности штриха с проверкой лучших кандидатов через ORB + RANSAC.
- **Разметка.** Десяток пар, подтверждённых глазами, дал бы парам листов настоящую метрику. Кандидаты на
  неё — цепочка `F0253 → F0332`.

Порог `MIN_SCORE` намеренно оставлен высоким: пустой центр экрана честнее неверной пары рядом.

## Свободный поиск языковой моделью

Зачем. В публичном эталоне организаторов **четыре проверки из пятнадцати — `FREE-HEATING-001`**:
«в помещении по ПД предусмотрен отопительный прибор, в РД его нет». Правилами это не берётся —
такого параметра в матрице нет и не будет, сравнивать нужно смысл двух описаний. Ещё шесть
проверок про конфигурацию приборов в помещениях. Отсюда [ADR-0008](../adr/0008-llm-scope.md),
которым правило «сначала правила, потом модели» снято **для свободного поиска** (для параметров
матрицы оно остаётся).

Результат — **гипотеза, а не находка**: `SuspicionResult` с `discovery_method =
SEMANTIC_DISSONANCE`. `CONFIRMED_VIOLATION` модель не ставит никогда (REQ-CMP-05) и статусы
проверок матрицы не трогает. В интерфейсе инспектор гипотезу решает и при желании превращает
в кандидата — эта обвязка уже готова на стороне api и фронта.

### Запрет на выдумку держится на коде

Главное требование приёмки — не качество формулировок, а то, что модель не может добавить
в протокол того, чего в документах нет. Ответ проходит две проверки (`llm/grounding.py`),
и обе обязательные:

| Проверка | Что отсекает |
|---|---|
| Цитата обязана найтись в документе | пересказ вместо цитаты, ссылка на несуществующий текст |
| Каждое число ответа встречается в переданных фрагментах | «площадь 51,7 м²», которой нет ни в ПД, ни в РД |

Не сошлось — гипотезы нет, причина пишется в журнал. Побочная польза от первой проверки:
найденная цитата даёт страницу и рамку, то есть доказательство, на которое инспектор нажмёт.
Без рамки гипотеза всё равно была бы бесполезной — так же устроено извлечение значений.

Сравнение чисел строгое: запятую и точку не различаем, а хвостовой ноль не отбрасываем.
Иначе выдуманное «пом. 1.10» проходило бы по настоящему «пом. 1.1». Лишняя строгость даёт
отсутствие гипотезы, а не ложную, — в эту сторону и ошибаемся.

### Что уходит в модель

Пары «документ ПД — документ РД» **одного раздела** (`discipline` из метаданных): сверять
отопление с конструкциями бессмысленно. Из документов берутся страницы с текстом — чертежи
и нераспознанные не отправляются. Бюджет — `LLM_MAX_CHARS` на весь запрос, по половине на стадию
(12 000 символов — около 6 000 токенов: русский текст — около двух символов на токен; до 27.09 бюджет был на
стадию, и запрос в 12 тыс. токенов Ollama обрезала по контексту 8 тыс.), разделов за прогон не больше трёх,
гипотез на раздел не больше пяти.

**Листы-чертежи (27.09).** Доказательство `FREE-HEATING-001` в эталоне — план отопления, лист 21 тома
ИОС5.4.2 «Примера нарушений» (стр. 99). Подписи помещений и «теплый пол» лежат в текстовом слое чертежа,
но текстовые разделы чертежи не берут и до стр. 99 по бюджету не доходят. Поэтому до разделов
сравниваются **пары листов-чертежей** (`sheet_pairs`, не больше трёх за прогон):

- **Оснащённые помещения ПД.** На листе ПД берутся номера помещений из подписей не дальше 0,1 листа
  от подписи прибора: радиатор, конвектор, тёплый пол, фанкойл, решётка, диффузор, клапан. «Отопление» и
  «вентиляция» якорем не считаются: они в заголовках и легендах по всему листу.
- **Лист РД.** Нужен лист-чертёж, на котором есть хотя бы три из этих помещений. Оснащение на листе РД
  не требуется: проверяем, что в РД прибора нет. В «Примере нарушений» план отопления РД — линии без
  текста, помещения 267–272 есть только в экспликации.
- **Порядок пар.** Выше пары одной инженерной системы: раздел ПД 5.4 — «ОВ» РД, 5.2 и 5.3 — «ВК», 5.1 —
  электрика. Иначе план отопления ПД сравнивался с планом водопровода РД того же этажа. Дальше — число
  общих помещений и их доля среди номеров листа РД. Каждый лист — не больше чем в одной паре.
- **Запрос.** Модель получает подписи обоих листов, по `LLM_MAX_CHARS / 2` на сторону, с вопросом: у каких
  помещений в ПД есть прибор или решение, а в РД — нет. Проверки цитат и чисел те же. Цитата ищется на
  самом листе, поэтому доказательство — страница чертежа с рамкой подписи.

На «Примере нарушений» лист 21 ПД (стр. 99) встаёт в пару с листом вентиляции РД ОВ1.С (стр. 19): на нём
есть помещения 267, 270, 271, 272 из эталона.

Уверенность гипотезы ограничена потолком **0.5**: модель не калибрована, и выдавать её
«уверенность» за вероятность нельзя. Если распознавание доказательства хуже потолка, берётся оно —
гипотеза не надёжнее текста, на котором стоит.

### Модель не может уронить прогон

Выключена, не поднята, ответила мусором, не уложилась в таймаут, кончилась видеопамять —
возвращается пустой список, и протокол получается ровно таким же, каким был бы без неё.
Подключение живёт в `jobs/handlers.py`, а не в движке сравнения: правила считаются всегда,
гипотезы добавляются сверху.

При `LLM_ENABLED=false` (умолчание и наш публичный стенд на 2 vCPU) модель не трогается вовсе.

### Наружу клиент не ходит, и это механизм

Правило для внешних API — не «стараемся не использовать внешние API»,
а «не используем»: документы госнадзора, 152-ФЗ. До этой правки `LLM_BASE_URL` принял бы любой
адрес, включая `https://api.openai.com/v1`; умолчание было безопасным, но это намерение,
а не запрет.

Теперь клиент **не поднимается на нелокальном адресе**. Локальным считается петля (`localhost`,
`127.0.0.1`, `::1`), имя без точек — так называются сервисы внутри compose (`vllm`, `ollama`), —
`host.docker.internal`, суффиксы `.local` / `.internal` и частные диапазоны адресов, из которых
в интернет не выйти. Всё остальное отклоняется записью уровня `error` с внятной причиной.

Осознанное исключение остаётся: `LLM_ALLOW_REMOTE=true`. Запрещена случайность, а не выбор.
Прогон при этом продолжается без гипотез — ронять проверку из-за настройки нельзя.

### Настройки и проверка связи

| Переменная | Умолчание | Смысл |
|---|---|---|
| `LLM_ENABLED` | `false` | включает свободный поиск |
| `LLM_BASE_URL` | `http://localhost:11434/v1` | OpenAI-совместимый адрес: Ollama или vLLM |
| `LLM_ALLOW_REMOTE` | `false` | разрешить нелокальный адрес — осознанно и под запись |
| `LLM_MODEL` | `qwen3:8b` | модель; на проверяющем стенде — квантизованная Qwen3 8B |
| `LLM_TIMEOUT_S` | `90` | не ответила за это время — гипотез нет |
| `LLM_MAX_CHARS` | `12000` | сколько текста кладём в запрос, по половине на ПД и РД |
| `LLM_THINK` | `true` | рассуждение Qwen3 перед ответом: на 8B без него гипотезы заметно хуже, но ответ в разы длиннее. `false` — быстрый режим (`reasoning_effort: none` для Ollama, `chat_template_kwargs.enable_thinking=false` для vLLM) |

```bash
uv run inspector-ml llm
```

Команда отвечает на три вопроса по порядку: включена ли модель, отвечает ли адрес и умеет ли
она отдавать JSON. Без последнего гипотез не будет, как бы хорошо она ни рассуждала — Qwen3
рассуждает вслух в теге `<think>`, и разбор ответа это учитывает.

Пакет `openai` не нужен: запрос один, `httpx` и так в зависимостях, extra `llm` остаётся
необязательным.

## Изменённые числа в совпадающем тексте (без модели)

Зачем. 26.09 со стенда пришла пара ПД/РД раздела ИОС3.2: текст пояснительной записки слово
в слово один, а в РД поменяли три числа — R0 грунта 270 → 300 кПа, суточный расход
123,576 → 125,576 м³/сут, секундный 8,397 → 11,397 л/с. Протокол вышел пустым: двух величин
в матрице нет вовсе, третья записана не теми словами, что якорь параметра. Человек такое видит
сразу — абзац тот же, число другое. Модель для этого не нужна, и работает это всегда, в том числе
на стенде без LLM.

Как ищем (`suspicion/number_diff.py`):

1. **Страницы с одним текстом.** Текст страницы без основной надписи режется на четвёрки слов,
   где любое число заменено на `#`. Для страницы ПД берётся страница РД с наибольшей долей общих
   четвёрок (≥ 0,5), пары один к одному. Четвёрки, которые стоят больше чем на 50 страницах РД,
   — шаблон бланка, а не текст, они не считаются.
2. **Выравнивание слов** (`difflib`). Изменением считается место, где с обеих сторон стоит только
   число, а перед ним совпали хотя бы три элемента текста. Поменялись слова — это другой текст.
3. **Отбор.** Число — величина: с единицей после, со знаком «=» перед или дробное. Годы, даты,
   шифры (дефис или косая черта в том же слове), номера листов, пунктов, томов, ГОСТ и деньги
   отбрасываются. Цифры, приклеенные к буквам («П1», «R0», «м3»), — обозначение, а не величина.
4. **Отказ от сравнения.** Изменилось больше 30 % чисел страницы — это разные листы по одному
   бланку (например, листы данных двух вентустановок), а не правка.

Результат — **гипотеза** `SEMANTIC_DISSONANCE` с уверенностью 0,6 и доказательствами на обеих
страницах: «с прослоями супеси R0 — в ПД 270 кПа, в РД 300 кПа». Нарушение это или согласованное
изменение, решает инспектор. Если ту же пару значений уже нашёл движок по параметру матрицы,
гипотеза не повторяется. Не больше 5 гипотез со страницы и 25 на проверку: дальше это уже
другая редакция документа, и инспектору нужен не список чисел.

| Объект | Гипотез | Время |
|---|---|---|
| пара ИОС3.2 со стенда | 3 — ровно три правки | < 1 с |
| Новослободская (обучающий) | 0 | 2,6 с |
| Алтуфьевское (обучающий) | 0 | 3,2 с |
| «Пример нарушений» (обучающий) | 25 — расхождения вентустановок ПД и РД | 7,9 с |

Выключается `NUMBER_DIFF_ENABLED=false`, если помешает на показе. Упасть не может: ошибка пишется
в журнал, и протокол остаётся таким, каким его посчитали правила.

## Опыт с Sentence-BERT: похожая формулировка вместо дословной (26.09)

У 106 параметров из 132 регулярка и якорь — дословное название, и документы, написанные своими
словами, не находятся. Опыт: кандидаты «подпись → число с единицей» со страницы, единица совпадает
с единицей параметра, подпись ранжируется по близости к названию и якорям (MiniLM из стека, процессор).
Замер — 75 числовых параметров на трёх обучающих объектах (259 документов), эталон — размеченный пул
(серебряный, до проверки человеком). Подробности, разметка и скрипты — [`data/samples/sbert-eval/`](../../data/samples/sbert-eval/README.md).

| Метод | precision | recall | F1 (95 % ДИ) |
|---|---|---|---|
| продукт (правила) | 0,830 | 0,543 | 0,656 (0,59–0,72) |
| Sentence-BERT один, τ = 0,85 | 0,341 | 0,383 | 0,361 (0,30–0,42) |
| **правила, где молчат — Sentence-BERT, τ = 0,9** | 0,717 | 0,709 | **0,713 (0,66–0,76)** |

Одна модель хуже правил: не отличает общий объём от подземного, нагрузку по ТУ от расчётного расхода,
норму от решения. Запасным путём после правил поднимает полноту на 0,17 при потере точности 0,11.
В продукт не включено: порог подобран на тех же объектах, честная проверка — на отложенных 12, 17, 18
после их разбора.

**Отложенные 12, 17, 18 (27.09, 714 документов, ничего не подбиралось).** Без фильтров запасной путь правила
не обогнал: F1 0,703 против 0,718, половина лишних ложных — числа под подписями «этаж». Модель отвечает,
похожа ли подпись на название параметра, а не «значение ли это параметра для этого здания»: «Общая площадь
здания, подземная часть», «объём сносимого здания», «расход водоотведения» для неё почти то же самое.
Фильтры поверх модели (`scripts/sbert_eval/sbert_filter.py`): значение в пределах параметра из матрицы,
целое у счётных, в подписи не меньше двух слов, нет стоп-основ, выученных по обучающим объектам (порог —
перекрёстной проверкой внутри них). С ними запасной путь на отложенных — **F1 0,749 (0,70–0,79)** против
0,718 (0,66–0,77) у правил: точность 0,755 (у правил 0,779), полнота +0,08. Прибавка в пределах разброса.
28.09 его включили в продукт за флагом — [ниже](#sentence-bert-в-продукте-2809). Подробности
опыта — [`data/samples/sbert-eval/`](../../data/samples/sbert-eval/README.md).

**LLM проверяет кандидатов (27.09, опыт вне продукта, через OpenRouter).** Модель отвечает по каждому кандидату, это
ли значение параметра для проектируемого объекта; ответ «нет» кандидата убирает. Проверка всех значений
(правил и Sentence-BERT) поднимает F1 на отложенных 0,716 → **0,850** (0,80–0,89), на обучающих 0,608 → 0,751;
точность на отложенных 0,78 → 0,95. Лёгкая Qwen3-30B-A3B (3B активных) не уступает Qwen3-235B, Qwen3.5-9B
чуть слабее (0,820), Qwen3-8B заметно (0,768). В продукте по правилу 9 — только локальная модель через
клиент `llm/`. Подробности — [`data/samples/sbert-eval/`](../../data/samples/sbert-eval/README.md).

### Sentence-BERT в продукте (28.09)

Решение 27.09: Sentence-BERT из стека ТЗ идёт в продукт запасным путём
извлечения. Код — [`extract/sbert.py`](../../services/ml/src/inspector_ml/extract/sbert.py), логика — та же, что
в опыте на отложенных, с фильтрами.

**Как работает.**

- Правила по параметру молчат **во всех документах стадии** — тогда спрашивается Sentence-BERT, не раньше. Из
  стадии берётся одно значение, самое близкое по смыслу: два разных числа в стадии движок превратил бы в
  «требуется уточнение» вместо сравнения.
- Берутся числовые параметры матрицы запроса **без ключа места** — 69 из 132, только документы ПД и РД.
  - У M-002 (помещения), M-009, M-016, M-041, M-058, M-074 свой разбор ставит ключ места: помещение,
    конструкцию, выпуск.
  - Значение без ключа с их точками не сводится (`compare/matching` не сливает группу `None` с группами с
    ключом), вышла бы отдельная проверка «на весь параметр».
  - Список — `extract/api.KEYED`, M-003 ключа не ставит.
- Кандидаты — «подпись → число с единицей» из фраз и строк таблиц; штамп листа не берётся.
- Единица числа должна подходить параметру. Миллиметры при параметре в метрах пересчитываются: 600 мм → 0,6.
- Четыре фильтра:
  - значение в пределах `min_value…max_value` матрицы;
  - у счётного параметра — целое;
  - в подписи не меньше двух содержательных слов;
  - в подписи нет стоп-основ ([`sbert_stops.json`](../../services/ml/src/inspector_ml/extract/sbert_stops.json),
    42 основы, выучены только на обучающих объектах).
- Кандидат должен быть не ниже порога `SBERT_THRESHOLD` (0,9).
- **Одна подпись — один параметр:** подпись достаётся параметру матрицы, к которому она ближе всего.
  - Сравнивается со всеми 132 параметрами — и с нечисловыми, и с найденными в документе правилами, и с
    параметрами с ключом места.
  - Проигравший параметр берёт своего следующего кандидата.
  - Так разводятся близкие параметры. «Общая площадь здания» ближе всего к M-002 (1,000), и M-001 (площадь
    застройки, 0,913) её не берёт. «Площадь застройки жилого дома» тоже уходит к M-002 (0,915).
    «…подземной части» достаётся M-005 (0,995), а не M-001 (0,913) или M-006 (0,951).
  - Все пары из ревью — площадь застройки, общая, полезная; строительный объём общий, подземный и надземный —
    сверены на MiniLM из образа. Порог поднимать не пришлось.

**Что получает движок.** Значение идёт в сравнение как обычное, со своим фрагментом и координатами, и может дать
кандидата. Отличия от правил:

- `rule_key = None` — значение относится к параметру целиком;
- `Extraction.method = "sbert"`;
- фрагмент помечен `extraction_method = SBERT` (контракт 0.23.0 REST и 0.8.0 событий). У правил поле пустое: пусто и `RULES` — одно и то же.

По пометке инспектор видит в карточке «найдено по смыслу» (FE, по желанию), а скорер получает признак `sbert` с
обеих сторон — из `GoldSource` при обучении и из фрагментов при применении. Уверенность фрагмента не трогаем:
это уверенность распознавания текста, а не метода. Первая версия ставила потолок 0,5, но две поправки на один
случай не нужны.

**Модель не может уронить проверку.**

- **Нет пакета `sentence-transformers` или весов** — предупреждение `sbert_unavailable`, дальше одни правила.
  - Модель грузится **только с диска** (`local_files_only`): в закрытом контуре задача не ходит на huggingface.co
    и не виснет на таймаутах.
  - Неудачная загрузка не запоминается: положили веса — следующая задача модель найдёт без перезапуска ml.
- **Лимит — число подписей, а не секунды.**
  - `SBERT_MAX_LABELS` (30 000) — сколько разных подписей задача кодирует, в порядке документов запроса.
  - Лимит детерминированный: пересчёт того же комплекта даёт те же значения при любом кеше и загрузке
    процессора. Кончился — `sbert_labels_exhausted`, остальные документы идут без Sentence-BERT.
  - Бюджет по часам `SBERT_BUDGET_S` (1800 с) остался только аварийным. Он проверяется перед каждой пачкой
    подписей, чтобы не съесть таймаут задачи.
- **Модель грузится один раз на рабочий процесс.** Эмбеддинги названий параметров считаются один раз на задачу,
  документа — один раз для всех параметров сразу.

**Дорого только кодирование подписей** — около 120 подписей в секунду на процессоре ноутбука (6 ядер; число
потоков и размер пачки почти не влияют). Поиск кандидатов и выбор — доли процента. Поэтому до модели подпись
проходит дешёвый отсев:

- не меньше двух содержательных слов — фильтр `generic` от параметра не зависит, его можно применить раньше;
- хотя бы одна общая основа из четырёх букв с названием или якорем какого-нибудь числового параметра.

Без общего слова близость 0,9 не набирается: из 84 значений первого повтора на отложенных ни одно не было без
общей основы со своим параметром, а кодировать остаётся 40 % подписей. Эмбеддинги подписей помнятся на процесс
(до 50 тыс., около 77 МБ): повторное сравнение того же комплекта их не пересчитывает.

**Замер кодом продукта (28.09).** Код продукта прогнан по тем же 714 документам ПД и РД отложенных объектов 12,

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `SBERT_ENABLED` | `false` | Включить запасной путь. Включается на стенде после контрольного комплекта 3 |
| `EMBEDDING_MODEL` | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` | Имя в кеше Hugging Face (`HF_HOME`) или путь к папке с весами |
| `SBERT_THRESHOLD` | `0.9` | Порог близости подписи к названию и якорям параметра |
| `SBERT_MAX_LABELS` | `30000` | Сколько разных подписей задача сравнения кодирует — детерминированный лимит |
| `SBERT_BUDGET_S` | `1800` | Аварийный бюджет на задачу, с — чтобы не съесть `ML_JOB_TIMEOUT_S` |

**Загрузка модели** — `SentenceTransformer(EMBEDDING_MODEL, device="cpu")`. Шаг сборки образа грузит её тем же
вызовом, и веса попадают в кеш Hugging Face:

```bash
.venv/bin/python -c "from sentence_transformers import SentenceTransformer as S; S('sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2', device='cpu')"
```

В работе нужны тот же `HF_HOME` и `HF_HUB_OFFLINE=1`: сеть не нужна.

**torch — сборка для процессора.** С PyPI под Linux torch тянул весь CUDA 13: `cuda-toolkit`, `nvidia-cudnn-cu13`,
`nccl`, `triton`. В `pyproject.toml` torch стал прямой зависимостью extra `embeddings` с индексом
`https://download.pytorch.org/whl/cpu` (`explicit`: из него берётся только torch). Из `uv.lock` ушли 19 пакетов —
15 `nvidia-*`, 3 `cuda-*` и `triton`, — torch теперь `2.14.0+cpu`. В образе с видеокартой тоже процессорный: MiniLM на процессоре работает быстро, а
CUDA там уже есть у paddle.

**Насколько вырастет образ** (28.09). Замер по окружению, собранному как в `ml.Dockerfile`: `uv sync --frozen
--no-dev`, копированием и с байт-кодом. Локальный Docker без `buildx` Dockerfile с BuildKit не собирает, а образ —
это базовый Python плюс это окружение.

|---|---|
| extra `ocr` (как сейчас на стенде) | 1,47 ГБ |
| extra `ocr` + `embeddings` | 2,47 ГБ |
| прирост пакетами | **0,99 ГБ**: torch 743 МБ, transformers 110 МБ, scipy и scikit-learn 140 МБ, остальное — мелочь |

Пакетов `nvidia-*` в окружении нет, `torch.version.cuda` — `None`. Для образа с видеокартой прирост тот же: те же

## Внутренний интерфейс `extract` ↔ `compare`

Это граница между извлечением и движком сравнения: меняется только согласованно с обеих сторон.

```python
# src/inspector_ml/extract/api.py
from dataclasses import dataclass
from inspector_ml.contracts.events import EvidenceFragment, MatrixParam, DocumentMetadata

@dataclass(frozen=True)
class LoadedDocument:
    file_id: str
    sha256: str
    metadata: DocumentMetadata          # после ручных правок из CompareFile.metadata
    parsed: "ParsedDocument"            # загруженный parsed JSON

@dataclass(frozen=True)
class Extraction:
    param_code: str
    stage: str                          # "PD" | "RD" | "ID"
    file_id: str
    rule_key: str | None                # экземпляр: «Д-3», «пом. 105», «Пм-1»; None — параметр объекта целиком
    raw_value: str                      # как в документе
    value: float | str | bool | None    # нормализованное (числа — в базовых единицах матрицы)
    unit: str | None
    fragment: EvidenceFragment          # page, bbox, snippet, quality, confidence
    method: str                         # "regex" | "table" | "llm" | "cv"

def extract_param(param: MatrixParam, docs: list[LoadedDocument]) -> list[Extraction]:
    """Все найденные значения параметра во всех переданных документах.
    ≤ 500 мс на параметр без LLM (REQ-PERF). Страницы ABSTAIN не используются."""
```

```python
# src/inspector_ml/compare/engine.py
def run(
    request: CompareRequest,
    docs: list[LoadedDocument],
    extract: Callable[[MatrixParam, list[LoadedDocument]], list[Extraction]],
    page_pairs: list[PagePairResult],        # от cv/pairing.py, может быть пустым
) -> CompareResult: ...
# вызывается из jobs/runner.py
```

Движок `compare` вызывает `extract_param` для документов актуальных редакций и сам решает:

- применимость;
- комплектность;
- сопоставление по `rule_key`;
- срабатывание триггера;
- итоговый статус.

Движок тестируется и на фейковых `Extraction` — так он не зависит от готовности извлечения.

- коды параметров организаторов (`PZ-002`, `KR-055`) однозначно соответствуют нашим `M-002`,
  `M-055` — таблица в [data/samples/parameter-code-map.csv](../../data/samples/parameter-code-map.csv).

## Геометрия (REQ-PRS-06) — покрыта тестами

- В PyMuPDF `page.rect` — видимая область с учётом CropBox и поворота.
- **Важно:** координаты текста PyMuPDF отдаёт в **неповёрнутой** системе, а `page.rect` — в повёрнутой.
  Перед нормализацией bbox нужно умножить на `page.rotation_matrix`, иначе на повёрнутых страницах
  (в корпусе таких около 20 %) подсветка уезжает. Проверено тестами на Rotate = 0/90/180/270
  и смещённом CropBox, точность 0.01.
- Нормализация: `x / page.rect.width`, `y / page.rect.height`, начало в левом верхнем углу, значения обрезаются до [0; 1].
- OCR и CV работают по растру (`page.get_pixmap(dpi=…)`, растр уже повёрнут), нормализация идёт по размеру изображения.
- Фронт рисует bbox поверх viewport pdf.js, у которого та же система координат.

## Пары страниц и визуальные различия (`page_pairs`)

1. `cv/pairing.py`: подобрать пары листов разных стадий — **сделано**, см. «Пары листов» выше.
2. `cv/render.py`: растр страницы из кеша `renders/{sha256}/{dpi}/{page}.png` — **сделано**, см. «Кеш растров страниц».
3. Совмещение ORB + RANSAC → `homography` (нормализованные координаты правой страницы → левой) — **сделано**
   для листов-чертежей с растром, `cv/sheetdiff.py` (подобие, а не полная гомография — см. ниже).
4. Области различий → `diff_regions` (bbox на обеих страницах, `score`, `label`) — **сделано**.
5. Гипотеза `VISUAL_DIFF` с `suspicion_key` в областях — **сделано**, `suspicion/visual.py`. Привязка
   области к доказательству finding (`finding_key`) — не сделана.
6. `compliance_percent` для пары — доля площади без различий. Это «Соответствие 84%» в UI. Не сделано.

### Листы-чертежи ПД ↔ РД ↔ ИД

Зачем. Куратор загрузил пару «Ситуационный план, М 1:2000»: в ПД на подложке канализация
(`d=200-225`, выпуски К1), в РД — водопровод (`d=300`, `d=250`, колодцы 70278…65265). План в обоих
листах — растр: у РД 1 текстовый слой — 85 символов подписи сверху, у ПД 1 — сплошной скан. Система
ответила «Нет доказательств» по всем 132 параметрам. Числа с чертежа параметрами матрицы не станут,
но показать инспектору, где листы расходятся, можно.

Как (`cv/sheetdiff.py`, `suspicion/visual.py`, вызов в `jobs/handlers._with_hypotheses`):

1. **Лист-чертёж** — страница, где самая крупная картинка занимает не меньше 15 % листа, а
   разобранного текста вне штампа меньше 600 символов (у сканов записок и актов текста больше).
   Растр берётся из исходного файла `STORAGE_DIR/raw/{sha256}`, общего для api и ml, в цвете: сети
   на планах различаются цветом, а в оттенках серого — почти нет. **Разбор и `PARSER_VERSION` не
   меняются**, кеш 0.5.0 на стенде остаётся годным.

   Отбор в два прохода, иначе комплект на сотни документов разбирается минутами. Сначала по
   ресурсам страницы, без её загрузки, берётся размер самой крупной картинки. Меньше 300 × 300 пикселей
   (логотип, штамп) или больше 100 картинок на листе — не растр-чертёж. Лист-мозаика из тысяч
   плиток — это векторный чертёж САПР с заливками: место картинки на таком листе ищется до 13 секунд.
   Потом, от крупных картинок к мелким, — место картинки на листе, растр и особые точки, пока в стадии
   не наберётся 12 листов.
2. **Совмещение** — ORB (5000 точек), тест Лоу, RANSAC. Берётся подобие (`estimateAffinePartial2D`):
   одна подложка на двух листах отличается поворотом, масштабом и сдвигом, а полная гомография
   добавляет из шума перспективу, и наложение «плывёт» к краям. Меньше 40 согласованных точек или
   меньше четверти от отобранных — это разные чертежи, пары нет.
3. **Различия** — «чернила» (насыщенный цвет или тёмный тон) одного листа, которых нет в радиусе
   9 px на другом; близкие пятна сливаются, области меньше 0,2 % растра отбрасываются.
4. **Подписи** — OCR только областей различий и полосы заголовка, при 250 dpi. Целый лист на
   процессоре распознаётся дольше 30 секунд, области — за секунды. Из текста берутся диаметры
   (`d=300`, `Ø110`, `Ду100`), системы (`К1`, `В1`, `Т3`), номера колодцев (5 цифр), заголовок с масштабом.
5. **Результат** — гипотеза `VISUAL_DIFF` (уверенность 0,35) с рамками на обоих листах и пара листов
   в `page_pairs` с `homography` и `diff_regions`. Экран сравнения показывает наложение.

**Пара-пример** (процессор, OCR на CPU):

> Лист-чертёж «Ситуационный план, М 1:2000»: после совмещения ПД и РД различаются 4 обл.
> Только в ПД: d=200-225. Только в РД: 70280, d=300, 70281, 70278, 65265, d=250, 65264.
> Возможно, на листах разные сети или изменена трасса — проверьте.

Совмещение — 731 согласованная точка из 781, масштаб 1,2. Без OCR — 0,3 с; с OCR на процессоре — 18–25 с на
пару (процессор в это время занят разбором корпуса).

**Обучающие объекты** — гипотез ноль, значит, и ложных нет. Нет ли там пропусков, не проверено:
разметки растровых чертежей у нас нет.

| Объект | Документов | Гипотез | Время, с (до отсева → после) |
|---|---|---|---|
| Новослободская | 145 | 0 | 65,5 → 24,2 |
| Пример нарушений на чертежах | 57 | 0 | 54,0 → 16,3 |
| Алтуфьевское, 79Б | 57 | 0 | 38,7 → 25,5 |

Из 23 с на Алтуфьевском 7 уходит на отрисовку 22 листов, 4 — на поиск места картинок и 5 — на
совмещение 60 пар.

Выключается `VISUAL_DIFF_ENABLED=false`. Упасть сравнению не даёт: ошибка пишется в журнал.
Ограничения: не больше 12 листов-чертежей на стадию и 60 проверок пар, OCR подписей — не больше
25 секунд на проверку; векторные чертежи (САПР без растра) сюда не попадают — для них поиска различий пока нет.

## Кеш (REQ-PRS-07)

Ключ — `{sha256}:{parser_version}`, значение — parsed JSON в `var/storage/parsed/...`, индекс лежит в `CACHE_DIR`. Повторная загрузка того же PDF, в том числе в другую проверку, отвечает мгновенно с `from_cache=true`. `PARSER_VERSION` поднимается при любом изменении парсинга, которое меняет результат.

## Производительность разбора (REQ-PERF)

Цели ТЗ: **100 страниц ≤ 3 мин, 500 страниц ≤ 10 мин.** Замеры на i5-11400H, медиана из трёх
прогонов, разбор без OCR (про OCR — ниже, и это главное).

| Файл | Стадия | Страниц | Размер | Разбор | На страницу | Нужен OCR |
|---|---|---:|---:|---:|---:|---:|
| F0054 | ПД | 14 | 3 МБ | 0.15 с | 11 мс | 0 |
| F0187 | ПД | 83 | 16 МБ | 2.66 с | 32 мс | 11 |
| F0186 | ПД | 168 | 3 МБ | 3.55 с | 21 мс | 1 |
| F0323 | ПД | 468 | 76 МБ | 13.4 с | 29 мс | 1 |
| F0189 | ПД | 969 | 45 МБ | 15.1 с | 16 мс | 43 |
| F0232 | ИД | 507 | 628 МБ | 1.6 с | 3 мс | **506** |

**468 страниц разбираются за 13 секунд при бюджете в 10 минут** — в 45 раз внутри. Даже с поправкой
на то, что стенд слабее ноутбука (2 vCPU против 12 потоков), запас остаётся двукратно-трёхкратным
с лишком. По текстовому разбору REQ-PERF выполняется с огромным зазором.

### Весь бюджет съедает OCR, а не разбор

Последняя строка таблицы — та, ради которой всё это мерилось. F0232 это скан исполнительной
документации: **разбор 1.6 секунды, а страниц без текстового слоя 506 из 507.** На процессоре OCR
стоит около минуты на страницу ([ADR-0007](../adr/0007-stand-cpu-precomputed-cache.md)), то есть
распознавание этого файла — восемь с половиной часов против полутора секунд разбора.

То же видно и на предрасчёте всего корпуса: 26 026 страниц за 6.5 часа, из них распознано 11 719.
Текстовый разбор всех 26 026 страниц при 25 мс — это **11 минут из 6.5 часов**, остальные 97 %
времени ушли в OCR.

Поэтому REQ-PERF держится не скоростью разбора, а двумя вещами, которые уже сделаны:

1. **Предрасчитанный кеш** покрывает весь корпус — знакомый файл отвечает из кеша сразу;
2. **`OCR_MAX_PAGES`** — потолок распознанных страниц на документ для новых файлов. При минуте
   на страницу даже три нераспознанных листа выносят трёхминутный бюджет, так что вопрос всегда
   «сколько страниц распознаём», а не «как быстро разбираем».

### Параллелизм по страницам: измерено и отклонено

В задаче он стоял, и мы его померили — пул потоков и пул процессов по страницам одного документа,
медиана из трёх прогонов:

| Файл | Последовательно | Потоков 2 | Потоков 4 | Процессов 2 | Процессов 4 |
|---|---:|---:|---:|---:|---:|
| F0054, 14 страниц | 0.15 с | ×1.16 | ×1.17 | ×0.17 | ×0.17 |
| F0187, 83 страницы | 2.66 с | ×1.02 | ×0.97 | ×0.71 | ×0.86 |
| F0186, 168 страниц | 3.55 с | ×1.00 | ×0.96 | ×1.22 | ×1.84 |

**Потоки не дают почти ничего** — PyMuPDF отпускает GIL не везде, отсюда ×1.0. **Процессы на мелких
файлах медленнее в шесть раз**: запуск интерпретатора и передача данных дороже самой работы.
Единственное настоящее ускорение — ×1.84 на 168-страничном файле — экономит **1.6 секунды**.

Делать этого не будем, и вот почему:

- **ускорять нечего.** Мы в 45 раз внутри бюджета, а узкое место — OCR, которого параллелизм
  страниц не касается;
- **ядра уже заняты.** В `jobs/runner.py` есть параллелизм уровня документа
  (`ProcessPoolExecutor`, `ML_WORKERS`). На стенде с 2 vCPU два документа выбирают оба ядра, и
  вложенный пул начнёт с ними драться;
- **PaddleOCR и так многопоточный.** Делить между процессами те же два ядра — перекладывать из
  кармана в карман, а каждый процесс поднимает свою копию модели при 8 ГБ памяти на всё;
- **риск не окупается.** Разбор страниц по пулу может изменить порядок блоков в `ParsedDocument`,
  а это подъём `PARSER_VERSION` и повторный предрасчёт на 6–7 часов ради полутора секунд.

Если на экспертизе упрёмся в скорость, полезнее будет не параллелизм, а приоритет страниц внутри
бюджета OCR: распознавать в первую очередь те, где матрица ждёт активные параметры.

## Кеш растров страниц

Наложению листов и поиску различий нужен растр, а на этапе сравнения у движка только
разобранный JSON: исходные PDF ему не передаются. Отсюда `cv/render.py` —
`renders/{sha256}/{dpi}/{page}.png` в `STORAGE_DIR` рядом с `parsed/`. Один лист за проверку
запрашивают несколько раз (подпись листа, выравнивание, diff, повторный просмотр инспектором),
и платить за рендер каждый раз незачем.

```bash
inspector-ml cache renders "<папка с PDF>" --dpi 150   # прогреть заранее
inspector-ml cache stats                                # что уже лежит, с разбивкой по dpi
inspector-ml cache renders --clear [sha256]             # вернуть место: один документ или всё
```

Очистка нужна на стенде: диск там делят исходные файлы, кеш разбора и копии базы, а растры
копятся всю экспертизу, пока эксперты листают чертежи. Удалять их безопасно — при следующем
запросе лист отрисуется заново примерно за 0.15 с, в отличие от разбора, который пришлось бы
считать заново с OCR. Значение, не похожее на sha256, команда отвергает: иначе `--clear` молча
съел бы путь к папке и отчитался, что удалять нечего.

### Этот кеш не едет на стенд — в отличие от кеша разбора

Решение сознательное, и вот цифры, на которых оно стоит. Разбор переносят архивом
([ADR-0007](../adr/0007-stand-cpu-precomputed-cache.md)) потому, что OCR на процессоре стоит
около минуты на страницу. Рендер — чистая растеризация PyMuPDF, моделей там нет:

| Что рендерили | Страниц | Время | На страницу | Размер | На страницу |
|---|---:|---:|---:|---:|---:|
| РД, раздел АР (листы A1), 150 dpi | 117 | 30.7 с | 0.262 с | 95.6 МБ | 856 КБ |
| РД, раздел АР (листы A1), 50 dpi | 117 | 16.9 с | 0.144 с | 28.8 МБ | 258 КБ |
| ПД, раздел АР (в основном A3), 150 dpi | 389 | 42.9 с | 0.110 с | 145.4 МБ | 392 КБ |

Итог по 506 листам при 150 dpi — **0.145 с и 500 КБ на страницу**. В пересчёте на весь корпус
это около часа работы и **порядка 13 ГБ** против 86 МБ у архива разбора. Возить такое на стенд
незачем: там, где разбор экономит минуту на страницу, растр экономит десятую долю секунды.

Поэтому растр считается на месте и по запросу, а кеш только не даёт считать одно и то же дважды.
Повторный прогон той же папки занял **0.3 с** и не отрисовал ни одной страницы.

### Три решения, которые стоит объяснить

- **`dpi` входит в ключ.** Потребители разные: подписи листа для пар хватает 50 dpi,
  а выравниванию по ORB и разностному diff нужно 150 — на 100 dpi у тонких линий чертежа мало
  особых точек. Без dpi в ключе смена `RENDER_DPI` молча отдавала бы картинку не того разрешения.
- **Оттенки серого, без альфы.** Вдвое меньше цветного PNG (99 КБ против 187 КБ на листе A3),
  а выравнивание и diff всё равно работают по яркости.
- **Длинная сторона ограничена `RENDER_MAX_PX`.** Лист A0 при 300 dpi — это 14 000 пикселей по
  длинной стороне и гигабайты в памяти. Предел тот же, что у OCR.

Запись идёт через временный файл и переименование: прогон идёт минутами, и обрыв посередине не
должен оставить обрезанный PNG — при следующем запуске он выглядел бы попаданием в кеш. Битый
файл при чтении считается промахом, а не ошибкой.

## Скорер кандидатов

Лёгкая обучаемая модель поверх правил: подтвердит ли инспектор кандидата в нарушения. Учится на
решениях инспектора — выпущенной версии GOLD-набора из api, — применяется после движка сравнения.
Пакет [`scorer/`](../../services/ml/src/inspector_ml/scorer/).

```bash
# выгрузка из api (API_URL, ML_API_LOGIN / ML_API_PASSWORD — учётка с ролью ML_ENGINEER)
inspector-ml train --dataset gold-2026.09.1 --register
# или по файлу выгрузки, без api
inspector-ml train --dataset gold-2026.09.1 --export gold-2026.09.1.jsonl
# первая итерация на настоящих объектах: порог решений каждого класса в TRAIN ниже 10
inspector-ml train --dataset <версия> --min-per-class 3 --register
```

`--min-per-class` (по умолчанию 10) — сколько подтверждённых и отклонённых нужно в `TRAIN`. На первой
итерации (решение 27.09: «Пример нарушений» — TRAIN, Новослободская — VALIDATION) кандидатов
мало, и подтверждённых 10 не набрать. Порог и число решений каждого класса уходят в `training_params`
регистрации и в метаданные файла модели: видно, на чём она обучена. Пороги §14 не трогаются.

1. **Выгрузка и хеши.** Строки `DatasetRecord` группируются по `split`, хеш части — SHA-256 байтов
   строк как они пришли (каждая с `\n`), без пересериализации JSON. Не сошлось с
   `DatasetVersion.split_hashes` — не обучаем.
2. **Обучение на `TRAIN`, замер на `VALIDATION`, `HIDDEN_TEST` не трогаем ни для чего** (REQ-ML-03;
   тест с перевёрнутыми метками `HIDDEN_TEST` это проверяет). Метка — `POSITIVE`, если инспектор
   подтвердил нарушение, `NEGATIVE` — если отклонил.
3. **Модель** — логистическая регрессия с L2 на numpy, классы уравновешены. Не scikit-learn (scipy —
   около 70 МБ в образ ради одной регрессии) и не pickle: файл модели — JSON с весами, его можно
   прочитать, у него стабильный SHA-256 (`artifact_hash`), и при загрузке он не исполняет код.
4. **Порог** — самый высокий, при котором на `TRAIN` сохраняется 95 % подтверждённых, и не выше 0.5.
   Скорер срезает пустых кандидатов, а не спорит с инспектором.
5. **Метрики §14 на `VALIDATION`:** precision, recall, F1, FPR, по разделам (`per_category` — по ним api
   проверяет регрессию) и 95 % интервал бутстрепом. Пороги §14 и регрессию считает api при регистрации
   (`POST /ml/models`), решение принимает ответственный.
6. **Мало данных — не обучаем:** меньше 10 решений любого класса в `TRAIN` или пустая `VALIDATION` —
   отказ с объяснением. Модель на десятке записей выглядит работающей и ничего не значит.

**Признаки** — только то, что есть и в записи GOLD, и в результате сравнения
([`scorer/features.py`](../../services/ml/src/inspector_ml/scorer/features.py)): раздел параметра, есть
ли ключ точки, число ли значение и относительное расхождение, разные ли строки, приоритет, пара стадий,
утверждённость источников, OCR и с 28.09 — `sbert`: значение найдено Sentence-BERT (`extraction_method`
фрагмента, контракт 0.23.0). В снимках GOLD раньше 0.23.0 ключа нет — это правила. Уверенности фрагмента в GOLD
нет, на неё не опираемся. Признаки при применении берутся по именам из файла модели: модель, обученная до
`sbert`, применяется дальше. Постоянный признак (в `ds-2026.09.2` пометок `SBERT` не будет) обучению не мешает —
его вес остаётся нулевым. С 29.09 есть и `log_ratio` — |ln(факт / эталон)|, во сколько раз разошлись значения:
`relative_delta` упирается в потолок уже на пятикратном расхождении, а ошибку извлечения от нарушения отличает
именно порядок.

**Применение** (`jobs/handlers._with_scorer`, после правил, до гипотез языковой модели): модель из
`STORAGE_DIR/models/<model_version>.json`, версия — из запроса сравнения (`versions.model_version`),
запасной вариант — `SCORER_MODEL`. `CANDIDATE` с вероятностью ниже порога → `NEGATIVE_VERIFIED`, в
`rationale` дописано, какая модель, какая вероятность и какой порог. Остальные статусы, значения и
доказательства не меняются; `CONFIRMED_VIOLATION` модель не ставит (REQ-CMP-05). Нет файла модели или он
сломан — результат правил без изменений, проверка не падает. Раздел параметра для признаков берётся из матрицы
запроса: `data/matrix` в образе ML нет, и до 29.09 на стенде все кандидаты попадали в раздел «?».

**Порог понижения.** По умолчанию — по сохранённой полноте на `TRAIN` (95 % подтверждённых выше порога), но
не выше 0,5.

- **Меньше 5 подтверждённых в `TRAIN`** — порог не выше 0,2 (`few_positives`). По одной записи порог по
  полноте равен её вероятности на собственных данных и упирается в 0,5: скорер понизил бы почти всех.
- **Явный порог** — `train --threshold 0–0.5` (`manual`).
- **Откуда порог** — в `training_params.threshold_source`.

**Режим «мало данных»** (с 29.09). Меньше 5 подтверждённых в `TRAIN` — модель учится на одном признаке
`log_ratio` и только на записях, где отношение «факт / эталон» определено (`mode = few_data`).

- **Почему один признак.** На всех признаках и девяти решениях модель ловила случайное — раздел, «строки разные»,
  пару стадий — и понижала внесённые ошибки комплекта 3 (ниже). Держится один сигнал: ошибка извлечения — это
  числа в разы и на порядки (41,7 → 3793,1), нарушение — проценты.
- **Кандидатов без отношения не трогает** — сигнала для них в данных нет. В метаданных модели `numeric_only`,
  и `apply` пропускает кандидатов с `ratio_defined = 0`.
  - Отношения нет у текста, марок (С0, КМ2, B25, А500), текста с цифрой («исполнение 1 по проекту»), нуля и
    значений разных знаков.
  - Значения разбирает `only_number`: число целиком, с единицей, но без прочих слов.
  - Раньше разбирал `number`, и он брал цифру из марки. На стенде С0 → С1 (M-023), КМ0 → КМ3 (M-107) и
    0 → 24 (M-012) давали ноль против числа и потолок признака — скорер понижал внесённые ошибки.
  - С правкой кода это касается и модели `-few`, обученной до неё: `apply` смотрит на `ratio_defined` у любой
    модели с `numeric_only`.
- **Потолок признака** — 6: расхождение в 400 раз и больше уже не различается.
- **Совместимость.** Модели, обученные раньше, применяются как прежде: признаки берутся по именам. Код без этой
  правки модель «мало данных» не применит — признака `log_ratio` в нём нет, — и останется результат правил.
- Режим — в метаданных модели и в `training_params.mode`.

**Итерация на стенде (28–29.09), `ds-2026.09.2`: контур пройден, модель «мало данных» не понижает внесённых ошибок.**

Выпуск набора, обучение, сверка хешей, метрики и регистрация прошли на стенде.

- **TRAIN.** Одна подтверждённая запись (пом. 104, 14,9 → 15,2) и восемь отклонённых.
  - Числовые отклонённые: M-025 7 → 2, пом. 305 11,2 → 10 и три ошибки извлечения — 41,7 → 3793,1,
    496,4 → 3793,1, 10,8 → 2192,9.
  - Текстовые отклонённые: три.
- **VALIDATION.** Шесть подтверждённых — расхождения в проценты — и одна отклонённая, 520,2 → 15,8.

Проверка перед тем, как делать модель текущей:

- **что проверяли** — кандидатов движка на контрольных комплектах 1–3 (внесённые ошибки) и на «Примере нарушений»
  (для модели это обучающие данные);
- **раздел** — из матрицы запроса.

| | Кандидатов | `scorer-ds-2026.09.2`, все признаки: понижено при 0,5 / 0,2 | `scorer-ds-2026.09.2-few2`: понижено при 0,2 |
|---|---|---|---|
| контрольный 1 | 3 | 2 / 0 | 0; оценён 1, классы бетона — нет |
| контрольный 2 | 3 | 2 / 0 | 0; оценён 1 |
| контрольный 3, 132 параметра | 86 | 84 / 23 | 0; оценено 51, минимум 0,513 |
| «Пример»: 41,7 → 3793,1 и 10,8 → 2192,9 | 2 | 2 / 2 | 2 (0,189 и 0,140) |
| «Пример»: 496,4 → 3793,1 | 1 | 1 / 1 | 0 (0,410) |
| «Пример»: пом. 104 и 305 — 14,9 → 15,2 (подтверждён) и 11,2 → 10 (отклонён) | 2 | 0 / 0 | 0 (0,629 и 0,619) |
| «Пример»: назначение помещений, текст | 3 | 3 / 1 | не оцениваются |

- **Модель на всех признаках (`scorer-ds-2026.09.2`).** Порога, который годится для обеих задач, у неё нет.
  - Не понижать внесённые ошибки комплекта 3 — значит взять порог ниже 0,06, и тогда она не понижает ничего.
  - При пороге 0,2 она понижает 23 внесённые ошибки комплекта 3, в том числе II → III, C → D и 24 → 19.
- **Модель «мало данных» (`scorer-ds-2026.09.2-few2`).** Веса те же, что у `-few`: обучающие записи с
  отношением не изменились. Отличается код — какие кандидаты модель оценивает.
  - Внесённые ошибки не трогает.
  - С0 → С1, КМ0 → КМ3 и 0 → 24 со стенда остаются кандидатами.
  - Снимает только грубые ошибки извлечения — числа в десятки и сотни раз.
  - Пом. 305 (11,2 → 10), который инспектор отклонил, она оставляет: по одному признаку его не отличить от
    нарушения в 11 %.
- **Метрики `-few2` на VALIDATION.** Precision 0,857, recall 1, FPR 1 — пороги §14 не пройдены.
  - Отклонённая запись одна (520,2 → 15,8, в 33 раза), и модель оценила её в 0,267 — выше порога.
  - Порог 0,2 — из правила `few_positives`, его не подбирали ни по VALIDATION, ни по комплектам.
  - При пороге 0,3 VALIDATION проходит 7 из 7, комплекты 1–3 остаются без понижений. Но такой порог подобран по
    единственной отклонённой записи VALIDATION, и метрики на ней тогда уже не независимые.
- **Рекомендация ML.** Текущей можно делать `scorer-ds-2026.09.2-few2`, но только после влития кода режима и
  пересборки стенда. Перед этим повторить проверку на комплектах 1 и 3. Решение — за Командой.

**Данных мало.** Публичные проверки организаторов — 10 записей, и все нарушения: для классификатора это не данные.
Источник — решения инспектора на стенде, выпущенные версией набора в api. Api передаёт текущую одобренную модель в
запросе сравнения. Чтобы скорер понижал с пользой, нужны десятки подтверждённых решений разных параметров,
а не одно.

## Метрики качества (§14) — `inspector-ml eval`

Готово: `eval ocr` (Character Accuracy, CER, WER, покрытие), `eval extract` (сверка
извлечения с публичным эталоном организаторов: ключ, значение, страница) и `eval coverage`
(находимость всех параметров матрицы на живых документах, ниже).

### Находимость параметров: `eval coverage`

Эталон организаторов — 15 проверок, а параметров 132. `eval extract` отвечает, верно ли найдено
там, где эксперт разметил, но молчит о том, **где параметр вообще находится**. `eval coverage`
закрывает второй вопрос: по каждому параметру × стадии × объекту — в скольких документах нашлось
значение, каким способом, с примерами и со списком подозрительных значений.

```bash
inspector-ml eval coverage ~/ml-precompute/storage --parser-version 0.4.0     --corpus /mnt/d/datasets --workers 6 --jsonl coverage.jsonl > coverage.json
```

- считается **по кешу разбора**, а не по PDF: разбор корпуса — часы, извлечение по готовому кешу —
  минуты. Путь — `STORAGE_DIR` с каталогом `parsed/`, по умолчанию из настроек;
- извлекатель выбирается тем же `extract.api.extractor_for`, что и в сравнении, а матрица читается
  из того же `data/matrix/params.csv`, что загружает api, — иначе замер мерил бы не то, что работает
  на стенде;
- `--corpus` даёт в отчёте имена файлов и объекты вместо sha256. Объект — папка перед первой папкой
  стадии («ПД», «Проектная документация», «Стадия П»): так устроены выгрузки организаторов;
- `--jsonl` сохраняет строку по каждому документу — по ней удобно сравнивать прогоны до и после
  правки.

**Подозрительное — не значит ложное.** Это список для глаз, чтобы ложные значения не прятались за
ростом находимости:

| Признак | Что значит |
|---|---|
| `out_of_range` | число вне `min_value`/`max_value` матрицы |
| `not_in_enum` | значение не из `enum_values` |
| `not_a_number` | у числового параметра значение не число |
| `word_fragment` | короткое значение есть в тексте только внутри слов: «а» из «лифт**а**» |
| `shared_value` | одно число с одной страницы взяли три и больше параметров — число из чужой фразы |

Короткость сама по себе не признак: «A+» и «B» — законные классы энергоэффективности. Подозрительна
склейка со словом.

### Компьютерное зрение: `eval cv`

Классификатор страниц, стадия по штампу, локализация доказательства и OCR — против открытой разметки
обучающей части `РАЗМЕЧЕННЫЙ_TRAIN_PUBLIC_203` ([`eval/cv.py`](../../services/ml/src/inspector_ml/eval/cv.py)).
Скрытую `РАЗМЕЧЕННЫЙ_TEST__213` команда открыть отказывается.

```bash
inspector-ml eval cv /mnt/d/datasets --storage ~/ml-precompute/storage --parser-version 0.4.0            # минуты
inspector-ml eval cv /mnt/d/datasets --storage ~/ml-precompute/storage --parser-version 0.4.0 --ocr-pages 60  # + OCR, GPU
```

Всё, кроме OCR, считается по кешу разбора (203 файла — 12 секунд). OCR — по исходным PDF на
**постоянном наборе страниц**: выборка по хешу ключа «файл:страница», одна и та же при каждом прогоне,
только страницы с годным текстовым слоем (он и служит эталоном).

**Замер 25.09** (кеш 0.4.0, код `main`):

| Что | Метрика | Значение |
|---|---|---|
| «Странице нужен OCR», 10 142 страницы | accuracy / precision / recall / F1 | **0.952 / 0.855 / 0.999 / 0.921** |
| то же на страницах без текстового слоя, 388 | recall | 0.997 |
| Стадия по штампу, 202 файла | accuracy / macro-F1 | **0.970 / 0.934** (ПД 0.97, РД 0.84, ИД 0.995 по F1) |
| Страница доказательства, 12 эталонных | доля верных | **0.917** |
| Рамка доказательства, 9 выверенных | центр эталона внутри нашей / IoU ≥ 0.5 | **0.78 / 0.11** |
| OCR, 60 страниц, настройки продукта (300 dpi, 4000 px, плитки 1600), GPU | Character Accuracy по странице / построчно / WER | **0.812** / 0.747 / 0.71 (по странице: текст 0.818, чертежи 0.785) |
| то же одной плиткой (2000 px, без нарезки) | то же | 0.876 / 0.900 / 0.56 (текст 0.904, чертежи 0.757) |

Как читать:

- **Precision «нужен OCR» 0.855 — это спор с разметкой, а не наша ошибка.** Из 487 страниц, которые мы
  распознаём, а разметка считает ненужными, 471 — в трёх томах «Примера нарушений» (Том 1.2 Книга 1,
  «ИЗМ ПО ЗАМЕЧАНИЯМ…-ОПЗ», БЭОКС), где текстовый слой — мусор: «Ɉ5M5EF6> E >7D4=<G5==>=»
  вместо «Общество с ограниченной ответственностью». Ради них в 0.4.0 и появилось распознавание
  битого слоя. Если засчитать их как верные, precision — **0.994**. Пропускаем страницы, которым нужен
  OCR, почти никогда: 3 из 2867.
- **Стадия — 196 из 202.** До нового порядка признаков было 0.886 / 0.873. Ошибки: 4 ПД → РД,
  1 РД → ИД, 1 ПД без стадии; смешанная разметка «RD_ID_MIXED» принимает и РД, и ИД.
- **IoU ≥ 0.5 почти не проходит по построению:** эталон обводит одно значение («B40»), наше
  доказательство — ячейку или абзац. Попадание центра эталона внутрь нашей рамки — 7 из 9; промахи —
  КЖ1.1.1 стр. 7 (M-058 отдаёт одно значение на документ, самую тонкую зону, со стр. 3) и КЖ1.1.2 стр. 4.
- **OCR ниже порога ТЗ (0.95), и главная потеря — стыки плиток.** Строка, разрезанная границей плитки,
  приходит из двух плиток половинами, их рамки пересекаются только в полосе перекрытия (160 px), и склейка
  по IoU ≥ 0.4 (`ocr/render.dedupe`) оставляет обе: «ограниченно енной», «СТРОИТЕЛЬНО ЕЛЬНОГО».
  Распознанного текста на 7 % больше эталона. Зато для чертежей 2000 px мало — мелкий текст теряется
  (по странице 0.785 → 0.757). Сшивка строк на стыках — отдельной правкой
  (`PARSER_VERSION 0.5.0`): по странице 0.812 → 0.880.
- **Эталон для OCR проверяется сам.** Текстовый слой служит эталоном, только если он годен и по разметке,
  и по нашему классификатору, в нём не меньше половины кириллицы и нет сплошных повторов
  (`reference_is_valid`). Без этого в выборку попадали мусорные слои («D545?L=O5 (<<=<<4?L=O5») и слой,
  напечатанный поверх себя («Заказчик: Заказчик: Заказчик:»), — с точностью 0 при любом распознавании,
  и итог занижался ещё на 9 п.п. (старой построчной метрикой: 0.52 вместо 0.61).
- **Пропущенный мусорный слой.** На обучающих объектах 103 страницы из ~9 750 с «годным» по
  классификатору слоем не содержат кириллицы (≥ 100 букв, кириллицы меньше половины) — часть из них мусор,
  который OCR не получил («8" 9 39 6 rF I 9r» в АОСР №2.5_ВП). Отдельная задача для классификатора страниц.
- **Оси.** Рамки организаторов отсчитываются от нижнего края страницы (как в PDF), наши — от
  верхнего; эталон переворачивается (`top_left`). Отдельные рамки многозначной аннотации
  («1000 | 1200 | 1500») сравниваются по одной.

### Прогоны в MLflow: `--mlflow`

Любой из трёх замеров пишется в MLflow (профиль compose `mlops`):
api держит там эталонный набор (`inspector-datasets`) и модели (`inspector-models`), замеры идут
в третий эксперимент — **`inspector-evals`**. Так на защите видна история: «находимость 15 → 22 из
132» — два прогона рядом, у каждого коммит и хеш матрицы.

```bash
# на стенде, из контейнера ml — MLflow в той же сети compose
inspector-ml eval coverage --parser-version 0.4.0 --workers 3 --mlflow http://mlflow:5000/mlflow
# адрес можно задать один раз: MLFLOW_URL (то же имя, что у api), тогда хватит --mlflow
```

| Замер | Метрики | Параметры прогона |
|---|---|---|
| `coverage` | `params_found`, `params_pd_and_rd`, `params_all_stages`, `documents.<стадия>`, `found.<тип>`, `suspicious`, `param.<код>.documents` и `.suspicious` | версия разбора, матрица и её хеш, процессы, объекты |
| `extract` | `recall_key`, `recall_value`, `recall_page` — всего и по каждому коду эталона (`KR-058.recall_value`) | выборка, файл эталона, матрица, коды |
| `ocr` | `character_accuracy`, `cer`, `wer`, `coverage`, `mean_confidence`, `seconds_per_page` | файл, движок, dpi |

У каждого прогона — краткая сводка в примечании (`mlflow.note.content`), коммит
(`mlflow.source.git.commit`: `GIT_COMMIT` из окружения образа или `git rev-parse`) и **полный отчёт
файлом `report.json`** — при сервере с `--serve-artifacts`, как в compose.

- **Запись по возможности**, как у api: MLflow выключен или не отвечает — отчёт напечатан, код
  возврата 0, причина в журнале.
- **Только внутрь контура.** В отчёте находимости — фрагменты текста документов, поэтому адрес
  проверяется правилом `llm.client.is_local`: имя сервиса compose и `localhost` — можно, внешний адрес —
  отказ без единого запроса.
- Клиент — REST на `httpx` ([`eval/tracking.py`](../../services/ml/src/inspector_ml/eval/tracking.py)),
  без пакета `mlflow`: нужно пять вызовов, а пакет тянет сотни мегабайт.

`eval extract` сверяет с эталоном организаторов уже четыре параметра: PZ-002, PZ-009, KR-055, KR-058.
Эталон KR-058 — перечень толщин зон («1000/1200 мм»), и значение совпадает, если наше число — одно из них.

**Замер 25.09** (`eval extract /mnt/d/datasets --split TRAIN_PUBLIC`, открытая разметка на диске,
код `main`): 12 точек эталона из 5 проверок (TRAIN-0011…0015) — **ключ 12/12, значение 12/12,
страница 11/12**. Единственный промах страницы — KR-058 в РД КЖ1.1.1: эталон указывает листы 3 и 7,
а M-058 отдаёт одно значение на документ (самую тонкую зону) — с листа 3. Проверок PZ-002 в открытом
эталоне нет вовсе; остальные 10 из 15 проверок — IOS4-078/079 (отопление) и FREE-HEATING-001
(свободный поиск), своих извлекателей у них нет.

Отчёт в JSON и Markdown:

- Character Accuracy, CER, WER, coverage (NFC, схлопнутые пробелы);
- Exact Match ключевых полей;
- linking accuracy;
- localization (file + page + IoU ≥ 0.5);
- P/R/F1 по evidence_group;
- FPR на `NEGATIVE_VERIFIED` и устаревших редакциях.

Метрики считаются в разрезе объектов, разделов и типов. Дополнительно публикуются размер выборки и 95% доверительный интервал (bootstrap).
