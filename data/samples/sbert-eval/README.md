# Опыт с Sentence-BERT: извлечение числовых параметров матрицы (26.09)

Вопрос: может ли модель из стека (Sentence-BERT) находить параметры матрицы по похожей формулировке, если
регулярка матрицы — дословное название (так у 106 параметров из 132)? Здесь — разметка, метрики и отчёт;
скрипты — [`services/ml/scripts/sbert_eval/`](../../../services/ml/scripts/sbert_eval/).

## Условия

- **Выборка:** обучающие объекты с кешем разбора 0.5.0 — Новослободская, Алтуфьевское 79Б, «Пример нарушений»
  (259 документов). Речников (скрытая тестовая часть) не использован.
- **Параметры:** 75 числовых параметров матрицы. Ячейка «документ × параметр» — единица счёта (19 425 ячеек).
- **Модель:** `paraphrase-multilingual-MiniLM-L12-v2`, процессор, `sentence-transformers 6.1.0`, `torch 2.14.0+cpu`.
- **Методы:**
  - `product` — то, что продукт извлекает сегодня (свой извлекатель или регулярка матрицы). У M-002 — только точка
    «Общая площадь здания», без помещений: сверка по помещениям — отдельная задача;
  - `sbert` — со страницы берутся кандидаты «подпись → число с единицей» (строки таблиц и фразы), единица должна
    совпадать с единицей параметра, подпись ранжируется по косинусной близости к названию и якорям параметра;
    прогноз — лучший кандидат документа с близостью ≥ τ;
  - `sbert_excl` — то же плюс «одна подпись — один параметр» (подпись достаётся самому близкому параметру);
  - `fallback` — продукт, а где он ничего не нашёл — `sbert_excl`.

## Эталон — пул с разметкой

Готового эталона по 132 параметрам нет ни у организаторов, ни у нас: задания 9×132 в открытой разметке объектов
10–18 не проверены (`NOT_REVIEWED`), закрытый эталон организатора не используем.
Поэтому эталон — **пул**: всё, что нашёл продукт, и три лучших кандидата Sentence-BERT на ячейку с близостью ≥ 0,7.
Разметка — единица «параметр — подпись — число»: `1` верно, `0` неверно, `?` не решить (исключается из счёта).

`labels.jsonl` — 2425 размеченных единиц: 222 верных, 2126 неверных, 77 «?». Разметка машинная, по
фрагментам текста; **это серебряный эталон, до проверки человеком**.

Ограничения, из-за которых цифры не абсолютные:

- полнота — относительная: что не нашёл ни один метод, считается отсутствием значения (допущение пула);
- порог τ подобран на этой же выборке — это оценка сверху; честная проверка — на отложенных объектах 12, 17, 18
  после их разбора;
- accuracy почти единица у всех методов: 19 тыс. ячеек из 19,4 тыс. — законные «пусто/пусто». Смотреть на
  precision, recall, F1;
- у Sentence-BERT нет пересчёта единиц (600 мм при параметре в метрах).

**Вывод.** Одна модель хуже правил: подпись «Строительный объём» похожа и на общий, и на подземный, и на надземный
объём; «нагрузка в точке подключения» похожа на суточный расход; нормы («не менее 1,2 м») похожи на решения.
Как **запасной путь** после правил она поднимает полноту с 0,54 до 0,71 при точности 0,72 (F1 +0,06). Больше всего
выигрывают параметры, у которых нет своего извлекателя: M-017 (0 → 0,94), M-008 (0,32 → 0,83), M-004 (0,50 → 0,82),
M-114 (0 → 0,75), M-061 (0 → 0,57). Проигрывают счётные параметры (этажность, машино-места) — там модель тащит
любые числа с подписью «этаж».

**Попутно.** У продукта M-002 «Общая площадь здания» — 17 ложных из 20: берётся итог этажной экспликации
(«Общая площадь помещений — 2797,1» при площади здания около 11 тыс. м²).

## Проверка на отложенных объектах 12, 17, 18 (27.09)

Отложенные объекты — 12_Полярная_25_ДОО220к9, 17_Изумрудная_12, 18_Октябрьская_103: 714 уникальных документов
ПД и РД, кеш разбора 0.5.0 (разбор 26.09, код `main` 080b7a3; продукт — более поздний `main`). По ним **ничего не
подбиралось**: τ = 0,9 и все фильтры взяты с обучающих объектов.

Разметка `labels-heldout.jsonl` — 452 единицы: все значения продукта (159) и все кандидаты Sentence-BERT с
близостью ≥ 0,85 (293). Этого хватает для точности при τ = 0,9. Кандидаты 0,7–0,85 (2884 единицы) не размечены,
поэтому полнота у всех методов — **оценка сверху** (пропущенные там верные значения не попали в эталон);
сравнение методов между собой честное — эталон у них общий.

**Без фильтров запасной путь на отложенных не помог:** F1 0,703 против 0,718 у правил
(`metrics-heldout-nofilter.json`). Прибавка обучающих объектов не перенеслась: из 44 лишних ложных 22 дала
этажность — числа под подписями «этаж», «Этаж», «строение 1, этаж».

### Почему модель ошибается

Sentence-BERT отвечает на вопрос «похожа ли подпись на название параметра», а нужно «это значение параметра
для этого здания». Отсюда пять типов ошибок (все — из разметки):

1. **Уточнение меняет смысл, а близость — почти нет:** «Общая площадь здания, подземная часть» → M-002 (0,89),
   «Строительный объём сносимого здания» → M-004 (0,96), «Общий расчётный расход водоотведения» → M-016 (0,89).
2. **Общие подписи:** «этаж → 20», «Площадь → 31 969,9» — номера строк, листов, этажей.
3. **Модель всегда что-то выбирает:** если значения в документе нет, берёт самое похожее; правила молчат.
4. **Чужое здание:** «Площадь застройки → 81,3» (близость 1,00) — из кадастровых сведений соседнего сооружения.
5. **Порог не переносится:** τ подобран на жилых домах, отложенные — детский сад, школа, ремонт.

### Фильтры поверх модели (`scripts/sbert_eval/sbert_filter.py`)

Кандидат Sentence-BERT отбрасывается до выбора лучшего, после чего кандидаты ячейки ранжируются заново:

- `range` — значение вне `min_value`…`max_value` параметра из матрицы;
- `integer` — у счётного параметра (шт., ед.) дробное значение;
- `generic` — в подписи меньше двух содержательных слов;
- `stops` — в подписи есть основа слова, которой нет в названии и якорях параметра и которая на **обучающих**
  объектах встречалась не меньше 3 раз и только у неверных кандидатов (`stops-train.json`, 42 основы:
  «строен», «этаж», «сущест», «павиль», «итог», «более», «кадаст»…).

Порог «не меньше 3» выбран перекрёстной проверкой внутри обучающих (учим на двух объектах, проверяем на
третьем; `cv-train-filters.txt`): 0,713 без фильтров → 0,730 со всеми фильтрами, пороги 3 и 4 — лучшие.
Эталон при фильтрах — по нефильтрованному пулу (`metrics.py --gold-pool`): иначе отсеянный верный кандидат
убирал бы ячейку из эталона и завышал полноту — первая версия замера так и ошиблась (0,781 вместо 0,749).

**Итог на отложенных** (`metrics-heldout.json`, `report-heldout.md`):

## LLM проверяет кандидатов (27.09, опыт вне продукта)

Гипотеза: языковая модель отличит «значение параметра для этого здания» от похожей подписи лучше, чем
правила и Sentence-BERT. Данные — [`llm/`](llm/). Скрипт опыта ходил во внешний API (OpenRouter), поэтому 28.09 он
убран из репозитория: организаторы запрещают внешние LLM API, и в комплекте сдачи его быть не должно.

- **Как.** По каждому кандидату, который может стать ответом (все значения продукта и кандидаты Sentence-BERT с
  близостью ≥ 0,9), модель отвечает `yes` / `no` / `unsure`: «является ли это значение значением параметра X для
  проектируемого объекта». В запросе — код, название, единица и раздел параметра из матрицы, подпись, число и
  фрагмент до 220 символов. Промпт общий: задача и общие признаки «не то значение» — другое здание, часть вместо
  целого, норма вместо решения, номер листа. Ошибки, увиденные при разметке, в него не вписаны. Кандидаты с
  ответом `no` убираются, дальше — те же `metrics.py --gold-pool` и τ = 0,9. Ничего не подбиралось ни на
  отложенных, ни на обучающих объектах.
- **Модели** — через OpenRouter, температура 0, без рассуждений:

  | Модель | Параметров | Где можно запустить |
  |---|---|---|
  | Qwen3-235B-A22B-2507 | 235B, активных 22B | мощная видеокарта |
  | Qwen3-30B-A3B-Instruct-2507 | 30B, активных 3B | локально |
  | Qwen3.5-9B | 9B | видеокарта рабочей станции |
  | Qwen3-8B | 8B | видеокарта рабочей станции |

  Всего 1960 запросов, около 0,9 млн токенов — несколько центов, около 2 с на кандидата.
- **Внешний API — только для опыта.** В продукте — только локальные модели. В запрос не
  уходят закрытые материалы и Речников, ФИО вычищаются, провайдерам с хранением данных запрос не
  отдаётся (`data_collection: deny`).

**Выводы.**

- **LLM-проверка всех значений — самая сильная прибавка за весь опыт:** F1 +0,13 на отложенных и +0,14 на
  обучающих объектах у 235B и 30B-A3B. На отложенных интервалы с правилами не пересекаются. Точность на
  отложенных 0,78 → 0,95. Модель отсекает кадастровые сведения соседних сооружений, высоту противостоящего
  здания, водоотведение вместо водопотребления, гектары вместо м².
- **Лёгкая Qwen3-30B-A3B не уступает Qwen3-235B.** Её можно поднять локально, это путь для продукта без внешних
  API.
- **Для кандидатов Sentence-BERT хватает любой модели:** отсекают 57–86 % неверных, верные почти не теряют.
- **Для значений правил важен размер:** Qwen3.5-9B ещё близка к большим, Qwen3-8B отсекает только половину
  неверных.
- **Чего модель не видит:** «Общая площадь помещений — 2797,1» — итог этажа, а не площадь здания. Это не
  понять из фрагмента в 220 символов, нужен контекст таблицы.

**Правка разметки** (`llm/label-corrections.jsonl`). Все 132 расхождения разметки с любой из моделей я
перепроверил в обе стороны. В 117 случаях разметка осталась прежней: чаще ошибалась модель — «этаж»,
кадастровые сведения, итоги этажей. Исправлено 15 меток:

- на обучающих: 9 значений M-016 оказались водоотведением, горячей водой или «К1», а не общим
  водопотреблением; одна цитата СП для M-041; 3 метки → «?»;
- на отложенных: 2 метки → «?».

Правились только найденные моделью ошибки, поэтому перепроверенная разметка немного подыгрывает LLM. Выводы от
версии разметки не меняются — видно по цифрам в квадратных скобках. Сами `labels.jsonl` и `labels-heldout.jsonl`
не менялись: правки — отдельным файлом.

## Как повторить

```bash
# пул (кеш разбора 0.5.0, строки eval coverage для стадии и объекта)
SBERT_MODEL=D:/sbert-exp/model python scripts/sbert_eval/sbert_pool.py <storage> 0.5.0 <coverage.jsonl> pool.jsonl --objects train
python scripts/sbert_eval/clean_pool.py pool.jsonl <coverage.jsonl> train pool-clean.jsonl docs.txt
python scripts/sbert_eval/label_keys.py pool-clean.jsonl keys.jsonl
python scripts/sbert_eval/metrics.py pool-clean.jsonl data/samples/sbert-eval/labels.jsonl docs.txt metrics.json
python scripts/sbert_eval/report_md.py metrics.json report.md

# фильтры: стоп-основы — только по обучающим, применение — к любому пулу, эталон — по нефильтрованному
python scripts/sbert_eval/sbert_filter.py learn pool-train-clean.jsonl data/samples/sbert-eval/labels.jsonl stops.json
python scripts/sbert_eval/sbert_filter.py apply pool-heldout-clean.jsonl stops.json pool-heldout-filtered.jsonl
python scripts/sbert_eval/metrics.py pool-heldout-filtered.jsonl data/samples/sbert-eval/labels-heldout.jsonl \
    docs-heldout.txt metrics-heldout.json --gold-pool pool-heldout-clean.jsonl --taus 0.9
```

LLM-проверку повторить из репозитория нельзя: её скрипт ходил во внешний API и 28.09 убран. Ответы моделей
остались — `llm/judge-*.jsonl`, сводки — `llm/summary-*.md`.

Пул отложенных объектов строился по кешу `~/ml-corpus` (разбор ПД и РД объектов 10–18), объект и имя файла — из
журналов разбора по sha256, стадия — по папке («пд», «рд»): по штампу она не определилась у 404 документов из 1775.
