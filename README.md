# Продукт

**«Продукт»** — ИИ-сервис отслеживания и анализа изменений между стадиями проектирования, а также контроля исполнительной документации.
Решение Команды для кейса 10 Соревнования.

> Документация — [docs/README.md](docs/README.md), комплект сдачи — [docs/SUBMISSION.md](docs/SUBMISSION.md).

## Что делает система

Сервис автоматически сверяет проектную (ПД), рабочую (РД) и исполнительную (ИД) документацию по **матрице из 132 параметров**. Он распознаёт текст, таблицы и чертежи в PDF (DOCX и XML принимаются в комплект, но пока не разбираются), выбирает актуальные утверждённые редакции и сопоставляет значения между стадиями. Результат — **цифровой протокол несоответствий** с привязкой к документу, листу и области на странице.

Инспектор в веб-интерфейсе подтверждает или отклоняет каждое расхождение (не больше 3 кликов). Подтверждённые нарушения передаются в ИАИС «РиН», а решения инспектора пополняют эталонный набор для управляемого дообучения.

```
React (web) ──REST/OpenAPI──▶ Node.js (api) ──RabbitMQ──▶ Python (ml: OCR · NLP · CV · compare)
                                │  PostgreSQL · MinIO · ClamAV          │  Redis · MinIO
                                └──▶ ИАИС «РиН»      Prometheus · Grafana · ELK
```

Подробнее — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Что готово

Комплект сдачи и где закрыто каждое требование организаторов — [docs/SUBMISSION.md](docs/SUBMISSION.md).

### Бэкенд (api)

- Запуск всей системы одной командой: `./start.sh` сам заводит секреты, выбирает вариант образа ML под железо, поднимает контур и проверяет вход.
- API, загрузка и реестр файлов (манифест организаторов, архив `.zip`, папка; стадия по папкам, реестр из корня находится сам), оркестрация ML, верификация и финализация, версии протокола.
- Экспорт PDF / DOCX / XML / GOLD и формат организаторов (`submission`, включая находки вне матрицы); примеры выходного JSON — [docs/examples](docs/examples/README.md).
- Журнал действий инспектора и системы; журнал пишется до действия, изменений без следа нет.
- Обмен с внешней ИС в обе стороны: мок `services/rin-mock`, автозабор пакетов, отправка результатов с повторами.
- ML-контур: версии GOLD-набора с хешами, реестр моделей с порогами §14 и откатом, недельный отчёт, запросы на откат финализации.
- Защита входа: 429 с `Retry-After` по паре «логин + адрес» и по адресу; пароль, равный логину, запрещён на сервере; пределы распаковки архивов и размера пакета.
- Зависший разбор не висит: api сверяет задачи с ML, переотправляет потерянные при перезапуске, снятый по таймауту файл уходит в ошибку.
- Работа без интернета проверена одной командой — `scripts/stand-offline-check.sh`; образы для закрытого контура — одним архивом с контрольной суммой (`scripts/images.sh`).
- Импорт матрицы в работающую базу — `npm run matrix:import` с планом без записи и версией матрицы; вся матрица включается одной командой — `--activate all`.

### Движок сравнения

- Дерево статусов, эталон ПД, выбор актуальной редакции (цепочки, выбор инспектора или единственной утверждённой; конфликт блокирует вывод до решения инспектора).
- **Проверяются все 132 параметра матрицы**: у каждого есть правило извлечения, значение берётся из документов раздела параметра, триггеры матрицы разобраны все.
- Применимость параметра к объекту по реестру (различает «реестра нет» и «реестр пуст»), сопоставление экземпляров правила между стадиями, ссылка на совмещённые листы.
- Инкрементальный пересчёт: по изменённым файлам определяются затронутые параметры, остальные переносятся из прошлой версии протокола вместе с решениями инспектора.
- Логические гипотезы: мини-язык правил согласованности между стадиями без `eval`, трёхзначная логика.
- Сравнение по каждой стадии — по строке на РД и ИД со своей дельтой и выводом (`stage_comparisons`).
- Контрольный комплект 3 (48 документов ПД / РД / ИД с ошибками по направлениям триггеров) даёт ожидаемый статус по 132 параметрам из 132, протокол за 22 с (`scripts/matrix-check.py`).

### ML-конвейер

- Разбор PDF с bbox, кеш разбора по sha256, классификатор качества страниц, основная надпись и метаданные документа (стадия по штампу, шифр проекта, язык, доля сканов, организация-разработчик).
- OCR сканов на PaddleOCR с метрикой Character Accuracy; таблицы пересобираются после OCR.
- Извлечение параметров с таблицами и bbox, свои извлекатели с ключом места; постоянный замер находимости `inspector-ml eval coverage`.
- Пары листов ПД ↔ РД по отметкам уровня на чертеже; совмещение растров листов-чертежей и гипотеза `VISUAL_DIFF` с наложением листов.
- Изменённые числа в совпадающем тексте ПД и РД — гипотезы без модели.
- Предрасчёт корпуса на замороженной версии разбора: 423 документа, 29 498 страниц; кеш `0.5.0` загружен на стенд.
- Sentence-BERT — запасной путь извлечения числовых параметров за флагом `SBERT_ENABLED`.
- Скорер кандидатов (`inspector-ml train`): выгрузка GOLD-набора из api с проверкой хешей, логистическая регрессия, метрики §14 на VALIDATION, регистрация модели.
- Очередь задач ML: зависший процесс убивается вместе с группой, сломанный пул пересоздаётся, результаты на диске переживают перезапуск ml.
- Замеры пишутся в MLflow — эксперимент `inspector-evals`.

### Фронтенд

- Дашборд объектов: светофор, статус последней проверки, счётчики, «Соответствие».
- Загрузка файлами, папкой и архивом с реестром, комплектность, дозагрузка.
- Протокол: версии, 5 таблиц и реестр файлов, финализация и её отмена с причиной, экспорт, передача во внешнюю ИС.
- Верификация: синхронные панели ПД / РД / ИД на pdf.js с рамками доказательств, решение в 3 клика и с клавиатуры, правка доказательств новой версией, массовое подтверждение, разделение составного несоответствия.
- Сравнение листов и гипотезы: наложение страниц по матрице совмещения, «Соответствие N %», решение по гипотезе и «Сделать кандидатом».
- Администрирование: матрица параметров, нормативные документы, логические правила, журнал аудита, разбор записей для дообучения, интеграция, дообучение (набор, версии, модели, недельный отчёт), MLflow.
- Интерфейс по ролям, уведомления, приложение электронной подписи к файлу, тёмная тема.

### Сквозной сценарий

Загрузка → протокол → решения → отчёт пройдены вживую на настоящих документах, в Docker, с настоящим ML. Комплект «Алтуфьевское 79Б»: сборка и старт с нуля 8 мин 25 с, разбор 4286 страниц за 33 мин, протокол `READY` — 76 файлов, 67 проверок, 49 пар совмещённых листов. Контрольный комплект 3 через сайт — по файлам, папкой и архивом — 132 параметра из 132 с ожидаемым статусом, протокол за 21–25 с.

### Ограничения

- **OCR ниже порога ТЗ 0,95:** Character Accuracy по странице 0,81, со сшивкой строк на стыках плиток — 0,88 (`PARSER_VERSION 0.5.0`).
- **Модель скорера не опубликована:** на контрольных комплектах обученная модель понижала внесённые ошибки; модель режима «мало данных» зарегистрирована, но пороги §14 не прошла, и api её не одобряет (REQ-ML-04). Стенд работает на правилах.
- **Sentence-BERT на стенде выключен:** на «Алтуфьевское, 79Б» прогон дольше (447 с вместо 266 с) и требует больше памяти, а новых кандидатов не дал; включается флагом.
- **Языковая модель по умолчанию выключена:** рантайма и весов в образах нет, допустим только локальный адрес.
- Визуальная подпись листа для фасадов, разрезов и сканов без отметок уровня не сделана.
- На время экспертизы включён открытый вход (`OPEN_ACCESS`); токен входа хранится в `localStorage`.

## Быстрый старт

### Минимальная локальная разработка (без Docker)

```bash
# 1. Клонировать репозиторий
git clone https://github.com/mixvadimyt-clon/425c044b3e1dfbf2bc140402005ee151073fa592cbc096a8eaf626b1c3ee7a3b.git inspector
cd inspector

# 2. Запустить api и web одной командой (зависимости поставятся сами; .env создастся из .env.example)
./scripts/start-local.sh
```

Откройте в браузере: **http://localhost:5173**  
API работает на: **http://localhost:3000**

**Тестовые логины:** `inspector` / `inspector`, `supervisor` / `supervisor`, `admin` / `admin`

Скрипт поднимает только то, что включено в `.env`: ML-сервис — при `ML_TRANSPORT=http` (по умолчанию работает ML-заглушка внутри api), мок внешней ИС — при `RIN_URL=http://localhost:4020` ([services/rin-mock](services/rin-mock/README.md)).

### Детальный запуск

**Backend (services/api):**
```bash
cd services/api
npm install
npm run gen        # генерация типов из контрактов
npm run db:reset   # инициализация SQLite базы
npm run dev        # http://localhost:3000
```

**Frontend (services/web):**
```bash
cd services/web
npm install
npm run gen        # генерация типов из контрактов
npm run dev        # http://localhost:5173
```

**Мок внешней ИС (services/rin-mock, по желанию):**
```bash
cd services/rin-mock
npm start          # http://localhost:4020; в .env api: RIN_URL=http://localhost:4020
npm run package -- <папка комплекта> --object-id ALT79B --name "ЖК …"   # пакет документов для автозабора
```

### Полный локальный прогон — обкатка перед показом

Поднять всю систему у себя, загрузить настоящий комплект **ПД + РД + ИД** и пройти сценарий
до выгрузки протокола: [docs/guides/local-demo-run.md](docs/guides/local-demo-run.md).

```bash
python3 scripts/demo-set.py /путь/к/датасету            # какие объекты годятся: нужны все три стадии
python3 scripts/demo-set.py /путь/к/датасету --object <объект> --out dataset --apply
./start.sh
```

`demo-set.py` показывает не то, что лежит на диске, а **что увидит сервер**: стадию он определяет
по именам папок. Собранный комплект кладётся вместе с реестром — без реестра проверка честно
уходит в `CLARIFICATION_REQUIRED`.

### Проверки

Те же проверки, что гоняет CI, только локально:

```bash
./scripts/check-local.sh             # contracts, api, web, rin-mock, ml
./scripts/check-local.sh api web     # только нужное
```

Скрипт повторяет `.github/workflows/ci.yml` шаг в шаг: линт и свежесть `contracts/dist`, `tsc`,
сборку и тесты каждого сервиса, `ruff` и `pytest` для ml. Нужны Node.js 22 и `uv`; чего нет —
пропускается с пометкой. Сборку образов и сквозной прогон в Docker он **не** заменяет: это
`images.yml` или `./start.sh`.

### Вся система одной командой — проверяющему

Нужен только Docker (Compose v2). Видеокарта не обязательна, но используется, если найдена.

```bash
git clone https://github.com/mixvadimyt-clon/425c044b3e1dfbf2bc140402005ee151073fa592cbc096a8eaf626b1c3ee7a3b.git inspector
cd inspector
./start.sh
```

Скрипт сам создаёт `.env.stand` со свежими секретами, выбирает вариант образа ML под железо, собирает образы, поднимает веб-клиент (Caddy), api, ml и мок внешней ИС «РиН», дожидается готовности и проверяет, что интерфейс отдаётся и вход работает. В конце печатает адрес и пароль демо-пользователей (`inspector`, `supervisor`, `admin`, `ml`).

**Первая сборка — 10–25 минут:** в образ ML кладутся веса распознавания, чтобы в работе не требовался интернет. Дальше запуск за секунды.

```bash
./start.sh --gpu            # или --cpu: решить за скрипт, какой образ ML брать
./start.sh --port 8080      # если 80-й порт занят
./start.sh --domain stand.example.ru   # HTTPS, сертификат Let's Encrypt получит Caddy
./start.sh check            # адрес отвечает, интерфейс отдаётся, вход работает
./start.sh logs             # логи api и ml
./start.sh stop             # остановить, данные сохранить
```

**GPU и CPU — честно.** Нормативы производительности организаторы меряют в GPU-конфигурации, поэтому основной вариант — GPU: `./start.sh` берёт его сам, если видит карту с архитектурой 6.1+ и NVIDIA Container Toolkit. Замер в одном и том же образе: страница скана распознаётся за **2,4 с на видеокарте против 34,3 с на процессоре**. Вариант CPU — резервный: на нём работает наш публичный стенд (2 vCPU, без видеокарты), и сканы там не распознаются заново, а берутся из кеша, предрасчитанного на GPU ([ADR-0007](docs/adr/0007-stand-cpu-precomputed-cache.md)). На процессоре распознавание ограничено 30 страницами на документ (`OCR_MAX_PAGES`), а ML получает половину ядер (`ML_CPUS`), чтобы интерфейс не вставал на тяжёлом скане.

**Без интернета.** В работе образы никуда не ходят: веса распознавания лежат внутри образа ML, мок внешней ИС — в том же compose, языковая модель по умолчанию выключена, а нелокальный адрес для неё запрещён в коде, вебхук и Telegram журнала действий выключены. Проверено 23.09 скриптом [`./scripts/stand-offline-check.sh`](scripts/stand-offline-check.sh): api, ml и мок «РиН» во внутренней сети Docker без маршрута наружу — изоляция подтверждается изнутри контейнера, контрольный комплект с одним сканом прошёл до протокола за 84 с, скан распознан на весах из образа, в логах ни одной попытки выйти в сеть. Наружу ходит только веб-сервер Caddy — за сертификатом Let's Encrypt и только если задан домен (`--domain`).

**В закрытом контуре — из готовых образов.** Официальный прогон идёт без интернета, а сборка образов качает пакеты и веса. Поэтому образы собираем мы и передаём архивом с контрольной суммой; на месте сборки нет:

```bash
./scripts/images.sh load inspector-images-<версия>-gpu.tar.gz   # сверит SHA-256 и загрузит образы в Docker
./start.sh --no-build --gpu                                      # или --cpu с архивом варианта cpu
```

Архив собирается командой `./scripts/images.sh save --gpu` (или `--cpu`, `--all`; `--mlflow` добавляет MLflow, Prometheus и Grafana). Внутри — api, веб-клиент, мок «РиН» и ML с весами распознавания; всё остальное — этот репозиторий. Список моделей, версии и лицензии — [docs/domain/models.md](docs/domain/models.md).

**Проверить на примере с известным ответом.** [`scripts/demo-errors-set.py`](scripts/demo-errors-set.py) собирает комплект ПД + РД + ИД с заранее внесёнными ошибками, разбор — секунды. Комплект 1 — жилой дом: три кандидата и одна подтверждённая точка; комплект 2 (`--set 2`) — школа: нарушение, найденное только в ИД, и все три исхода, включая «нужен выбор источника». Примеры выходного JSON — в формате организаторов (`submission`) и GOLD — в [docs/examples](docs/examples/README.md).

До 22.09 ту же команду выполнял CI на каждый PR по сборке; сейчас проверки Actions отключены — минуты исчерпаны до конца месяца, — и сборка проверяется этой же командой на машине с Docker. Остальные проверки — [`./scripts/check-local.sh`](scripts/check-local.sh), шаг в шаг то же, что гонял CI. Переменные, данные, HTTPS, обслуживание, стенд в Yandex Cloud — [docs/guides/deploy.md](docs/guides/deploy.md).

Полный контур из ТЗ (Postgres, Redis, RabbitMQ, MinIO, ClamAV, мониторинг) — по желанию, `docker compose up -d`, подробнее в [docs/guides/dev-setup.md](docs/guides/dev-setup.md).

### Публичный стенд

Стенд в Yandex Cloud ([ADR-0007](docs/adr/0007-stand-cpu-precomputed-cache.md)) **работает непрерывно с 27.09 по 23.10** — обкатка, техническая экспертиза и презентация.

```bash
./infra/stand/yc-stand.sh plan          # что будет создано в облаке и почём
sudo /opt/inspector/infra/stand/setup.sh   # на самой ВМ: Docker, секреты, запуск, сторож, копии базы
```

**Адрес: https://lct.bakost.com** (с 27.09; Yandex Cloud, 2 vCPU / 8 ГБ, без видеокарты — сканы
отвечают из кеша разбора, посчитанного на GPU). **На время экспертизы вход открыт** (просьба организаторов): на странице входа кнопки ролей `inspector`, `supervisor`, `admin`, `ml` — пароль не нужен.
На стенде: контрольные комплекты 1–3 (комплект 3 — все 132 параметра) и выборка ПД и РД объекта
«Алтуфьевское ш., 79Б» из датасета. Порядок развёртывания и обслуживание
стенда — [docs/guides/deploy.md](docs/guides/deploy.md).
